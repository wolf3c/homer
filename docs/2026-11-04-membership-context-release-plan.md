## 2. 兼容关系与旧客户端影响

这里的“旧网站”指四字段契约或上一版带 `deepseek` 的五字段草案；“新网站”指包含必需 `context`、可选 `capabilities` 的通用契约。旧版本之间也不能混用，应先核实发布前基线。

| 客户端 / 网站 | 结果 |
| --- | --- |
| 旧客户端 + 旧网站 | 原有行为，使用旧配置。 |
| 新客户端 + 新网站 | 正常下发并在启动/重启时采用 272000 / 244800。旧本地四/五字段配置仅恢复账号和 Token，再拉取完整新配置，无需重新授权。 |
| 新客户端 + 旧网站 | 拒绝旧响应。若本地只有旧四/五字段配置，则保留凭据但会员推理待配置；若已有完整新缓存，则仍可沿用该缓存。新会员连接不能完成新契约校验。 |
| 旧客户端 + 新网站 | 可能拒绝 context / capabilities 字段、模型或推理强度。已有对应旧格式有效缓存可继续按旧参数运行，刷新报错且不会采用新数值；新登录/重新连接不能完成客户端校验。需要更新客户端。 |

网站代码和私有配置也必须配对：新 context 配置交给旧代码、旧格式配置交给新代码都会校验失败并返回 503。不能把两者分开上线并把中间状态当作可用。

当前未实现按客户端版本返回不同契约，也没有强制升级机制。因此不存在仅靠更新顺序即可让所有新旧客户端无感共存的方案。旧客户端的影响不是只发生在维护窗口：窗口结束后，仍未升级的旧客户端继续无法刷新或重新登录会员。

已有用户不应被要求先退出会员或清除本地文件。已有 Token 不因本次升级而轮换；过期、撤销或本来无效的 Token 不属于此次配置升级可修复的范围。旧客户端的一次登录兑换可能已消费 code 后才在本地拒绝新响应，升级后该次连接需重新发起；这不等于清除了已有登录凭据。

## 3. 推荐更新顺序

### 阶段 A：先准备可交付客户端，保持生产不变

1. 再核对两仓源码、分支与未提交改动；从明确的干净发行源码构建，不把工作区其他功能带入。正式发行 SHA 可以增加另行核准的版本元数据，但必须包含当前通用模型 / context / capabilities 改动的最终提交；不能仅凭当前 HEAD 名称认定发行范围。
2. 确定客户端发行版本、build、目标平台及网站发行版本。现有版本、线上网站 SHA、部署产物和 Latest 均需在真正执行前重新核对；功能提交的父提交不是已经核实的生产回滚目标。
3. 按 [GitHub 构建技能](../.codex/skills/homer-github-build/SKILL.md) 准备并验收安装包。当前 GitHub 桌面规划入口只支持 Mac ARM64；其他平台需另有已验证的构建与安装证据，不能承诺已就绪。正式签名/系统信任按实际平台流程验收，不把 ad-hoc 候选包当作正式分发就绪。
4. 在隔离测试环境完成“新网站 + 新客户端 + 旧缓存”的安装升级、刷新失败后重启恢复、主 Agent 与 Worker 配置采用及 ChatGPT 登录回归。保留旧版本可用安装包与哈希；先完成安装包验收，再进入网站切换窗口。
5. 真正获准后，可以把验收过的客户端附件备入远端草稿并重新下载核对；草稿不是用户可下载入口。切换前必须确认发布附件、下载入口及可执行回退均已准备好。本轮没有执行这些动作。

### 阶段 B：同一维护窗口切换网站代码与配置

1. 发布前记录实际线上网站产物/版本、原 `clientConfig`、原客户端发行与下载入口基线。完整生产设置只在私有操作区安全备份，不进入文档、日志或 Git。只改 `private.homer.clientConfig` 下两个角色的目标配置，不用示例覆盖其他设置。
2. 提前说明会员旧客户端需要更新；维护期间可能无法新登录/重新连接，已有缓存可能继续工作。若业务要求旧客户端持续可重新登录，当前实现不满足，需先另行设计兼容发布，不能将本方案当作无损升级。
3. 网站新代码与新配置作为同一部署单元切换；新旧实例混用期间按维护窗口处理。沿用网站现有 MUP 发布、版本记录、任务排空及健康验收流程，不为了本次配置绕过网站的整体发布约束。
4. 先验收公开 `GET /api/homer/v1/config`：200、`Cache-Control: no-store`、两角色完整数值、无私有凭据；再验收专用测试账号的授权兑换采用同一配置。任一失败停止推进，不先推广客户端来掩盖网站故障。

### 阶段 C：立即开放客户端更新并完成升级验收

1. 网站验收通过后，发布已验收的客户端版本，并核对公开下载字节与摘要，再切换已授权的下载/更新入口。沿用现有分发机制；当前方案不新增自动更新或强制升级能力。
2. 用户先安装新版本再正常启动。新客户端读取旧缓存的账号和 Token，获取新配置并原子保存；本次启动采用新快照。不要让用户清除账号、删除数据或先退出登录。
3. 如果网站配置在客户端运行期间才刷新成功，保持当前进程快照，提示正常重启后采用。失败不会触发热切换，也不要求再次授权。
4. 在已授权的专用验收环境核对主 Agent、实际调度的 Worker、重启/恢复线程以及 ChatGPT 登录；不得只查看设置页或仅凭单个角色的 `config/read` 报告全链路通过。
5. 公告明确旧版不再支持会员配置刷新/重新连接，给出新包固定版本入口。不能假设所有用户已经升级，也不能把低流量观察当作零故障。

不推荐在旧网站仍提供旧格式配置时先向用户推广新客户端；旧缓存用户升级后会暂时失去会员推理能力。推荐顺序缩短这一影响窗口，但仍需要接受旧客户端契约不兼容的长期影响。

## 5. 优先回退模型或数值，保留新契约和新客户端

适用于 DeepSeek 模型或当前参数导致容量、延迟或压缩问题，而升级/登录链路正常的情况。这是本次变更最小的回退。

1. 停止推广本次模型或数值，保留新网站代码、新客户端及通用格式。
2. 通过相同受控网站配置发布，将两角色模型、effort、context 改回发布前已记录且已验收的组合。模型能力和强度以网关已验收的组合为准，会员 Fast 始终为 false，需要自定义目录时同步回退 capabilities；仍保留 context 字段。若只改数值则保留模型选择。不能把删除 context 当作回退。
3. 验收 GET/兑换仍返回合法通用配置、两角色值一致；已运行客户端不会立即降阈值，需重新拉取后正常重启。
4. 对已有长会话单独验收缩小窗口后的恢复与压缩行为；不得宣称回调数值会撤销已经发生的摘要或恢复被压缩的完整上下文。

刷新失败时，客户端可能继续沿用已保存的 272000 / 244800；服务端改值不代表所有运行进程已回退。未确认拉取和重启的用户保留未确认状态。

## 6. 完整回退网站和客户端

适用于客户端实现或新契约本身有缺陷。完整回退涉及分散在用户设备上的缓存，当前没有已实现、已验收的一键降级工具，不能承诺自动无损回退所有用户。

1. 停止新版本分发/推广，保留新旧安装包、版本、摘要和故障证据，不覆盖已发布附件或移动旧标签。下载/更新入口切回操作须使用已核准的旧版本；它只改变后续下载，不会自动降级已经升级的用户。
2. 维护窗口内，将网站代码和私有 `clientConfig` 一起恢复到发布前核实的旧版本与其配套格式配置。不能只删新字段，也不能只回退代码。保留新旧产物与设置的配对记录。
3. 已安装新客户端且已有通用格式缓存的用户，即使旧网站拒绝刷新，仍可能沿用新缓存运行；新客户端仅有旧缓存的用户则仍会等待新配置。网站回退本身不会统一这些设备的运行状态。
4. 确需降级客户端的设备，先正常停止 Homer，备份本机当前私有连接文件，再处理缓存。旧客户端拒绝新的 context / capabilities 缓存，直接覆盖安装旧包不能保证登录可用。
5. 对完整新缓存，先核实目标旧客户端的精确模型和字段合同；不能仅删 context 就认定与旧 DeepSeek 契约兼容。只在隔离副本验证过旧模型、effort 和四字段（或旧 deepseek 五字段）转换后，原子保存同一当前账号和 Token，并保留权限/所有者约束；主动退出状态保持无 Token。仅含账号的待配置/退出缓存需另行准备旧版可读的归属结构，不能强行套用“删字段”。不要用旧备份覆盖更新后的账号、恢复已退出的 Token，或重置整个 profile。
6. 上述本地降级必须先在隔离副本验证，再用于具体设备；当前源码没有此自动降级流程，本轮也未编写或验证。若无法可靠完成，保持文件不动，优先前滚修复新客户端；不得把“清空凭据重新登录”作为默认恢复步骤。
7. 安装已核验旧包，使用配套旧网站，确认账号归属、历史、主 Agent/Worker 和 ChatGPT 登录，再结束该设备的回退。未完成设备不能计作已回退。

如果网站切换失败且尚无用户写入新缓存，恢复旧网站代码+旧配置、保持旧客户端下载即可；无需对用户缓存做批量操作。若已产生新缓存，则必须按受影响设备状态处理，不能用一次服务器回退代表整轮完成。
