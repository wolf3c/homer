# 主 Agent 动态协调与待处理事项：技术方案

更新日期：2026-10-19  
状态：隔离候选已实现，尚未采用或部署；依据 [需求方案](34-main-agent-work-cycle-requirements.md)。本文记录候选的实际契约；合成证据不等同于真实模型或线上验收。

## 1. 设计结论

采用“一个轻量记录实体＋三个记录工具＋现有任务工具”的结构：
- SQLite 负责持久事实；主 Agent 负责处理策略。
- 相关模型轮提供有界待处理摘要，主 Agent 按需查询完整记录，再决定行动。
- 实际派工复用现有任务事务、队列和回执；必要时只补来源引用与事项关联。
- 不建立需求状态机、验收放行器、版本释放关系、自动派工器或新的调度服务。

“高扩展性”来自记录、决策和执行的职责分开，以及稳定 ID 与真实来源；不依赖预留大量字段、插件系统或通用工作流框架。

2026-10-19 只读核对维护源码；这不是日常运行版本的证明。执行架构采用任务仍独立进行，实现前须重新核对实际基线。

## 3. 最小数据模型

候选新增 pending_items 一张表，沿用当前 SQLite 连接，不开独立数据库。DDL 与 pendingSchemaVersion=1 在 pending-items.ts；由现有 RecursiveTasks.migrate 调用，recursiveSchemaVersion 保持 2。

| 字段（建议名） | 含义 |
| --- | --- |
| id | 稳定事项 ID |
| content | 主 Agent 整理的事项内容，作为数据而非指令权限 |
| sourceRequestIdsJson | 真实用户请求 ID 的有序引用；无用户来源的 Agent 建议可为空 |
| relatedTaskId | 可空，事项产生时关联的工作，用于查找上下文，不是执行依赖 |
| linkedTaskId | 可空，最近一次明确关联的实际后续任务；历史操作沿已有回执追查 |
| state | open / closed，只表示是否仍需主 Agent 关注 |
| handlingNote | 当前处理说明，例如暂缓、待用户、已转任务或取消原因 |
| revision | 乐观并发校验用整数，不是任务契约版本 |
| createdAt / updatedAt | 记录与更新时间，排序增加 id 保持稳定 |

来源由宿主绑定或核验，模型不能提交伪造原文或身份。用户要求修改事项时，保留原来源并追加当前真实请求引用；Agent 自己润色不产生新的用户授权。实际来源正文继续在现有聊天历史，避免维护另一套原始消息。

一个数据库沿用既有用户/实例归属；查询和修改必须经过当前主 Agent 与该实例的可见范围检查。不新增猜测的全局用户模型，也不跨实例搜索私有内容。

只有两种关注状态：
- open：后续仍需考虑。暂缓、等待、正在跟进可写说明。
- closed：目前已处理或无需再关注。可表示已转入现有任务系统、用户取消等，不等于执行成功。

状态由主 Agent 显式更新。任务成功/失败不自动改变它；主 Agent 可根据新情况重开。不能让 closed 覆盖任务的失败事实，也不建立 open→成功→已交付等平行生命周期。

首期不加优先级、截止时间、版本门槛、合并实体、复杂多对多映射或通用 metadata。必要查询使用 state、relatedTaskId、稳定时间/ID排序的小型索引；无数据量证据不建设全文搜索和缓存。

## 4. 三个记录工具

下列为建议名称与契约，实施时统一现有命名和参数风格。

| 工具 | 最小输入 | 返回与行为 |
| --- | --- | --- |
| pending_add | operationId、content、可选 relatedTaskId | 宿主绑定来源；返回 id、revision、state；不派工、不改当前任务 |
| pending_list | 可选 id / taskId / state、分页游标及数量、operationId/operationScope、sourceRequestId | 返回记录、真实来源引用、关联与说明；支持查单条、open及closed |
| pending_update | operationId、id、expectedRevision、明确字段 patch | 修改内容/说明/关注状态/关联；校验实际任务与来源，返回新 revision |

默认数量有界、支持游标，超限返回继续查询方式。patch 省略字段表示保留，显式 null 才清除可空关联；空 patch、未知字段和非法状态明确拒绝。

来源引用可以由 Agent 选择已有真实请求，但宿主必须核对请求存在、用户角色、当前实例与可见范围。不能让模型通过参数自称用户，或将 Worker/网页中的文字登记成用户指令。

不提供独立“决定下一步”“自动处理待办”“释放下一轮”工具。记录工具不执行任意 SQL，不修改 Task/Run 状态，也不为记录动作调用模型。

写工具只面向主 Agent。Worker 有建议时使用现有内部消息提交，由主 Agent 决定是否记录；避免多个 Worker 竞争维护用户需求。用户通过自然对话操作，不增加专用管理页。

## 5. 让主 Agent 看得见、但不替它决定

在现有主 Agent 进入用户轮、相关内部消息轮、Worker 成果/问题处理轮以及正常恢复入口时，提供相关 open 事项的数量和有界摘要（ID、简短内容、关联任务）。

- 有明确相关任务时先展示相关项，并告知还有其他 open 项可查询；不能把未关联项永久隐藏。
- 来源及事项内容均作为数据传入，不提升为 system/developer 指令。摘要不充当授权，也不写诊断日志。
- 主 Agent 决定需要哪些完整记录，并使用 pending_list、work_inspect 等读取真实上下文。
- 摘要只帮助发现事项，不声称它已被处理。用户取消或修改后必须读最新 revision，不按旧摘要执行。
- 不为每条 open 项新增一条唤醒消息，不为“仍有待办”无限排队模型轮，也不扫描全部历史生成需求。

现有 Worker 结果通知和持久 inbox 是唤醒来源；记录数据是判断材料。若某个实际路径没有通知主 Agent，修复那个事件路径，不建设通用需求调度器。

例：Worker 报失败，主 Agent 可先读失败证据与 N1，然后选择修正、改方案、暂缓或询问。后台不会先检查 N1 的“成功门槛”，也不会因为 open 而自动派工。

## 6. 动态决定与现有执行工具的衔接

### 6.1 决策完全在模型轮中

主 Agent 阅读事实后选择行动，并给出适合的完整任务或处理说明。单纯记录、修改或查看事项，不触发实际执行。

现有任务继续规则、验收准确性、执行停止保护及权限约束保持由其 owner 校验。它们保护真实操作，不能被解释成需要再建一套“待办应该如何处理”的规则。

### 6.2 需要补齐的来源路径

当前维护源码中，service.ts 的 rootAuthority 要求当前真实用户轮；内部事件轮没有这个来源，不能直接创建根任务。task_update 又沿原任务权限，不能自动获得新附件。动态决策不能靠伪造用户轮或删除这些校验实现。

建议在现有 task_delegate 增加可选“所引用事项及修订”和“真实请求来源”参数，仍由同一个任务业务入口创建任务：
1. 主 Agent 明确选择事项、完整契约及其实际依据；默认用户轮的旧调用保持原语义。
2. 宿主重新读取所选事项及真实请求，验证归属、可见性、修订和引用关系；Actor 仍保持实际事件轮身份。
3. 由原授权 owner 构建有来源的任务上下文，保留主请求及必要补充来源。新契约只使用这些有效来源明确允许的输入；首期附件仅沿主请求精确授权，补充来源保留文本、批注及请求引用，不合并历史附件范围。需要不同附件来源时显式选择其为主来源。不开放全部历史附件、不把不同范围的授权无条件拼接。
4. 确定主请求以沿用已有正式交付路由；其他引用不自动成为新的外发目标。
5. 用户“先记下、不执行”等意图由主 Agent 负责理解和遵守；记录存在不产生授权。现有外发、费用、权限和敏感操作的检查/审批照常适用。

主 Agent 的建议若没有可引用的真实执行授权，只能保持记录或询问，不能凭自身记录创造授权。文本摘要和 handlingNote 不能替代原始请求。

首期只打通实际需要的合法来源续接，不做通用授权 DSL、语义权限分类器或新审批系统。修改现有任务的范围仍走其原本规则；需要不同授权的新工作可明确建新任务，不改写历史权限。

### 6.3 任务关联只记录事实

派工工具可以显式带多个事项引用；创建实际 Task 与写入 linkedTaskId 在同一短事务内完成，防止任务已创建而记录无法追查。事项状态保持不变，除非主 Agent 明确要求更新。

这不是“自动消费待办”：没有显式派工调用就没有创建；没有检查前轮成功、交付收据或版本释放关系。关联的作用是查证该次操作产生了哪个实际任务。

带事项引用的任务创建会同时更新关联及 revision；重试先查询原 operationId，竞争旧修订返回冲突。主 Agent 若明确需要再次安排，读取当前记录、已有任务和回执后，可用新操作继续，无需为再次交办伪造内容修改或关闭/重开事项。这里的修订检查只防并发覆盖，不限制主 Agent 合理安排新任务。

多条事项可关联一个 Task。复杂执行拆分继续用现有任务树，记录模块不建设拆分/合并工作流。Task 的运行及成果状态仍只从 Task/Run/Result 查询。

## 7. 可靠性实现边界

| 问题 | 最小处理 |
| --- | --- |
| 保存/更新回执丢失 | 沿既有 operations 保存操作身份与结果；相同 operationId 和载荷返回原回执，载荷冲突拒绝 |
| 并发修改 | 更新使用 expectedRevision；冲突重读，不覆盖用户新决定 |
| 交办后中断 | 任务创建、事项关联和操作回执同一事务；恢复后查原操作，不重新派发 |
| 派工已提交但引擎未启动 | 沿现有持久任务队列启动与恢复，不在记录模块新建执行循环 |
| 数据库写入失败 | 返回明确失败；主 Agent 不说“已保存/已安排” |
| 暂缓或取消 | 主 Agent 显式更新 state/handlingNote；不硬删除原始来源或代替停止工具 |
| Worker 后来失败 | 保留真实关联；交给主 Agent重新判断，不自动清除关联、重开或重派 |
| 记录内容变化 | 新 revision 和真实修改来源；不改已运行任务的契约或授权 |

沿现有 Store.transaction 和操作回执语义实现短同步事务。模型判断、远程调用和引擎启动都在事务外；不能外层开事务再调用会 BEGIN 的公共方法。

建议记录访问代码保持一个小模块，在现有事务 owner 内提供内部读写，供记录工具与任务创建组合使用；不为复用复制一套 operations、不把递归任务模块包成通用工作流框架。创建前先重读本次来源和事项修订，创建后再进入现有调度。

operationId/载荷校验、修订号与输入校验是客观一致性保护，属于应保留的代码；它们不决定主 Agent 的工作策略。限于本地数据库事实，不能宣称事务能撤回外发或任意 Shell 副作用。

## 8. 模块与改动位置

| 位置 | 预计变化 | 不做的事 |
| --- | --- | --- |
| store.ts 的 schema owner | 最小新表、版本声明与必要索引 | 在任意工具构造器中偷偷 DDL |
| 小型 pending-items 模块 | 查询、更新、修订与现有事务内关联 | 执行队列、业务判断或第二套任务状态 |
| pending-tools 定义及既有主 MCP 接线 | 三个工具、真实调用者/来源绑定 | 新服务、新 Worker 管理工具或修改原五项 MAIN_TOOLS 指纹 |
| recursive-tools / recursive-tasks | 显式来源引用及事务内关联的最小扩展 | 自动派工、改变原无参数调用的语义 |
| service.ts | 相关模型轮摘要及原授权路径的合法续接 | 基于成功/失败自动选下一步 |
| prompts/main.md | 工作原则、读取与回执习惯、动态判断责任 | 固定状态转换和强制处理模板 |
| 现有 schema/工具兼容检查与聚焦测试 | 登记 owner/契约变更、数据保持及行为验证 | 顺带重构其他模块 |

上述是职责划分，不要求机械新建同名文件。若现有相邻模块已能清楚容纳，优先少改文件；不引入额外 npm 依赖。

## 9. 数据迁移与采用

使用届时实际在用的 schema owner 和版本体系。拟新增表及功能版本声明，但本方案不预占 recursiveSchemaVersion 编号，不混入正在进行的执行架构迁移。

- 在隔离数据库副本做增量迁移，保持既有用户、对话、任务、记忆、附件、消息和未知发送事实。
- schemaHash/pinned metadata 必须覆盖新 owner 与版本；仅新增 meta 字段不能证明旧构建兼容。
- 不自动从历史聊天提取全部待处理项，避免重复、误读和未经确认的旧授权复用。
- 后续上线沿现有真实审阅、维护点及安全采用规则；有新业务事实后不恢复旧数据库覆盖它们。
- 本次方案编写不执行迁移、重启、部署或写运行数据。

## 10. 验证设计

| 对应需求 | 最小验证 |
| --- | --- |
| R1 / AC01 | 只保存事项时派工/steer计数不增加；同操作重试只有一条记录 |
| R2 / AC02 | 重新打开隔离SQLite后仍可查；模拟摘要丢失后按ID/关联恢复；未关联项可发现且大列表可分页 |
| R3 / AC04 | 修改、暂缓、关闭及重开由明确工具调用产生；任务状态不被记录状态改写 |
| R4 / AC03 | 相同失败事实下，分别由可控Agent选择修正、暂缓或结束，服务忠实执行合法选择而无预设分支 |
| R5 / AC05 | 事件轮基于真实已存来源可合法交办；伪造请求、跨范围输入和新外发目标被拒；没有事项引用的旧调用保持原保护 |
| R6 / AC06 | 并发CAS、派工事务中断、重复引用、丢回执均不产生重复任务或孤立关联；来源变动按最新修订重核 |
| R6 / AC07 | 迁移副本前后原业务行保持；已有queue、验收、停止、publication及schema检查回归 |
| AC08 | 获准真实主对话中，主Agent确实保存、查询并结合Worker结果作有依据的安排；证据与合成测试分开 |

行为变化优先用稳定契约做红绿测试；无需为每个字段写镜像断言。新增共享工具/来源/事务路径后，完成相关集成测试及项目要求的完整检查。仅文档整理不运行会写产物或调用生产的测试。

主 Agent 的策略不要求唯一答案，但动作必须与当前真实用户要求、事实及授权一致。可以检验“先记下”的需求没有执行；不能要求所有失败都选返工或所有成功都启动下一轮。

## 11. 简洁性与扩展性复核

- **简洁**：一张记录表，三个记录工具；任务、消息、执行和审批复用现有机制。
- **清晰**：记录只表达内容、来源、关联和关注状态；工作判断留给主 Agent。
- **可靠**：保存回执、CAS、幂等和事务关联；上下文恢复时重新读取。
- **可扩展**：稳定ID和来源可供以后明确需要的查询或界面使用；新的处理方式先由Agent工作方法表达，不必不断增加状态/分支。
- **克制**：没有现时需要就不加新字段、新状态、新服务或调度。以后出现真实一项对应多任务的独立查询需求，再用明确迁移演进，不提前造通用关系模型。

## 12. 实际实现与验证边界（2026-10-19）

候选代码所有者：
- `src/pending-items.ts`：表/版本、用户来源核验、查询、CAS、有界摘要及事务内关联。没有调度器或 Task 结果监听。
- `src/pending-tools.ts`：三个严格输入校验的主 Agent 工具；`worker-interaction-mcp.ts` 仅向主目录登记，原五项 MAIN_TOOLS 不变。
- `recursive-tasks.ts`：继续拥有 operations 和短事务。`createPendingRoot` 在回执查找后核验选择与来源，创建 Task、关联多个事项及保存回执；不嵌套 BEGIN、不改关注状态。旧 createRoot guard 保留。
- `recursive-tools.ts`：task_delegate 可选 `pending={items:[{id,expectedRevision}],sourceRequestIds,primarySourceRequestId}`；仅支持根派工，子任务仍沿原任务树。其他输入不变。
