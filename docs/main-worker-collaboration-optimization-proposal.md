# Homer 协作优化评审稿

2026-11-24 · 第 25 版评审稿。现行设计及实际验收范围见[主 Agent 与 Worker 会话架构](architecture/main-worker-chat-architecture.md)和[架构索引](architecture/README.md#协作优化与数据库升级)。

Homer 根据用户原话和工作事实决定改稿、联系谁、怎样续办。宿主核验调用身份、目标记录、执行状态和实际操作回执。沿用现有事项、版本、Worker 会话、Run、消息与操作记录。

**移除宿主业务权限机制。** 当前「原授权」是 `task_versions.authorityJson` 里的主请求 ID、可选补充请求 ID 和描述。宿主从用户轮或已关联的后台事件取得它，首派时写入事项版本，Run 记录主来源 ID。宿主用这些字段核对来源及其与事项、Run 的关系，拦截编辑、派工、领取等操作。定时和交互记录也复用这套来源校验。方案移除这类业务权限、首派绑定和重新绑定，Homer 根据用户原话及实际记录作判断。直接删除要求用户请求 ID、真实用户当轮、旧委托或来源匹配的业务门槛。请求 ID 和触发记录有则用于展示与追溯，缺失时兼容空值。复用已有目标、状态、路由和回执，不增加替代实体或触发证据校验。系统沙箱、平台访问、消息归属、执行状态和回执属于各自的边界。 [授权字段与校验](../src/recursive-tasks.ts#L118) · [首派写入](../src/recursive-tasks.ts#L393) · [来源选择](../src/service.ts#L3362)

## 1. Worker 工作标题与工作记录

**现状与目标。** 事项标题描述共同目标，Run 记录一次执行。目前缺少 Worker 分工标题。首次派工可写简短的 `workTitle`，例如「核对来源」。确认原轮已结束后，Homer 可用 `worker_message` 明确派下一阶段，例如「复测归档」。补资料、追问、重试和单独改目标均沿用原分工。执行结果未确认时沿用已有投递状态。

**实现。** 在两种派工工具的现有 MCP 参数与 `worker_input` 正文载荷中加可选 `workTitle`。以首次受理该分工的输入 ID 为起点，按同一 Worker 已受理输入的顺序和 Run 关联读取。无标题的追问、重试和确认未启动后的替换沿用上一分工，只有受理新分工才写标题。按受理顺序投影到 `work_inspect(taskId)` 和桌面、移动端事项详情，原文继续用 `worker_read`。每个 Worker 最多一项当前分工，空闲时可显示上次分工，历史可回看。状态来自原执行事实。旧输入缺标题时照常显示历史，首版只覆盖已派工的分工。 [派工与读取](../src/recursive-tasks.ts) · [现有工具目录升级](architecture/host-tool-upgrades.md)

## 2. `task_update` 可在后台修改目标

**现状与目标。** 普通目标修改也走 `bindRequirements`，要求当前轮存在真实 `sourceRequestId`。后台收到 Worker 证据或定时事件时，Homer 应能编辑可见事项的目标，包括暂停中的事项。仅编辑笔记已有独立路径。

**实现。** 沿用版本写入事务、修订和幂等校验。用户轮和后台轮均可编辑目标。新版本沿用工作目录，`triggerOpId` 指向本次编辑，操作记录保留真实输入、线程和轮次。仅改笔记时递增修订。 [工具入口](../src/recursive-tools.ts) · [版本写入](../src/recursive-tasks.ts)

**旧业务问题。** 普通目标改版时，去掉 `cancelQuestions` 对这次编辑的取消动作，以及 `questionCurrent` 中要求问题版本等于事项当前版本的条件。已接收且尚未处理的问题保留原文、已有答复和入箱顺序，由 Homer 结合上下文决定回答、澄清或忽略。答复接收按主会话、原业务问题和已关联的真实答复核验，可无祖先用户请求 ID，归档期间也可把用户答复按原身份落账。暂停或归档时返回已保存、待投递，主轮正常结清并暂缓实际回投，恢复并解除暂停后按原问题、Worker 和回执续投。仍在原轮则只投该轮，原轮已确认结束时可沿同一 Worker 的原线程续办。新接单版本与旧问题版本不同本身不使答复失效。已有投递回执优先对账。待答列表、通知、详情、接收与应答均按原问题、Run 和主会话读取，移除必须由本轮持有原问题或答复的门槛。暂停和普通续谈保留旧问题。原轮退出后的续投走同一 Worker 原线程，仅在可安全接续时办理，另一个正在运行的轮次不接收旧轮 steer。 [改版与问题有效性](../src/recursive-tasks.ts#L306) · [业务答复投递](../src/service.ts#L3024)

**定时安排。** 修改定时任务内容直接调用 `schedule_update` 更新正文，省略 `taskId` 时沿用原交付目标。移除 `scheduledResultTask` 发布前要求事项当前版本等于绑定版本的条件，沿原订阅和发件箱交付。用户要求变更交付目标时，更新订阅去向。 [更新正文与保留绑定](../src/schedule-tools.ts#L66) · [定时结果发布](../src/service.ts#L2593)

## 3. `pause` 保留，`resume` 只解除暂停

**现状。** 当前 `controlTask(resume)` 要求较新的真实用户来源，检查旧 Run 退出和未决交互、操作，再生成新目标版本并重绑委托。本方案将 `resume` 定义为事项状态操作。

**实现。** `pause` 继续阻止暂停期间的新派工和队列领取。Homer 需要停止具体执行时，逐个调用 `worker_interrupt` 并按原回执确认。任一有效 Main 轮均可对可见的暂停事项调用 `resume`。走现有事务与回执，仅将状态置回 `open` 并更新修订。去除 `rootAuthority`、强制新用户来源和汇总未决检查。改目标走普通 `task_update`，同步移除工具层 `resume` 可带 `goal` 的特例。旧版记录的来源、Run、审批和回执按原样保留。

用户叫停时，Homer 按用户指定的范围停止相关工作。之后由 Homer 根据用户原话、后续证据，自主判断恢复时点和续办方式。若本次指示明确给了停止期限或恢复条件，就按该指示办理。Homer 用 `work_inspect`、`worker_read`、现有交互与操作回执核对事实。旧 Worker 的退出、未决审批和未知副作用按原记录核对，续办动作仍受相应门禁约束。归档可见性继续由原入口处理。历史 Run 和回报沿原版本核对。 [控制、调度与退出](../src/recursive-tasks.ts) · [唤醒与执行守卫](../src/service.ts)

事项解除暂停后，原调度器按接单版本自动领取已保留、仍有效的排队 Run。Homer 判断某轮已不适用时，可在恢复前用现有的 `worker_interrupt` 处理该轮并核对回执。沿用原队列和领取条件。历史样本不足以估算排队工作恢复时已不适用的比例。 [现有队列领取入口](../src/recursive-tasks.ts#L519) · [暂停队列测试](../tests/recursive-terminal-queue.test.ts#L80)

## 4. `worker_message` 可跨事项联系已有 Worker

**现状与目标。** 后台 A 事项回报触发的普通消息在 `dispatchAuthority` 被目标 B 的事项来源匹配拦下。Homer 应能在该轮联系 B 中已有的 Worker，消息、执行和回报归 B。

**实现。** 在 `workerMessage` 和 `workerMessageRecovery` 移除事项来源和委托校验，沿目标事项状态及实际运行记录路由。提问答复用原问题和回投记录，定时用原触发和交付记录。宿主按现有身份与状态路由，活动轮只 steer 原 Run、epoch、线程和轮次，按该 Run 的版本登记。确认退出且可续办时，在原线程、原 Worker 目录排入新版目标下的 followup。沿用首次未创建进程的已确认失败重启分支。投递竞态和未知 ACK 查原回执，保留实际投递目的地。附件按原转交入口逐项核验。 [消息路由与恢复](../src/recursive-tasks.ts) · [交互和宿主投递](../src/service.ts)

## 5. `worker_open` 可为其他事项增派

**现状与目标。** 当前首派需要绑定委托，后台 A 事项回报触发的增派还会遇到目标 B 的来源限制。Homer 可直接选择可执行的 B，按当前目标和工作目录新开 Worker。

**实现。** 移除 `workerOpen` 的首次委托绑定及来源匹配。复用现有事务创建归 B 的 `worker_input`、Worker、Run 和受理回执，操作记录保留 A 的触发事件。 [新开 Worker 与首派绑定](../src/recursive-tasks.ts)

在 `task_update` 的工具描述中说明，`notes` 用于后续轮次仍需参考的结论或约束。跨事项协调时，Homer 自主判断是否更新目标事项 B 的笔记。提交 `notes` 会整段替换，先读取原笔记并把仍适用的内容一并写回。普通派工可查原消息、Run 和操作回执，按需补记即可。此说明只放在工具描述中。 [现有工具描述](../src/recursive-tools.ts#L22) · [笔记写入](../src/recursive-tasks.ts#L326)

## 6. Homer 可读取同主会话聊天原文及附件

**现状与目标。** `readUserMessage` 和 Main 的 `authorizeAttachment` 都会按当前后台事项或触发来源筛选。Homer 在有效 Main 轮可读同一主会话中用户可见的正文及附件，由模型判断与当前工作的关系和用途。

**实现。** `work_inspect(messageId)` 读取正文与附件引用，继续校验准确消息 ID、同主会话及用户可见状态。读取图片、文档提取文本或语音转写仍调用现有 `inspect_attachment(assetId, revision)`。Main 的这两个读取入口去掉后台事项和来源匹配，附件按准确资产 ID、版本及其归属的用户可见消息查找。保留当前用户输入的读取能力及消息撤销、取消、草稿、内部消息边界。复用现有消息与附件关系。Worker 读取、导出、转交和外送继续走各自入口。 `work_inspect(taskId, sourceRequestId)` 继续查事项来源，`worker_read` 继续查 Worker 会话。 [正文读取](../src/service.ts#L2355) · [附件查找](../src/service.ts#L398) · [附件提取](../src/service.ts#L646)

## 7. 归档和恢复可见性由 Homer 判断

**现状。** 据本事项记录，17 项跨事项后台归档被 `history_source_required` 拒绝。当前后台归档只接受目标事项自己的合格 Worker 回报，`restore_work` 则走真实用户轮。归档还会检查运行、待答、未处理消息及未确认操作。提交归档会取消未送达的业务问题，把事项置为已归档、暂停并发出 `task_archived`。恢复只改回可见。 [归档来源及状态](../src/recursive-tasks.ts#L738) · [归档与恢复入口](../src/recursive-tasks.ts#L807)

**方案。** Homer 根据用户意图和现有记录自主决定归档或恢复可见性。两种操作均可在 Main 后台轮执行。移除来源限制和归档前对运行、待答、未决操作等的阻断及延迟提交，复用事项状态写入、修订校验和幂等回执。运行与退出、待答、消息及未知操作的事实继续可查，归档时保留这些记录，包括未送达的业务问题。

归档沿用「已归档、暂停」状态，暂停挡住新派工和队列领取。已在途的 Worker 终态、消息投递、回执及待处理答复照原记录落账，保留原顺序，恢复后按原事实处理。按现有回执区分未送出、已送出待确认、已确认。归档挡住新的发送，已经送出的 steer 即使在归档后才收到 ACK，也按原 Run、epoch、线程和轮次登记。已领取但尚未发出原生启动的 Run，结清为可核对的未启动并释放已有占用。已发启动而尚未确认时按原轮次对账。运行中的原生响应及附件读按其既有操作事实处理。归档后的正式正文、附件和通知沿已验证回报及接单版本提交，移除当前可见性和当前版本匹配门槛。需要停止正在运行的 Worker 时，Homer 用 `worker_interrupt` 并查回执。 `restore_work` 只恢复可见性，`resume` 才解除暂停并允许仍有效的队列继续。实际首次归档沿原事务发一次 `task_archived`，复核以当前归档动作的通知及已提交回执为依据。用现有操作记录核对最近一次已提交的归档或恢复，恢复后或再次归档后，旧通知不能触发当前清理。归档只改变事项状态并触发复核，清理由 Homer 根据资源是否在用、保留价值和用户授权另行判断。事项清单先提交归档和通知，复核暂不可用时按原状态说明。所有归档通知均核对当前归档动作，复核 Skill 改沿通知和操作读原文。运行、待答和未知操作继续可查。归档复核与原生审批按下表接线。 [归档复核](../src/recursive-tasks.ts#L189) · [归档复核与清理约定](../.codex/skills/homer-archive-review/SKILL.md)

## 版本与验收

事项当前目标和 Run 接单版本分别读取。编辑目标或解除暂停后，已受理、运行中的 Worker 仍按原 Run 的 `version` 和实际输入工作。确认活跃轮收到补充时，从该条 `worker_input`、投递回执与目标 Run/epoch/turn 核对，原回报与迟到回报仍按原版本归档。新版目标由之后受理的新 Run 使用。独立记录当前任务要求版本与仍在执行的轮次接收版本，只有宿主 Run 或回执能证实实际接收。
