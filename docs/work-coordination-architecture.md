# Homer 工作架构收敛方案

本文保留 2026-11-04 基于 `966f0c7` 的故障复现、恢复依据及当时的提案。2026-11-05 用户决定直接替换旧协作架构，不再保留本文的旧合同、候选验收、Matter 映射和迁移兼容设计。执行归属、未知外发与恢复证据仍供参考，最新方案和实施进度见[主 Agent 与 Worker 会话架构](architecture/main-worker-chat-architecture.md)。

## 1. 从一件事的始末决定架构

用户关心的是“我交办的事做到哪了、还能不能继续、最后交给了我什么”。这三个问题有时有不同的答案。例如，Worker 已退出，文件已生成，主 Agent 还没验收。此时重开应用，正确的下一步是审阅文件。重跑 Worker 会浪费工作，宣称已经交付也会误导用户。

**建议保留一个主 Agent、一层业务 Worker、一条主输入队列。** 一件需要跟踪的事沿用一个 Task。Worker 是某次执行的承担者，可以更换。主 Agent 决定下一步做什么，宿主判断上一次执行是否已经收住、某个动作是否已经发生。这样，换 Worker 是同一件事的正常延续，用户不用了解恢复协议。

从入口到交付只经过以下职责。它们都已有对应实现。

| 环节 | 谁做决定 | 写下的事实 |
| --- | --- | --- |
| 接到用户消息 | Web、CLI 或已绑定的 IM 验证来源，现有主队列按可领取顺序交给主 Agent | 原请求、来源、顺序、领取回执。普通问答直接回复，不产生任务 |
| 承接工作 | 主 Agent 判断何时派工、拆分、等待，何时直接回答。独立长工作交给 Worker | 需要持续跟踪时才保留目标、输入、验收条件和原授权。后续补充可以归入原事 |
| 执行 | 宿主领取一次 Run，绑定执行身份。Worker 自主完成本次授权范围内的工作 | 运行身份、实际输出、文件引用、真实退出证据。Worker 内部原生子 Agent 由引擎管理 |
| 验收 | 宿主把候选和通知一起提交。主 Agent 判断是否达标、是否返工、哪些缺口要说明 | 对准确版本、候选及所需子成果的业务决定。证据不足可以明确保留待审 |
| 交付 | 主 Agent 选择对用户有用的正文与文件，宿主按原可信来源交给渠道 | 宿主记录交付准备与本地收录，渠道记录实际发送回执。界面分别展示有证据的结果 |

适用范围是桌面、CLI、Web、移动 WebView 和 IM 共用的工作生命周期。桌面负责运行实例归属，渠道负责身份和发送，引擎负责原生会话和审批。账号、计费、设备配对和升级分发继续经各自已有接口提供约束。产品已有的单主对话、授权域内统一排队、动态协调与一级 Worker 是本方案的前提。[主 Agent 工作原则](34-main-agent-work-cycle-requirements.md) · [一级 Worker 架构](12-recursive-agent-architecture.md) · [统一队列合同](2026-10-23-worker-return-main-queue-plan.md)

## 2. 现行设计如何在真实工作中失效

| 可观察的情况 | 当前代码路径与后果 |
| --- | --- |
| 重启后有 Task 处于 `recovery`，Run 是 `interrupted / uncertain`、错误为 `restart_unconfirmed`，没有该 Run 的 lease | 普通启动的 `RecursiveTasks.reconcile()` 只枚举 queued、running、awaiting_review。上述组合进不了这段对账。对终态 Run，`Homer.stop()` 只有在仍有进程槽位或 lease 时才可能回填关闭事实。隔离复现经过两条入口，随后 `task_continue` 仍返回 `run_stop_unconfirmed`。现场记录足以确认阻塞条件，无法据此还原旧进程的实际结局 |
| 同一桌面启动动作有另一条路径 | 桌面采用既有资料时，构造函数可因旧运行、未完成交付或不明归属在启动前退出。允许启动时，`pauseOldDesktopWork` 又跳过普通任务对账。一次普通用户接待成功后，会清空桌面层的历史暂停集合并放开旧 Worker 消息。一次询问因此可能改变无关旧工作的可调度范围，具体是否执行仍取决于任务本身 |
| 退出应用会影响业务结果 | `Homer.close()` 对 queued、running、awaiting_review 等调用 `stop(runId, "shutdown")`。对未结算任务，这会走业务停止流程。内存库复现中，有候选的 Run 从 awaiting_review 变为 cancelled，Task 的 outcome 变为 cancelled，候选从 offered 变为 invalid。用户可能只是想关掉应用，已有工作却失去了正常验收入口 |
| 消息是否“处理过”和成果是否真正处置可以相反 | 主 Agent 提前 `inbox_ack`，在审阅前失败，回执可已 processed，候选仍待审。反过来，主 Agent 已验收且交付已 prepared，却漏掉 ACK，`processWorkerInput()` 的收尾仍可把回执置为 blocked。第一种会漏办，第二种会让后续接待重复核对 |
| 无关的新问题要替旧回执收尾 | `mainTurn()` 可在处理新请求时逐条追加历史 uncertain 回执的模型轮次，候选筛选还依赖公开处理段的 worked 标记。隔离桌面夹具里，一条明确要求只回答新问题的消息跑了两轮，旧回执未确认使本次接待报告失败。另有既有测试在主动要求核对 81 条历史时断言 82 轮。这是协议调用数，不是线上耗时统计 |

同一个“执行结束了吗”也有多套判法。Worker 的一条正常收尾路径先删除 lease，再另行提交 `endSegment()`，两次写入之间存在崩溃窗口。`reviewExitConfirmed` 只看槽位和 lease，普通启动又可把 awaiting_review 下的 uncertain 改为 ended。相反，历史操作的 `historyBlockers()` 还会因过去的 `restart_unconfirmed` 拒绝把运行视为已关闭。各入口对同一次关闭可以给出不同答案。现有现场记录足以定位阻塞条件，具体在哪一步丢失了证据仍无法还原。

进程退出、用户放弃目标、主 Agent 读过消息、成果获准、渠道送达可以独立发生。把它们混在一起，有时会替用户取消已有工作，有时又会让一个缺失的回执挡住新请求。直接放宽停止检查可能让两个执行者同时改同一工作区或重复发送。主提示词禁止靠另建任务绕过停止、终态或预算限制，应保留这条约束。[宿主运行与关机](../src/service.ts) · [任务状态与写入](../src/recursive-tasks.ts) · [主队列与历史筛选](../src/recursive-main-inputs.ts) · [历史核对的调用次数断言](../tests/main-history-recovery.test.ts) · [当前主 Agent 指令](../prompts/main.md)

## 3. 保留哪些概念，哪些应该退出日常调度

取舍标准是能否独立变化、能否举出必须单独留证的场景。表格区分产品概念和存储兼容。去掉一项调度职责，不要求同步删除承载历史引用的表。

| 现有概念 | 目标归属和取舍 |
| --- | --- |
| 用户请求、会话、消息领取 | 保留。来源决定授权和回复路径，消息与领取回执决定队列顺序及当前处理者。一条原消息沿用一个身份。同一主授权域中的用户输入与 Worker 业务回传沿用统一队列，保留允许的用户重排与领取后的锁定 |
| Matter、根 Task、子 Task | 根 Task 负责整件事，目标从当前 TaskVersion 读取，结论连到实际验收记录。Matter 降为旧 ID、材料目录、标题和发现入口的兼容映射，展示状态从根 Task 读取。只有需要独立调度、独立验收或确有并行责任时才建子 Task。一个步骤、一次返工或一次工具调用均不单独建 Task |
| TaskVersion、revision、Run、epoch | 目标、输入、验收条件或执行范围发生实质变化才产生新合同版本。revision 用于拒绝过时写入。Run 记录某版目标的一次尝试，epoch 用于挡住旧执行者的回调。目标未变且前次尚未验收时可以换 Run。已有验收或交付的版本保留原结论，新修订另立版本 |
| Worker、协调者、原生 thread/turn | Worker 随 Run 启停，业务层继续用现有任务地址路由。固定主协调者由上下文提供。保留真实的暂停、接管责任和父级约束。原生会话标识留给引擎绑定、诊断和隔离，用户只需看到由谁处理及工作进展 |
| Result、文件、Delivery | 三者保留。Result 记录具体候选和审阅决定，实际文件的路径、字节及摘要可校验，Delivery 记录某根任务版本向哪个原来源发布了哪些内容。一组五个文件可能只发布两个，发布准备后也可能遭遇渠道断线。合并会丢掉这两种事实 |
| 操作回执、lease、原生审批 | 保留在能核实事实的一侧。原操作标识及载荷约束用来识别重复请求，lease 用来定位拥有的进程，审批绑定原请求与回调。读到旧许可、旧 PID 或旧工具调用都不能据此生成一次新的批准 |
| 待办、依赖、等待 | 用户明确留下的后续需求才成为待办。确有前置成果、原生交互或需要唤醒的等待时才保留相应记录，引用具体任务版本。普通进度和历史异常留在原工作上。子成果应被采用、暂留或列为缺口，由主 Agent 决定 |
| 处理段、任务总览、归档 | 处理段负责重现当时对话，总览负责显示当前事实，归档负责可见性。三者均可引用历史事实。移除根据界面 worked/working 决定业务事件能否恢复的依赖。归档所允许的清理范围和用户要求保留的服务继续按既有约定处理 |

现有数据库已有“一事项一个根”“一任务一个活跃 Run”“每版至多一个已验收主结果”“每根版本一条正式交付”等约束。活跃 Run 的唯一索引**不覆盖**已经 interrupted 但仍可能有写入者的情况。安全换人仍须由任务写入事务检查原 Run 的关闭证据、未决操作和版本。实施起点采用现有 SQLite、事务和原 ID，无需再造 Worker 表、恢复任务、审批代理或通用工作流引擎。[现有索引和实体](../src/recursive-tasks.ts) · [先前协作接口精简的兼容边界](collaboration-identity-simplification.md) · [归档与环境收尾](task-archive-housekeeping.md)

## 4. 重启、换 Worker 与用户取消

**建议把“重试”定义为继续履行原目标。** 主 Agent 看到用户说“继续排查”，引用原 Task。宿主先查该 Task 的候选、当前 Run、未完成操作及授权，再处理本次请求。已有成果先审。确需执行且条件成立才创建替代 Run，写入 `replacesRunId`，沿用原版本、工作目录、输入和授权，也继承已用预算。判定和创建在同一事务中检查当前 revision。并发的两次继续至多创建一个替代 Run，迟到的旧回调不能改动它。当前会话收到可恢复失败的回传时，原授权仍有效、仍有预算且确有可推进的步骤，主 Agent 就可以照此换人，无需等用户再说一遍“重跑”。同一阻塞没有新证据时，保留原因并告知影响。

| 宿主能核实的情况 | 下一步及用户体验 |
| --- | --- |
| 任务从未提交给引擎，或者同一宿主仍持有安全暂停的活 Run | 有持久证据证明未提交时，重新领取原排队项。仍持有原执行者时，可恢复原 Run。重启后的新进程不能复用旧内存回调 |
| 原运行确已退出，已有有效候选 | 领取原回传或对原结果补齐审阅，展示具体候选和已有文件。等待审阅期间关机，再次进入仍然可以审 |
| 原运行确已退出，目标未完成，允许的下一步没有未决冲突 | 主 Agent 可在同一 Task 派新 Worker。保留原尝试、已验证的发现和剩余工作。用户只交办一次，换人本身不需要重新审批 |
| 找不到槽位或 lease，且没有足够证据证明旧执行者已失去相关写入能力 | 记录原 Run 的不确定性。用户请求继续时由宿主定向核实原归属、代次和实际退出记录。能强制隔离的只读核查可在原授权内先做，写入、重复发送等冲突动作继续受限。向用户说明缺的是哪项证据、可核查什么、哪些工作还能做 |
| 确认进程结束，但上次写文件、外部提交或发送结果未知 | 优先核对实际文件及摘要、原提交标识或渠道回执。能按原幂等标识查询就查，无法确认则保留这项效果为未知。回读证据只解决它能证明的问题，例如文件存在无法证明消息已发出 |
| 用户主动取消任务，或只是退出应用／升级 | 取消按用户选择的范围处置目标及子工作。退出应用只关闭本宿主持有的执行者，记录执行中断，保留目标、有效候选、待审和交付记录。再次打开时先核对事实，启动业务工作仍遵守原授权和队列 |
| 用户明确要求重做已取消或已正式交付的工作 | 这条新请求提供本次工作的来源。在原目标上建立新版本并保留原结论、旧文件和交付历史。若用户给的是独立目标，才创建新的 Task。重做仍要核实前次可能产生冲突的外部动作 |
| 新消息与被阻塞工作无关 | 宿主可用且权限独立时，新问题按自己的队列位置正常处理。一次普通接待不解锁整批历史。桌面资料仍有不明全局写入者时，继续遵守实例独占保护，不能另起第二个宿主写同一数据库 |

**关闭证据必须绑定原执行者。** 同一宿主可记录对应 Run、epoch、原生会话及所管理执行范围的真实关闭回执。重启后的核查还可使用带进程身份的持久 lease、平台实际可验证的进程树、已有候选中可信的退出证据。写入方先挡住过期回调，实际确认关闭后，在同一 SQLite 事务里把关闭证据写回对应 Run 并释放对应 lease。历史错误码和候选创建时的退出快照保留当时含义，后续继续、验收、归档和升级检查均读取同一个当前关闭事实，各自再检查所需的其他条件。引擎轮次返回、PID 消失、空 lease、等待超时各自只证明一部分。原生工具另起的进程或外部系统已经接收的操作，要按其自身证据核实。若当前存储确实缺少能跨重启保存的一项关键证据，优先补在原 Run 或原操作记录里，说明写入者和失效条件。

桌面采用与普通服务共用同一个判定。前者先过实例锁和资料归属检查，允许接管后才可写入已核实的事实。机械核对可以在启动时处理已识别记录，也可以在用户点名旧任务时定向进行。启动或回答新问题本身不代表用户授权恢复历史执行。旧版仅有 `uncertain`、无法证明归属的记录允许保留未知，并给出对应的核对路径。旧版已经取消的任务也要保留历史，不能仅凭 `shutdown` 字样批量复活。[桌面启动选择](../scripts/desktop-runtime.mjs) · [实例归属](../scripts/desktop-profile.mjs) · [进程身份与终止](../src/processes.ts)

以截图中的 Android 图标排查为例，若旧 Worker 留下了 Expo 配置线索，新 Worker 应从核实该线索及实际 Android 资源开始，沿用同一任务，把结论交回主 Agent。只有线索时不能当作已验证结论。只读检查若能被权限层隔离，可先推进这一部分。若旧执行者可能还在改同一目录且无法隔离，应先核实它或取得可信快照，避免两边改同一份文件。

## 5. 谁来收尾一条消息

主 Agent 值得花一轮推理的事情，是判断成果是否可信、缺口是否需要返工、用户此时需要听到什么。把“请再调一个工具证明你处理过消息”从正常路径拿掉。收件、业务处置、对外发布分别使用原有记录，各自有可验证的完成条件。

| 原输入 | 宿主可以凭什么收尾 | 中途退出时如何处理 |
| --- | --- | --- |
| 用户问题或指令 | 原请求的接待轮、真实终态和对应回复。派工成功另有原操作回执 | 只影响该请求的答复。若已经派工，按原操作查出 Task，继续说明进度 |
| 可验收的 Worker 候选 | 该消息所指 task/version/run/result 的审阅、返工、终止，或明确保存的暂缓理由。验收保留原有实际内容及必需标准的检查 | 审阅事务已提交就补齐原回执。若未作处置，即便模型提前 ACK，候选仍可在原任务和原队列机制中被找到，不能静默漏办 |
| 进展、结束、归档等通知 | 只需知悉的通知在对应协调轮真正处理后收尾。已有宿主观测到的进度可直接供显示。若事实需要主 Agent 取舍，原消息继续排队 | 普通进展无需额外制造用户回复。失败、部分可用或重要阻塞要记录本轮已说明的内容或仍待说明的缺口 |
| 原生提问或审批 | 原交互的接收者、真实决策及引擎回执 | 原回调不可达时如实结束该交互。再次执行如需权限，沿新执行的真实请求重新取得 |
| 已准备对外发布 | `prepared` 表示正文、选定文件和路由已入库。`recorded` 表示宿主交付事件已被接收端收录。IM 服务是否收到，要看原渠道发件记录 | 提交前退出，按原交付记录处理。可能已经发出时依原发送标识查证，缺少查证能力就保留未知。用户可先在本地看到已有验收结果 |

这些规则落在既有写入点。领取时锁定消息、接收者和本轮身份，业务事务知道正在处理哪一条消息。能同库提交的动作与原消息收尾同事务提交。验收与交付之间仍允许应用退出，重新打开只补缺少的下一步。对宿主能控制的派工与发送，先将原操作和执行意图落库，再调用，取得真实回执后提交结果。Worker 通过原生工具直接作出的外部变更，可能没有 Homer 的操作记录，须回到文件或目标系统查证。外部系统不支持幂等或查证时，保持原发送结果未知。

历史校正以原消息和准确的业务引用为范围。对已 processed 但候选仍待审，或已 blocked 但原动作已提交的记录，先匹配原操作、版本和结果，能证明时才校正原回执。需要重新处理时沿用原消息身份，保留原顺序和领取版本校验。定向查看历史不抢领队列后面的消息。缺少执行条件的记录留在对应任务上，不占据主队列的可领取位置。显式暂缓保留理由和原任务入口，等相关证据、用户指令或前置条件改变后再评估，避免同一个缺口反复触发模型。归属无法重建时，在该任务详情保留缺口。Worker 之间的消息签收、用户输入的接收确认和渠道回执仍按各自协议执行。[消息领取与排序](../src/recursive-main-inputs.ts) · [Worker 自动回传](40-worker-automatic-return.md) · [审阅与发布的现有约束](2026-11-02-review-publication-repair.md)

## 6. 给主 Agent 的接口应该长什么样

沿用现有工具名可以达到目标。主 Agent 可以用已有状态或一次定向检查回答“刚才做到哪了”。一旦需要独立调查、实现或持续验证，就派 Worker 并结束本轮接待。用户明确要求亲自处理、禁止委派或停止时，按该要求执行。模型只填写会改变意图、范围或证据的内容，固定身份和并发控制交给宿主。

| 常见意图 | 建议的调用与宿主责任 |
| --- | --- |
| “排查这个项目的图标” | 主 Agent 用 `task_delegate` 表达目标、实际工作目录、必要输入和验收标准。来源、固定协调者、初次 Run 及原生身份由宿主绑定。目标相同的已知任务优先沿用准确引用，禁止用模糊标题自动合并独立请求 |
| “接着做” | `task_continue` 面向原 Task，给出可审候选、已恢复、已建立替代 Run 或具体阻塞原因。宿主处理旧 Run，不让模型轮流试 continue、takeover、stop_replace。原已受理操作按原载荷取回执，过时或有歧义则要求重读准确版本 |
| “这个结果还差一项” | 主 Agent 核实候选后，用 `task_review(request_changes)` 说明证据、缺口和返工要求。目标与授权均未变时，复用原合同，记录旧候选的处置，再建下一次 Run。改变目录、输入、验收口径或外部动作时明确变更版本及所需授权。已验收的历史版本不可被覆盖 |
| “顺便再做一件事”或“现在就改方向” | 主 Agent 根据用户意图选记录待办、另派独立工作或变更原 Task。`task_update` 只向模型索取实际受影响的子任务、排队版本和权限决定。默认保持正在执行的约定，不能把无关待办静默取消或把旧依赖自动指向最新版 |
| “父任务停了，这个孩子继续” | 在已有授权、无祖先停止屏障时，由 `task_continue` 承载明确的解除暂停意图。先迁移 `task_takeover` 和 transfer 分支中有效的责任交接、独立处置及约束，再退役仅为固定主 Agent 指派自己的仪式性参数和调用 |
| “给我结果” | `work_inspect` 默认给当前目标、运行、候选、阻塞原因和可用证据引用，需要时读取精确文件组或分页历史。`task_review` 做语义验收，`publish_delivery` 选择正文、文件、原路由。可在同一轮完成。用户不为内部 ACK 或轮询多等一轮 |

省略字段要同时满足主体由宿主唯一确定、引用绑定本轮已读快照、数据库提交时版本仍相符。保留原操作 ID 的幂等约束、revision 的并发比较和原生 epoch 的过期写入保护。两个主端同时看到不同版本时，过时的一方必须重新读取。文件被替换、结果组变化或授权撤回，也需在真正执行或验收时重新校验。

缩减框架开销有两个具体落点。目前 Worker 启动把 `inspectTask` 的结果作为 `persistent` 带入执行，其中可含整个任务的历史结果。改为首次执行只取本次所需合同、授权内输入和检查点，续跑再附已验证发现、差异及未决事项，完整历史按引用展开。历史回执核对移出每条新用户输入的必经路径。仍需处理的 Worker 业务输入沿主队列正常排序，用户主动“把旧工作逐项核对”时才纳入所选范围。Web、移动端和 IM 复用这些事实，在现有聊天与任务详情说明“已获得什么、还缺什么、下一步能做什么”。[Worker 启动与协调入口](../src/service.ts) · [当前工具契约](../src/recursive-tools.ts) · [现有工作状态界面](../ui/DESIGN.md)

## 7. 实施顺序与退出旧逻辑的条件

每一步替换原有职责的一个写入点。始终由同一宿主写同一份数据。可以离线对比新旧判定的结果，一个记录不交给两套调度器执行。

| 顺序 | 改动归属，以及要移除的旧行为 | 完成条件 |
| --- | --- | --- |
| 1 · 先固定行为合同 | 在现有隔离 fixture 上覆盖下节的用户旅程。沿 `Homer`、`RecursiveTasks`、`MainInputs`、交付渠道和桌面启动追出所有相关读写点，标明证据来源。以合成历史快照记录现有失败和调用数 | 同一组夹具可走普通启动与桌面采用分支。能在正常入口复现卡死、关机误取消、提前／遗漏 ACK 及无关请求被拖累，测试能分清原有安全拒绝和错误拒绝 |
| 2 · 统一执行归属与关机语义 | `service.ts`、`engine.ts`、`processes.ts` 只报告确切运行事实，`recursive-tasks.ts` 在原事务内处置 Run 与 Task。退出应用改走执行中断，用户取消单独保留。合并启动、手动继续、停止后散落的关闭判定及直接改 phase/outcome 的分支 | 有证据时可在原任务换 Worker，无证据时只阻塞对应操作。关机后候选可审，旧回调无写权限。桌面已拒绝接管的资料仍受独占保护 |
| 3 · 由现有主队列完成消息收尾 | 以 `recursive-main-inputs.ts` 负责领取／归还原消息，以现有审阅和发布事务记录业务事实。`service.ts` 移除强依赖模型 ACK 的收尾、每条新输入驱动的历史模型循环，以及普通接待后全量解禁。保留原生轮次的开始、结束及归属证据，移除对界面 worked 标记的调度依赖 | 提前 ACK 不吞结果，漏 ACK 不重复动作，无关新问答独立完成。Worker 与各入口仍按同一队列排序，Web 重排、来源隔离和单主轮所有权通过竞态测试 |
| 4 · 缩减工具和运行上下文 | 先在 `recursive-tools.ts` 的 MCP 工具及主／Worker 提示词简化常用操作，把完整历史改为定向读取。保留 `tools.ts` 中旧材料工具的原生签名，以及已受理调用的原载荷与回执。逐个移走只为填固定参数或回 ACK 的正常路径 | 原材料任务、无材料派工、并行子工作、返工与发布均可走通。已持久化原生 thread 的工具签名兼容经过验证后才切换，新旧签名无法安全兼容时沿原协议继续既有会话 |
| 5 · 退出重复状态写入 | 让总览、队列摘要、对话卡片、CLI 和渠道查询同一组业务事实。去掉依赖 Matter 旧状态或界面处理段来决定业务调度的分支。旧 ID、路径、历史下载、原生会话访问仍可解析 | 同一任务从各入口读到一致的目标、尝试、候选和交付。可从事实重建展示，旧记录仍可访问。是否物理删列或删表，待全部读者退出且确有收益时单独决定 |

旧数据按能证明的事实采用。已受理的操作用原标识及原载荷查回执，缺回执的外部操作不换标识重放。已验收结果、已发布文件选择及来源保留原样。失去证据的历史记录可以带着缺口继续存在，不能靠批量更新 `phase='ended'`、清 lease、清队列、重建 thread 或重置库过关。桌面采用原资料时先在隔离副本按实际约束预演。

回退以停止新领取、确认当前写入者收住为前提。先核对旧版本能否解释新增的处置语义以及哪些外部动作已经提交。可兼容的步骤可撤回对应代码。旧版本可能把已经处理的输入重新派发时，应保留当前数据、继续只读核对并前向修正。恢复旧数据库快照会抹掉真实发送或确认记录，不能用它撤销外部世界已经发生的事。

## 8. 怎么判断这次调整值得采用

首先验用户能否继续工作，再数减少了多少额外模型轮次和重复读取。以下都是目标门槛，不能把现有夹具的通过数当成新架构已通过。

| 旅程或故障注入点 | 必须能观察到的结果 |
| --- | --- |
| 用户问一个独立问题，历史分别有 0、1、81 条不相关 uncertain 回执 | 新问题正常完成，不产生 Task。由历史核对追加的模型轮数均为 **0**。显式要求核对某一任务时只读该范围，不抢领后面的回传 |
| 用户派工，Worker 自然结束，主 Agent 验收并选两个文件交付 | 一个目标、一次执行、一个候选组、该根版本一条正式交付。Web 只公开选中的文件，IM 依原渠道能力提供通知或文件。分别断言本地收录与渠道发送结果 |
| 分别在领取前、提交给引擎后、持久化终态后、候选入队后退出 | 从各自已有事实继续。确认从未提交的项可领取，提交状态不明时先查证，已有终态只补缺失步骤，已有候选不重跑。四种情况均保留用户目标 |
| 已确认旧 Worker 退出，同时收到两次继续、一个迟到的旧回调 | 至多一次替代 Run，始终属于原 Task。合法首次继续成功，重复操作返回原回执或可读冲突，旧回调不能提交候选或覆盖新运行 |
| 旧 Run 仍有 owner、PID 被复用、关闭证据缺失，或进程已退出但外部动作未知 | 各自指出具体缺口，不终止无关进程，不重复有风险的操作。可强制隔离的只读工作按其授权推进。实际效果后来查明时可沿原任务继续 |
| 有有效候选时分别退出应用、取消这项事、只停止本轮对话 | 退出应用后仍可审阅。取消只处置用户选定的范围。停止对话只结束对应主轮。可独立运行的兄弟任务和已交付历史保持原状 |
| 模型先 ACK 再崩溃，或审阅／准备发布已提交但随后未 ACK | 前者能找回准确候选，后者按原回执补齐。两者均无需重新执行 Worker 或再准备一份交付，待审与渠道结果仍分别可查 |
| 长任务中用户补充另一个待办、改一个验收条件、保留一个独立孩子 | 保留准确的版本、来源和子工作。只有实质变化产生新版本。在并发变更时拒绝过期写入，不靠覆盖最新版消除冲突 |
| Web 重排尚未领取的输入，同时收到 Worker 和 IM 的消息，另有不同来源的请求尝试审阅或下载 | 仍只领取一次，遵守统一队列既有顺序和重排范围。无法根据同队列、同标题、同目录扩大授权。原生审批不被宿主自动重答 |
| 外发时断线，或新版本读取旧工具回执、旧归档及历史文件 | 只对有依据的原发送作核对，未确认保持未知，已有正式交付不重复。历史引用、原工具载荷冲突检查、下载权限及会话兼容性可验证 |

验证先用独立 SQLite、合成引擎与渠道，走真实接待、关闭、重开和派工入口，覆盖事务前后的故障点。复用已有的 [中断与替换用例](../tests/interruption-stop-replace.test.ts)、[关机用例](../tests/service-shutdown.test.ts)、[历史接待夹具](../tests/main-history-recovery-fixture.ts)、[回执与结果恢复](../tests/receipt-result-recovery.test.ts) 和 [桌面启动用例](../tests/desktop-service-startup.test.mjs)。桌面独占及平台进程树、原生审批／会话恢复、真实渠道确认，按平台做专项验收，并区分渠道回执与用户实际读到的信息。[测试边界](testing.md)

效率按同一组固定输入前后比较。记录每个请求新增的模型轮数、重复派工／发布次数、首次执行和续跑送入的上下文字节数，以及一次定向查询读取的历史范围。普通问答的附加历史轮数必须为零，重复操作不得新增外部尝试。目标规模增大时，普通输入和 Worker 启动的默认载荷应只随本轮所需内容增长。上下文和用时改善以实测为准，无需为此采集用户正文或另建生产指标系统。
