## 根因：已确认的机制与待验证的解释

此前[第二轮](worker-directory-llm-validation-2026-11-14-r2.md)十次仅四次通过。新 Main 规则确实加载，实际 Worker cwd 与宿主接受值一致；查询后继续定位时，可以找到合同层并加载规则。扫描遗漏、目录参数未传入引擎、旧提示未采用，都不是这些样本的主要解释。

但旧指标只保留最终 cwd，没有区分参数省略和显式选择默认目录。本轮先原样重建 R2 快照，补充 `workingDirectoryProvided` 等派生指标，再仅复现 Atlas 一次，得到：

| 边界 | 本次原样复现 |
| --- | --- |
| Main 查询工具 | 原生 inventory 中存在，说明与候选源文件一致 |
| Main 提示词 | 原生历史中确认采用 R2 目录规则 |
| 派工前查询／文件操作 | 均为 0 |
| `worker_open.workingDirectory` | 参数被省略 |
| 宿主实际 cwd | 按既有默认正常得到 `Main` |
| Worker 上下文 | 没有 Atlas／原生模块规则 |

这条失败链是确定的：**模型省略可选参数 → 宿主沿用默认 → Worker 没有目标分支的原生上下文**。宿主执行了现有契约，没有替模型选择错误目录。

为什么模型省略，不能仅靠动作记录证明其内部推理。当前最有依据的解释是派工约定留有歧义：

- 较早的派工段落要求“直接用 `worker_open`”，没有明确目录定位是前置步骤。
- 目录段落使用“工作入口”“默认适用”，未明确名称与绝对路径的区别，也未明确由 Main 在派工前完成定位。
- 查询说明只约束需要查询时如何使用工具，无法单独保证模型在派工前查询。
- 参数可选和合理的默认行为，让“先把任务交给 Worker 再定位”也能成功受理。

客户案例的证据也吻合这一解释：R2 两次失败的文件结果只有客户名线索，成功那次继续出现 `contracts`、`current` 层信息。问题发生在继续定位与结束定位的选择上，而非必须增加全量目录注入。

“派工消息出现定位词”只能辅助分析。候选成功样本中也有此类词语，因为 Worker 可以在已选目录内继续寻找业务文件；不能以关键词单独判断职责是否被错误转交。

## 方案评选

以下为保留现有扫描、`work_directory`、`worker_open` 及旧会话机制约束下的比较；“优先”是依据失败路径的判断，不是预先测得的成功概率。

| 方案 | 能解决什么 | 成本或缺口 | 选择 |
| --- | --- | --- | --- |
| Main 派工前置定位，合并目录责任与派工顺序 | 同时约束省略 cwd、名称等同目录、停在父层和外包定位 | 仍需真实 LLM 验证；增加必要定位工作 | **首选，本轮验证** |
| 强化 `worker_open` 字段说明 | 决策位置更接近调用 | 改动固定动态声明会改变指纹，需处理旧 Main 兼容；不能只当成普通 MCP 说明更新 | 本轮不选 |
| cwd 必填或宿主硬拦截 | 能阻止字段省略 | 显式填写默认或错误目录仍可能合法；进一步判断需新增语义依据、状态或分类逻辑 | 不作为最小修复 |
| 返回更多层级／完整候选树 | 减少展开步骤 | 未调用查询的样本仍看不到结果；增加上下文成本，未先解决派工责任 | 暂缓 |
| 代码从任务路径计算目录 | 有完整路径时能计算候选 | 项目／客户名称没有路径时无从计算，跨目录任务还需语义判断 | 不选 |

## 具体候选

保留 R2 查询工具说明。将下面这一条放在 Main 的业务派工段落之前，取代原目录段落：

> 目录由你在派工前确定。任务涉及本机已有项目或资料时，先定位本次工作文件或子目录，取得对应的绝对目录，再显式填写 `worker_open.workingDirectory`。项目名、客户名和“让 Worker 自己找”都不算目录已确定。已有明确路径直接使用；入口未知才用 `list_work_directories`，入口已知只用文件工具展开相关分支直到任务范围明确。任务限定子目录时用该范围；跨目录任务选有实际操作意义的起点。仅无本机既有资料或工作明确就在默认目录时，才沿用默认；定位失败先澄清，不开业务 Worker 代做定位，不切换 Main cwd。

派工句中的“直接用 `worker_open`”改为“按上述规则确定目录后用 `worker_open`”。其余记事项、授权、历史回执、消息和交付规则保留。

这是一个策略变量：把目录从可顺手考虑的信息，变成 Main 负责完成的派工前置条件。没有强制所有任务填写字段：通用文案仍可省略并使用默认；没有要求已知路径再次全局查询，也没有机械追到最深目录。未分别消融位置调整与措辞调整，结果支持这一整组前置约定，不能证明其中某一句单独有效。

## 成本、限制与交付边界

候选十次 Main 用量为 826,454 token：输入 822,066，其中缓存 724,352、非缓存 97,714；输出 4,388，其中推理 138。工具轮次共 46。额外的原样诊断为 27,658 token、1 个工具轮次；本轮十一业务轮共 854,112 token。

目录未知样本的首次派工中位数为 16.008 秒，明确／默认适用为 6.358 秒。R2 的若干快速样本跳过了必要定位，不能将其更少轮次作为正确工作的成本基准。候选更多操作是实际定位准备；缓存、顺序和生成差异使货币成本或净收益不能据此确定。K1 还做了一次派工后的 `worker_read`，增加整轮 token，但不属于目录查询或首次派工耗时。

Main usage 均与原生历史及对应响应计数核对，缓存输入和推理输出不重复累加。额外原生零输出响应与账号后台请求不等于业务轮用量，不能把上述数字当成账号账单。
