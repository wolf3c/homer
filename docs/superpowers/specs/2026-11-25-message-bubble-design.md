# 对话气泡与事项入口统一方案

2026-11-25 方案。用户已通过上方多事项标题竖向排列和下方「新开事项」外置行的 Demo。产品实施范围限于前端展示与定时气泡时间适配，沿用现有后端、工具、消息协议和数据结构。隔离候选已接入真实组件。现有数据无法覆盖的「新开事项」入口待单独讨论。

## 复用现有消息布局

主对话和事项 Preview 通过 `UserMessage` 与 `AssistantMessage` 共用 `MessageBubble`。气泡组件负责正文表面和右下时间，现有 `MessageDetails` 负责气泡行与侧边动作。各渲染器继续根据已有消息数据决定有无正文、标题内容和允许的操作。标题沿用现有位置，气泡下方事项行等待已有数据能够准确表达创建归属时再接入。

保留 `MessagePrimitive.Root` 和各自的消息 ID 前缀、正文选区、消息分组、虚拟器测量与历史分页。正文和时间保留现有直接子节点位置，尤其是选区允许结束在紧邻正文的时间节点这一边界。下方事项行在气泡外，排除在正文选取、整条引用、复制文本和流式消息内容之外。纯附件、批注、原请求、成果、授权／咨询回执和无正文过程继续走原入口。存在已核实的新开事项时才渲染下方事项行。

保留现有 `MessageActions` 的「引用 → 复制」顺序，事项 Preview 的「在主对话查看」仍在最后。复用横排／竖排、桌面左右位置、触屏落位、长文停靠和回焦；保护共享工作区中正在调整的宽度测量。继续复用 `ReferenceCard`、`QuoteBlock`、assistant-ui、Lucide 及现有样式和处理器。事项引用定位工作状态，消息引用回原消息，事项标题打开事项 Preview，定时标题打开定时详情。渠道来源留在原位置。

## 标题宽度由气泡确定

标题宽度上限等于对应气泡表面的实际边框盒宽度，标题留在既有过程提示之前或之后。一个共享的尺寸观察器只观察带标题的气泡，把测得的宽度交给消息根节点上的 CSS 变量。标题文字和点击区域不参与气泡测宽，气泡正文、虚拟列表及侧边动作继续沿原布局。无正文且无气泡时，标题的宽度上限沿用当前阅读列。

单事项保留现有图标、文本及点击条件，超长省略，完整名称保留给可访问名称与现有说明。极短时优先留图标，已核实的目标仍可打开同一事项，触屏和键盘仍能操作。定时标题使用同样的宽度约束，保留现有时钟、详情和回焦。没有实际气泡时沿既有标题或过程的阅读区，不建立空气泡供测宽。

### 多事项标题竖向逐项排列

独立只读核查在当前主会话找到 7 条有正文助手回复，其同一过程关联多个事项交办事件，其中 6 条各有 2 项、1 条有 3 项。6 条里的事项均通过身份校验，另 1 条的两个标题只能显示为静态文本。这里的数字是本次会话观察。界面已有 `taskSources[]` 和过程事件投影，可沿现有去重及首次出现顺序复用。按 `taskId` 区分，同名而 ID 不同的项继续各自呈现。对历史静态条目沿现有事件身份处理。无需为上方多事项标题增加协议字段。

沿用现有事项标题样式和顺序，多项在原标题位置由上至下排列，每项独占一行。每行紧贴气泡同侧边缘，宽度最多等于气泡边框盒宽度，超长名称省略并保留完整可访问名称。核实身份的标题沿用原按钮，直接打开对应事项 Preview，关闭后回焦到触发该次导航的标题。静态历史项按原样显示可读名称。键盘焦点和触屏命中区域逐项核验，避免覆盖相邻行或动作。

### 连续事项回复只在组首显示标题

**已实施，隔离验证通过，待代码复审。** 以统一气泡提交 `9f9c7448` 为基础，修正主对话中已有的连续分组。0.1.25 build 313 与该提交都取虚拟列表的前一行。原始记录中，同一事项的「复审通过」与「已提交」两条回复之间有两条已完成的内部 Worker 过程。它们没有可见内容，仍占据列表位置，导致后一条回复显示了重复标题。 [原交互约定](../../../ui/DESIGN.md#2026-11-23-连续事项回复与消息操作)

#### 展示与实现

独立复审确认两处需要收敛。前驱和当前回复共用实际回答投影，同时按同一帧的消息元数据判定事项归属。外层分组跟随同 ID 的运行时更新，避免正文已刷新、标题仍沿用上一帧。带启动失败、来源待核实、交互说明、成果或有效链接来源的无正文记录保留为边界。历史补页沿用现有按 ID 对齐和锚点校准，标题继续沿用现有样式和回焦。

代码复审补充了两项边界。事项 Preview 入口可用时，静态标题之后的首个已核验标题另起一组，使首个可点击入口保留，随后同组的重复入口继续隐藏。独立成果沿用气泡筛选条件，随成果列表更新一次生成消息 ID 集合，扫描历史时按 ID 查询。内嵌链接所对应的成果继续由正文呈现。

1. 仅当助手记录属于内部 Worker 过程、消息已完成且过程终态也已确认完成、整行没有可见内容时，分组才跳过该行。复用渲染组件现有的条件，涵盖正文、原请求、成果、事项标题、启动失败与来源待核实提示、交互说明、链接来源、操作及可见日期／时间。必要时将共用条件提取为就近的纯判断。正文以实际运行时投影的可渲染回答为准，包括经现有身份检查的流式正文。空 `text`、`audience` 或 DOM 高度都不足以单独证明该行可以跨过。缺少判定依据时保留该行作为边界。
2. 沿当前已加载的连续历史扫描现有 `rows`，记录上一条未跳过的行，然后复用 `continuesReplyTask`。用户气泡、交互回执、可见的无正文过程、仅成果或原请求的行、定时回复、进行中或异常记录仍可截断分组。沿用同一会话、前条回复已完成、单一明确事项 ID 和标题相同、同一天的规则，以及 `data-continues-task` 与日期分隔的 CSS 优先级。组首保留现有事项入口，组内标题沿用现有隐藏和焦点行为。
3. 在前端按已加载行顺序单次计算分组。跳过仅影响分组取前驱，保留历史记录、虚拟行、消息 ID、分页和锚点。首条可见回复先显示标题，补页确认接续后按合并顺序重算。前驱滚出视口或卸载后仍参与分组，未接上的历史范围各自判定。按消息 ID 对齐运行时内容与投影元数据，同 ID 的正文、状态、说明或成果更新后重算，也覆盖记录在空过程和可见过程之间转换。实现限于主对话现有分组入口，复用统一气泡、前端模块和样式。

#### 验收

- 扩展 `tests/message-actions.browser.mjs` 的现有分组场景，用合成记录重现两条同事项回复夹两条空的内部终态过程。验证仅组首标题可见，第二条正文、时间和操作可用。事项入口启用时，复用 `tests/task-conversation.browser.mjs` 的已有标题入口夹具，核对组首可打开同一事项、第二个标题不进入键盘焦点。将中间记录更新为带可见内容的同 ID 过程，验明后条恢复标题。覆盖启动失败或归属提示、交互回执或说明，以及仅成果、原请求、链接来源的可见行。
- 保留 `tests/chat-timestamps.test.ts` 中的标题变化、同名异 ID、多事项、来源待核实、发送者变化和跨日断组断言。复用浏览器流式场景，验证无正文但有事项标题的处理中记录保留标题，流式正文出现且符合条件时接续，正式发布后分组稳定。
- 在现有浏览器虚拟化和早页回填场景中，把空过程置于补页衔接处。验证补页前首条可见回复有标题，确认接上同事项前驱后隐藏重复标题，前驱离开挂载范围仍能分组，阅读锚点保持稳定。实施后执行现有定向离线检查及隔离浏览器专项。 [专项入口](../../testing.md#2026-11-23-消息操作横排与停靠)

## 气泡下方的新开事项行

沿用已通过 Demo 的紧凑事项行。有气泡时贴在下方外侧，事项行的可见范围不超过实际气泡宽度，也不撑宽气泡。单项一行，多项连续排列，标题单行省略，完整名称用于可访问名称。无正文时复用同一款单项或多项行，放在已有消息／过程位置，宽度受当前阅读列约束。两种情况均省略「已新建事项」独立标题。桌面动作沿原侧边，触屏动作排在事项行之后并保持原顺序。

下方事项行只显示现有前端数据能核实的创建结果。证据必须能确认 Main 的 `task_create` 已获确认、事项身份与回执一致、创建唯一归属到当前消息或过程位置。满足条件的条目沿过程顺序按事项 ID 去重，保留首次出现位置。仅有模型正文、普通事项引用、派工或更新、待确认回执，或历史记录无法核实归属时，静默省略该项。

现有 `taskSources` 同时表达创建、派工和其他归属。过程中的 `create_task` 活动可来自 `task_create` 或 `worker_open`，而 `previewVerified` 只提供现有导航所需的校验结果。部分无正文过程也没有对应的来源投影。前端沿现有可见性和作用域读取已有消息数据。数据不足时，完整覆盖待单独讨论，本次沿用现有投影和接口。

正文出现时，同一组事项移到气泡下方，保持消息锚点、事项顺序和可用焦点。点击复用 `openTaskConversation`，现有详情接口检查当前权限，关闭后回焦到触发入口。上下两处的同一事项共用按 ID 识别的 Preview 标签。上方标题表示消息归属，下方事项行表示已核实的本次创建。LLM 输入、提示词和原消息继续沿现有路径。

## 时间和验收

公开且正文非空的定时助手回复沿用 Worker 气泡时间规则，以现有 `createdAt` 显示，`scheduledAt` 继续记录原定投递。复用 `MessageTimestamp` 与 `MessageDaySeparator`。历史重新加载不需迁移。内部过程、仅有流式片段、空正文和无效时间仍沿原判断，日期分隔的游标保持原规则。 [定时气泡时间方案](../../architecture/scheduled-tasks-architecture.md#6-homer-如何收到消息)

- 以真实组件合成数据对照主对话和事项 Preview，在桌面、拆分窄栏、390 和 320 CSS px 验证左右对齐、外置行与实际气泡宽度、极短与长标题，以及动作顺序、布局、键盘及触屏焦点。覆盖 2 项、3 项、同名不同 ID、静态历史项和逐项打开回焦。
- 验证流式更新、虚拟历史补页和合并后选文及锚点稳定。覆盖正文选到紧邻时间、附件和批注、咨询／审批卡、跨日和定时时间资格。核对原消息和模型内容没有混入标题、时间或事项入口。
- 用真实前端组件和合成数据验收外置行，覆盖确认创建、同轮多输出与多项、重复回执，以及无正文到流式正文的过渡。核对宽度、顺序、Preview 标签复用、权限与回焦。验证仅派工、仅更新、历史缺失、无法唯一归属或其他证据不足时静默省略。真实消息的数据覆盖另行核对，合成案例只验收展示与交互。

两个 Demo 的通过范围为展示与交互。本轮实现共用气泡、多事项逐项标题与定时气泡时间；下方事项行等待能核实创建归属的数据。
