# Homer 会话架构实施计划

> **For agentic workers:** 按本计划逐项实施；使用 superpowers:executing-plans 的验证与记录方法。用户已指定多个 Codex chat 并行，不再另行询问执行方式。每项交付由独立 chat 审核。实施阶段未授权 Git 提交；后续用户已明确授权审核、本地提交到 main 和清理本轮 worktree。安装、发布和日常数据修改仍未授权。

**Goal:** 把 Homer 收敛为任务管理表与 Worker 会话工具，直接接收 Worker 原文，可靠支持并行、追问、改要求、暂停、恢复、正式交付和归档收尾。

**Architecture:** 一行 Task 管用户目标，原生 thread 管连续会话，Run 管一次执行。复用已有消息、回执、操作、来源与交付记录；模型只作业务选择，宿主绑定身份、版本、幂等、授权和执行事实。只有一条正式协作链路，不保留旧合同或旧工具兼容分支。

**Tech Stack:** TypeScript、Node 22、SQLite、固定 Codex App Server、现有 React 界面与 Node 测试工具。

**Spec:** [主 Agent 与 Worker 会话架构](../../architecture/main-worker-chat-architecture.md)。2026-11-05 用户新决定优先：不考虑旧版本数据与架构兼容；旧草案中兼容、双轨及旧库迁移条款不再适用。

## 全局约束

- 不改审批策略和沙箱权限，不触碰日常 Homer、账号、数据库、原生会话及其他 chat 的改动。
- 不新增调度服务、会话表、资源注册中心、第二主输入队列或跨 Worker 停服机制。
- 新 schema 只服务新链路；不支持的旧库在任何写入前明确拒绝，不自动清空或转换。开发验收使用独立数据库。
- Result 只保存主 Agent 显式采纳的准确成果；Delivery 只保存明确发布及渠道回执。普通文字无需两者。
- 任务版本、原始用户来源、执行租约、未知外发、幂等回执与明确审批是可靠性边界，不因去兼容而删除。
- 公开原文保留顺序、段落、完整正文和原生消息身份；不以正文相似性去重。超长内容按原消息分页可读。
- 归档沿真实用户授权入口；成功后一次事实通知加载通用归档 Skill。资源用途由 Agent 判断，不写清理特例。
- 不重做 UI、不升级引擎或依赖、不增加定时系统与主动接单观察模式。
- 实施过程保留现有变更；只改明确分配的文件。新增测试先失败后通过，删除旧测试前保留其仍有效的安全与故障断言。

## 审核重点

1. 两个会话同时回报、修改笔记及并发追问：原文不丢、任务不被 Worker 自动结案，同会话只运行一个执行。
2. 用户撤回或推翻要求：新来源和版本原子绑定，排队旧动作不能执行，迟到旧回复仍属旧版。
3. 暂停撞上异步启动、关机或强退：未确认退出不能换人；恢复只生成一个后继，已有原文可读。
4. 工具已提交但响应丢失、外发结果未知：按真实调用身份查原回执，不随机生成重试身份、不重复外发。
5. 归档含共享依赖、独有工作或用户保留要求：保全有价值资源；普通文字可结案归档，未决动作和未知交付仍阻止归档。

### 内部契约

- Task 保存目标版本、notes、办理状态、结案结果与归档状态。移除 Task 上的单 Worker 身份和 currentRunId 事实来源，整项结案由 Main 明确决定。
- 会话从 Run 归集。首个 Run 的已有 ID 可作创建中及续谈的稳定锚点，不另造 Worker ID；原生 threadId 在引擎确认后绑定。一个会话最多一个活跃或退出未知的执行。
- Main/Worker 真实工具调用身份由宿主取得并关联现有 operations，不由模型填写。新协作工具优先使用已有动态工具回调的 threadId/turnId/callId；不能以相同正文或随机新键模拟幂等。
- 既有 operations 同时关联本次已领取输入和协调轮。提交后丢响应时，恢复输入自动带入已提交动作及其当前回执；Main 先查原执行，不以新 callId 盲目重做。外发结果未知仍阻止重放。
- 目标变更同时绑定可信用户来源；工作笔记及普通对话不能扩权。Worker 获得本事项获准原话及实际采用版本，不读取整个主聊天。
- 用户撤回授权时，同一提交冻结受影响的旧排队动作，并登记所有受影响在途 Run 的停止意图；无法证明哪些会话不受影响时停止该事项全部旧轮。确认停止后才可按新版续谈；已经发生或未知的副作用保持事实。
- Worker 最终公开正文与 agent_receipts 在结束事务中保存到 agent_messages，再清除临时检查点。主队列直接读原文；正常协调结束由宿主记录处理进度。
- 普通发送排入同一会话，明确立即改向须操作准确当前轮次。任何改向接收回执均不等于已采用新要求；无法证明采用时保留旧版本，必要时确认停止后开原 thread 的新轮。
- 开始实施前，A 在现有模块内给出准确 TypeScript 方法/类型，C 将模型工具映射到它们，B/D 直接消费；不建立第二份运行时契约注册表。

### 授权来源接口收敛（后续优化）

第 7 轮的误选不是缺少当前授权信息：模型已读到历史 A/B 与当前 B，仍手填 A/B。普通创建和改目标移除模型填写的 `sourceRequestIds`，复用宿主已有的当前用户／事项事件绑定；历史原话继续可读，内部来源记录与越权检查保留。

确实需要多来源的后续办理通过选择已有 `pendingIds` 表达。宿主取各待办最近一次真实用户回执绑定的来源，再沿原校验处理；待办累积的历史引用和事件修改不作新授权。批量查询复用现有操作及消息记录，普通派工无新增查询，不加实体、表、迁移或授权服务。现有 Worker 的事项与正式成果选择保持原入口和范围校验。Skill 只同步移除手选授权 ID 的调用说明，通用判断原则不变。

独立审核发现仅有待办选择会挡住“后续用户要求复用旧成果、原工作没有待办”的正常协作，已补上创建时可选的 `resultIds`。宿主在现有创建事务内、原回执重放后读取所选成果准确版本的来源；真实用户轮可补充来源，事件轮不得借此扩权。主来源、材料、附件及 Worker 的精确成果选择不变，不增加结果转交实体。补测覆盖无待办转交、无关回报和归档拒绝、原版本来源、未选成果隔离，以及成果文件后来变化仍可回放原创建回执。
