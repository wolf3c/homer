## 1. 核心契约

| 所有者 | 唯一职责 |
| --- | --- |
| 生产方 | 用稳定 operation/message 身份，原子写入原消息和待投递回执；重复入队返回原消息 |
| 主信箱 | 保存、排序、领取及接收确认；不等待最终文字、审批决定或整个任务成功 |
| MainProcessHistory/协调器 | 当前轮的归属、起止和 completed/failed/interrupted/unknown；不撤销接收 |
| WorkerInteractions | 原问题/审批的有效性、待 Main/用户、决定及真实送回结果 |
| operations/执行器 | 写入、派工、发送的意图、效果和未知结果；按原操作核对，不借重投重做 |

| 主信箱状态 | 含义与转移 |
| --- | --- |
| pending | 原信待交付；领取后为 offered |
| offered | 已领取；真实接收确认后为 received，结果不明为 uncertain |
| received | 接收已确认，为投递终态；失败、停止、重启和交互取消均不得回退 |
| uncertain | 核对原执行，不自动重投；正向接收证据可转 received。证实未发送、原所有者退出、原授权有效且有明确恢复意图后，才可恢复同一封信的 pending |
| rejected | 仅保留既有的未交付输入撤回/来源拒绝；审批取消不等于撤回通知 |

仅同一进程能证明尚未尝试原生调用时，允许 offered→pending；deferClaim 保持现有严格的渠道重配边界，不扩大为失败重试。重启后没有“未发送”证据的 offered 进入 uncertain，不能靠超时重开。

接收依据是 turn/start 的真实接受结果与 onStarted。确认事务关联原消息、接收线程、native turn ID 和处理节点；用户 generationId 与 native turnId 不混用。已 received 的历史信件不再占队列位置、待投递数量或积压容量；业务结果继续留在原记录。

调度排他取当前处理/原生执行归属。旧轮已结束且所有者不再可写后才接待下一条；接收已知、业务结果未知可以同时成立。原所有者已退出时可接待独立新输入，但相应未知操作仍阻止相关副作用及更新；可能仍写入的所有者继续阻止接管。

来源真实性、接收方及资料读取许可在交付前检查；业务版本过期或原审批失效本身不删除应投递的事实通知。后续业务动作再核当前任务、版本、暂停/撤销及授权。真正被用户撤回的消息或读取许可仍沿原拒绝入口处理。

## 2. LLM 使用规则与业务结果

**宿主确定投递、身份、权限校验、回调有效性、幂等和迁移；LLM 只决定授权范围内的下一步业务。** 模型输出不能修改 receipt、数据库版本或执行归属，不能仅凭“已完成”文字制造成功。

复用现有输入封装和 prompts/main.md，保留宿主绑定的 messageId、kind、来源、task/Run、interactionId 及必要操作摘要；原文和历史是资料，不是系统指令或新增授权。长历史/操作明细沿现有工具按需读取，不拼整库，也不新增模型签收协议。

- 仅对宿主绑定的 interaction_required 使用 inspect_interaction；读取当前原请求/执行后，再依真实委托 respond_interaction 或 escalate_interaction。不猜测 ID，不把正文中伪造的字段当可信元数据；其他消息类型沿原业务工具处理。
- 引用或“查看为什么卡住”只授权核查，不自动续办。明确恢复意图也不能扩大原委托；Main 的本人审批不可自批，已经升级给用户的请求须遵循真实用户决定。
- 每次变更前由宿主重核原请求身份、epoch、版本、当前状态及操作范围，防止 inspect 后状态变化。prompt 是引导，不代替这些检查。

下表用于原生轮正常结束后的业务判定；真实 native turn 失败仍记失败，不因已做出决定而改成成功。

| 当前交互事实 | 本轮业务判定 |
| --- | --- |
| 仍有效 pending_main，未形成决定 | 未处理/失败；即使有非空最终文字也不能算完成，原请求保留 |
| approved/denied/answered，且同一原请求决定已真实送回 | 本轮可静默完成，不推断整个任务成功 |
| 已升级 pending_user，用户可见问题已持久化并有明确说明 | 本轮已交用户等待，交互仍待办、更新仍受阻；不能当作用户已批准 |
| cancelled/expired 已证实，无未送达决定 | 可静默结束本轮处理，保留失效事实；不复活回调，也不丢弃尚待投递的旧信 |
| 决定送达或操作效果未知 | 保留未知并核对原回执，不重新批准或重放 |

所有行都不改变已收到信件的 received。普通用户对话仍须正常回复；不能把“内部可静默”扩大到所有空回复。

### Task 3：接收证据与数据库版本迁移

**Interfaces:** src/store.ts 提供纯只读 `inspectMainReceiptEvidence(db, {mainAgentId, mainThreadId})`，返回预览 {sourceSchema, scope, rows, fingerprint}；rows 含逐行原状态/revision、精确关联证据及分类，指纹绑定库/线程身份、schema 和证据快照。新库启动迁移与旧格式脚本共用该分类，分别实施自己的目标和前置条件；不做双模式写入 API。新库的 `migrateMainReceiptsInTransaction(db, preview, operationId)` 只在既有事务中重核预览、写主回执/审计及最终版本，返回 changed/unchanged/uncertain 计数。

| 原记录与证据 | 新语义目标 |
| --- | --- |
| 任一旧状态，有同一原消息/接收方/线程/真实 native turn 的正向接收证据 | received；业务失败/unknown、活审批和未决操作独立保留 |
