# Homer Hook 系统设计

2026-11-07 · 首版源码已接入，已完成本地合成监听器定向验收。Hook 让宿主功能和受信插件监听业务事实的变化。事件由拥有该事实的模块定义和发出。首版提供通用监听接口和一个事件 `message.committed`。

## 监听接口

`hooks.on(eventName, handler)` 在当前 Homer 实例注册一个已定义事件的监听函数，返回可重复调用的取消函数。宿主在功能或插件启用时登记，停用时取消。取消后，尚未开始的回调不执行，已经开始的回调由调用方管理。监听端只取得注册接口，事件发送端由事实所属模块持有。

宿主在业务事务成功提交后分别调度监听器。发出通知后立即继续主流程，各监听器独立捕获同步异常和异步拒绝，诊断只记录监听器、事件类型和错误类别。异步回调迟迟未返回时，其他监听器仍可处理。首版运行在同一个进程，监听函数应快速交回控制权，同步阻塞或进程崩溃会影响整个宿主。

每个监听注册最多有一个执行中的回调和一条待调度通知。回调未结束时，新通知只保留最后到达的一条，覆盖前一条待调度通知。回调结束后再调度这条通知。注销时清空待调度通知。即使回调一直未返回，该注册也只占用这两个位置，其他监听器不受影响。需要逐条处理的消费者通过补读找回被覆盖的消息。

通知是尽力而为的唤醒，可能丢失、重复或乱序。监听器返回值不参与业务决策。Hook 不增加数据库表、持久队列、回放或重试机制。需要可靠处理的消费者按业务记录自行补读和去重。

## 首版事件

`message.committed` 携带 `{ messageId }`。消息模块只在一条**面向用户的消息首次完成持久提交**后发出通知。插件按自己的权限读取已提交消息，稳定 ID 本身不授予正文或附件的读取权。

| 来源 | 通知时点 |
| --- | --- |
| 自然答复 | 回复占位首次写入受控读取可见的终态，与相关输入状态一同提交后。通知使用该请求的 `replyId`。 |
| `send_user_message` | 本次消息、所选附件关系和操作回执一起提交后。首次即时回复可复用 `replyId`，后续显式发送及后台消息使用各自的 `messageId`。后续轮次收尾或回放已提交的操作均不再通知。 |

状态为 `completed` 的已提交消息按权限读取正文和准确附件。对已确认的失败或中断，只有宿主已为原请求提交面向用户的终态结果时才发出通知。受控读取返回原 `messageId`、`requestId` 和实际状态 `failed` 或 `interrupted`，正文中的残片、内部错误详情和附件均不开放。渠道可以据此向原入口显示简短状态。执行结果未确认，或启动恢复只把运行中占位改为 `interrupted` 时，该占位不触发通知，也不进入可外送的补读结果。辅助失败提示记录不单独通知。[受控读取和提交接线](../../src/service.ts) · [输入终态证明](../../src/recursive-main-inputs.ts) · [启动恢复](../../src/web-history.ts)

流式增量、内部 Worker 回报、内部协调、附件暂存、辅助状态记录和回滚都不触发事件。订阅者通过消息接口核对当前状态及授权。实现接点是两条路径各自的成功提交处，数据库表变动通知保留在宿主内部。 [消息架构](main-worker-chat-architecture.md#消息与附件统一交付) · [宿主提交路径](../../src/service.ts)

将来有新消费者需要其他事实时，由该事实所属模块定义事件名、触发点和最少字段，再复用监听接口。需要可靠执行的核心流程继续沿各自的持久路径办理。渠道订阅、受控补读及外送见[多渠道方案](multi-channel-architecture.md)，模型主动调用的扩展工具见[主 Agent 插件工具注册](main-agent-tool-registration.md)。

## 验收

| 场景 | 通过条件 |
| --- | --- |
| 自然回复、显式发送及后台消息 | 成功提交后才可收到消息 ID，并读取已提交事实。显式发送后再收尾、操作回放、事务回滚、增量和内部记录均不额外触发。 |
| 失败、中断及未知结果 | 已确认且提交了用户终态的失败与中断分别通知一次，只能按权限读取状态和稳定 ID。执行未确认、恢复标记的占位及辅助提示均不通知，也不成为外送候选。 |
| 慢监听器 | 让一个监听器永不返回并连续提交多条消息。该注册始终只有一个在途回调和一条待调度通知，其他监听器和主流程继续推进。另测回调结束时只调度最后保留的一条，抛错或拒绝也能释放在途位置。 |
| 注销和实例隔离 | 取消后未开始的回调不执行，其他实例的监听器收不到此实例事件。停用全部监听器时，宿主照常提交和读取消息。 |
| COMMIT 失败 | 用延迟外键约束让自然答复和显式发送真正失败在 COMMIT。回滚后的消息均不通知，也不能作为已提交结果读取。 |
| 读取期间有未提交修改 | 同一连接正在修改消息正文或临时解除撤销时，受控读取暂不可用。事务回滚后能重新读取原已提交消息，撤销状态继续生效。 |
| 同一函数注销后重新注册 | 旧注册的在途回调结束时不调度已取消的积压，新注册独立接收事件，再次注销后也无迟到回调。 |

## 首版实现与验证

通用实现位于 [hooks.ts](../../src/hooks.ts)。宿主暴露 `app.hooks.on('message.committed', handler)`，在自然答复、已确认的输入拒绝和显式消息事务成功返回后发出事件。关闭宿主时清理注册及待调度通知。

合成监听器通过 `app.readCommittedMessage(messageId, scope)` 读取结果。调用方是受信的进程内宿主模块，须提供已获准的请求范围 `{requestId}` 或后台事项的准确版本 `{taskId, taskVersion}`。该方法再次核对消息归属、撤销、操作回执或输入终态。同一连接处于事务内时暂不提供结果，事务结束后可重试。渠道授权及工具注册按各自方案接入。
