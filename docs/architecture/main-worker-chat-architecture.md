# Homer 主 Agent 与 Worker 会话架构

**Homer 用一张任务管理表管用户交办的事，用一组会话工具与 Worker 共事。** 它可以自己办，也可以同时开几个 Worker 会话。Worker 发来问题或最终回复时，宿主自动送给 Homer，由 Homer 判断下一步。

本次候选将待办并入任务表，用消息保存 Worker 原文及用户答复，用附件保留可下载的准确文件版本。首次派工同时记任务，暂停与结案续办沿原事项处理。核心删除 Pending、Result、Delivery 和 Worker 授权副本，按新主 schema 6 和媒体 schema 2 初始化独立库。旧实例使用与其数据匹配的原版本。[实施范围与验收](#本次最小实施范围与验收)

**把用户注意力作为成本。** 对外主动说明应提供可用结果、待决定的问题或影响预期的重要变化。交办确认简短说明将做什么，重复接收、内部协调和普通进度留在现有状态与记录中，用户询问时照常答复。界面优先呈现需要用户处理的事项，过程按需查看。[注意力原则参考](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/000-philosophy.md)

**主 Agent 工作原则。** [主提示词](../../prompts/main.md#原则)包含主人翁责任、善用资源并创造办法、判断可靠、深入细节、通过小步试验学习、赢得信任和崇尚行动七项原则。用户视角与质量验收纳入主人翁责任，整体路径重审纳入善用资源，具体产物与反馈纳入小步试验学习，异议与决定后执行纳入赢得信任；既有授权、资源限制和验收边界继续生效。2026-11-11，本地提示词资源与合成线程恢复测试 5 项通过；真实模型行为效果未验证，未安装发布。

**拒绝审批后的沟通。** 主提示词要求转达拒绝后说明停止的步骤、对原任务的影响，以及存在时的可行下一步。该文字已进入隔离真实审批验收候选，拒绝回执及不执行效果通过；现有断言未单独验证回复是否完整解释任务影响和替代方案。提示词资源检查不替代这项模型行为验收。

## 核心边界

**Homer 在本机代表用户办事。** 主 Agent 和 Worker 直接复用 Codex 已有的工具、MCP、Skill 和插件，沿 Codex 原生机制发现、安装、配置和调用。读写普通文件、操作浏览器、联网等通用能力的执行权限和确认由用户选择的 Codex 配置及操作系统决定，Homer 不另设目录黑名单、工具白名单或通用审批关卡。

本次切换的产品仅提供本地桌面、Web、移动 App 和 CLI 入口。微信及 Telegram 旧桥接、启动和设置入口随旧交付链退役。多渠道接入另行实施，旧实例继续使用原代码与数据。

Homer 只定义自己的业务工具，负责管理任务、协调 Worker 会话和交付消息附件。宿主校验这些动作的委托来源、事项与会话归属、接收方及操作回执，并负责中断与恢复。入口核验用户身份并处理外部收发，核心保存输入来源。

扩展接口与渠道方案见 [Hook 系统设计](hook-system-design.md) · [主 Agent 插件工具注册](main-agent-tool-registration.md) · [多渠道接入架构](multi-channel-architecture.md)。核心消息独立提交和读取，实际业务动作沿原操作记录核对权限及未知效果。

**实施状态。** 隔离候选已移除 Main／Worker 的通用权限覆盖和浏览器目录名单。Codex 读取本实例专属 `CODEX_HOME` 的原生配置，空配置走引擎默认，恢复沿原线程及原生恢复语义。宿主保留自身文件操作的来源、路径、准确字节和覆盖检查。[执行配置](../../src/engine.ts) · [宿主接线](../../src/service.ts)

渠道订阅覆盖某事项在授权生效后所有明确发给用户的后台消息及其附件，内容、发送时机和附件选择由 Homer 决定。插件负责入口授权、订阅路由与发送。普通回复按真实 `requestId` 回到原入口，后台用户消息按事项订阅选择唯一地址，沿同一 `message.committed` 与受控读取接口处理。

渠道首版支持文字收件、消息及附件外送和聊天内订阅。主程序沿用现有表结构，只补按授权范围补读与可信的订阅工具接线。待答、审批卡和外部附件入站各自接入已有交互或媒体能力，并单独验收。[多渠道首版范围](multi-channel-architecture.md#1-首版范围与消息路由)

## 任务管理表

**一行代表一件需要持续跟踪的事，包括尚未开始的待办。** Homer 记录内容后，可以在已有授权内自己办理或开 Worker 会话；直接首次派工时由同一次操作建行。即时问答和无需跟踪的想法留在主聊天，不再另建 Pending 记录。记下想法不等于获准执行。

### 事项、会话和执行

| 现有记录 | 含义与生命周期 |
| --- | --- |
| 事项 `taskId` | 持续跟踪一个目标或想法，关联零个或多个 Worker 会话。改要求、追问和换人沿用原事项。 |
| 原生会话 `threadId` | 保存与一个 Worker 的连续对话。同一会话可以先后办理不同版本的要求，空闲后仍可继续追问。 |
| 执行 `Run` 与原生 `turnId` | Run 保存一次执行尝试及其所属事项、会话和版本，turn 标识模型轮次。已登记等待的轮次沿原 Run 接续，完成答复且确认执行退出后记为已结束。后续追问创建新 Run，优先恢复原 thread。 |

宿主从已有执行记录按原生会话关联历史。引擎确认会话前，沿本次派工回执识别创建过程。重启先查原执行及已提交动作，确需替代执行时沿用 `replacesRunId`。原会话可恢复就继续该会话，需要另开会话时保留前次关联。

会话读取提供当前 Run 的 `exitConfirmed`；历史回执中的同名字段保留当时的事实。执行器已退出不等于用户目标已完成，续办仍须核对当前授权、版本和未决操作。

### 字段与存放位置

Homer 打开的是同一条任务记录。表格最后三行是随任务一起显示的只读资料，按需从原记录读取。

| 字段 | 类型与初值 | 谁维护、存在哪里 |
| --- | --- | --- |
| `taskId` 事项编号 | 文本，宿主生成，唯一 | 沿用 `tasks.id`。追问、换 Worker 和重启都沿用这个编号。 |
| `goal` 工作内容或目标 | 非空文本，创建时必填 | 显示当前版本的 `task_versions.goal`。首次派工可直接取首条 `message`；Homer 用完整目标和仍有效的限制承接实质变更，旧版可回看。 |
| `state` 办理状态 | `open / paused / settled`，初始 `open` | `open` 包括尚未启动的待办，不代表已授权或正在执行；执行事实单独显示。整项暂停须确认相关执行已停，再记 `paused`。恢复或结案通过对应事项动作处理。 |
| `notes` 工作笔记 | 文本，默认空串 | 存在 `tasks.notes`。Homer 可补写或修订判断、依赖、期限、下一步及结论。业务上的新情况先用文字表达。 |
| `outcome` 结案结果 | 枚举，初始为空 | Homer 结案时将成功（`succeeded`）、部分完成（`partial`）或失败（`failed`）与 `settled` 一起写入。取消经确认后记 `cancelled`。执行中断是 Run 的事实，不自动结案。 |
| `historyState` 归档状态 | `visible / archived` | 沿现有用户授权入口办理，通过下文的归档检查后写 `archived`。恢复可见性写 `visible`，归档不擦除原文或回执。 |
| 原用户请求 `sourceHistoryIds` | 只读历史引用列表，可为空 | 回看真实交办及后续变更。尚无用户委托的想法可没有用户来源，`version.authority` 为空；获准执行的事项必须有可核验来源和动作范围。历史可读、用户只要求记录或已有任务行，均不等于执行授权。 |
| Worker 会话 `workers` | 只读列表，初始为空 | 按 `runs.taskId` 找到执行，以首个 Run ID 作为稳定 `workerId` 归集；引擎确认后绑定 `threadId`。显示各轮实际采用的任务版本、状态及原回复。 |
| 已回复内容与附件 | 按需读取的消息引用，初始为空 | 从关联的用户消息、Worker 原文及其附件读取。任务表不再保存 `results`、`deliveries` 或另一份成果状态。 |

### 这张表怎么读写

- **记一件事或查进度。** 新建时由宿主绑定实际输入，有真实用户来源才登记该来源。列表默认看可见事项，支持按办理状态分页、按事项编号或关联会话定位。打开详情才读会话和消息。列表标题可沿用已有标题，缺省用目标首行。
- **改一项内容。** Homer 只提交要改的字段或办理决定。宿主按读取时的 `tasks.revision` 校验并提交，版本冲突就重读。工作笔记可以独立更新，暂停、恢复、取消、归档、授权变化和对外发送经对应动作校验后提交。
- **接一次回报。** Worker 的开工、提问、最终回复和中断由宿主记在对应会话。任务行自动反映最新事实，需要 Homer 处理的原消息进入主队列。重复回报按原轮次和消息身份识别。回报只更新对应会话，工作笔记和整项结案决定由 Homer 写。

实际入口仍为 `task_create`、`list_work`、`work_inspect` 和 `task_update`。只记事、暂不派工或由 Homer 亲办时用 `task_create`；首次直接派工用 `worker_open`，不必先创建任务。待办的内容、处理说明和关注状态合入同一行的 `goal / notes / state`，不增加待办类型、转换状态或第二套编号。以后明确交办已记录的事项时，先用 `task_update.goal` 绑定这次真实授权，再使用原 `taskId` 派工。决定不再跟进时沿原取消动作关闭该行并记录原因。列表和相关轮的有界摘要复用同一工作表；存在 `open` 行不会自行唤醒模型或启动执行。

删除 `pending_add / pending_list / pending_update`、`task_create.pendingIds` 及待办来源选择流程。创建、更新要求时，宿主沿当前真实用户输入或事项事件绑定来源；无用户委托的记录不得伪造来源。后续用户交办在原事项的版本和操作中关联当次真实输入，笔记修改不能产生新授权。`work_inspect` 继续读取获准原话，来源读取与校验从 Pending 模块归回已有消息、任务和操作记录。

用户补充或复用资料时，Homer 在 Worker 消息中给文件地址或附上选定附件。宿主核验现有文件权限、资料来源和本次转交范围；后台轮沿已有委托办理。任务表不登记附件授权清单，详见[授权与后续复用](#授权与后续复用)。`archive_work / restore_work` 只处理归档可见性，不启动或删除工作。

**存储与调度改动。** 复用 `tasks.notes`，删除 `pending_items` 及其独立索引、摘要、关联与归档阻塞。无用户委托的记录允许现有版本来源及 `authorityJson` 为空，不另加授权状态；执行前仍须取得有效用户授权，不要求成果类型或验收表。同一事项下多个会话可以并行，每个会话至多一个活跃或退出未确认的执行。宿主按绑定的会话和 Run 校验调用者、轮次及权限。首个 Run 的已有 ID 可标识创建中的会话，后续关联原生 thread，不再建立 Worker 实体。Task 不再保存单个 `currentRunId` 或 Worker 身份；Worker 终态只更新对应执行，整项结案由 Homer 决定。旧子任务合同与迁移分支删除，不支持的旧数据库在写入前明确拒绝，不自动转换或清空。[任务表、版本与终态处理](../../src/recursive-tasks.ts) · [执行与会话字段](../../src/store.ts) · [主输入队列](../../src/recursive-main-inputs.ts)

### 用户补充、改口或推翻重来

用户只是提出想法时，原话保存在聊天，需要持续跟踪才记入同一工作表；已有事项的补充先记原行笔记。普通资料补充保存在原用户消息中，Homer 按需追加到相关 Worker 会话；任务笔记可引用该消息，无须登记附件或改要求版本。**如果按原要求做完已经无法验收，或者用户改变了允许执行的动作，就在同一 `taskId` 下保存新版要求。** 从“只记下”到“现在开始”同样须绑定新的真实授权。比如“改到周六，仍然只起草”，新版同时保留周六和只起草两个要求。即使整稿推翻，只要用户仍要同一份交付，就沿用这一行。用户另要一份独立推进、单独验收的交付时再开新行，引用选定的原稿版本。

宿主在创建新版的同一次提交中，将本次已核实的用户请求关联到 `task_versions.triggerOpId` 指向的操作。以后既能读到上一版目标，也能查到用户哪句话改变了它。当前授权取仍然有效的用户要求，用户明确撤回的动作从允许范围中移除。已排队消息和动作在启动前重核版本与授权，冲突交 Homer 处理。已开始的动作核对实际执行及中断结果，外发沿原回执处理。

授权撤回同时冻结受影响的旧排队动作，并为受影响的在途执行登记停止意图。无法证明哪些会话不受影响时，停止该事项全部旧轮；确认停止后才按新版继续。已经发生或效果未知的动作仍保留实际记录。

**每次回复都随本轮实际采用的版本返回。** Homer 可以在原会话下一轮补充，也可以让受影响的在途工作改向或停止。普通收发由宿主绑定版本。旧轮只确认收到改向、尚未采用新版时，迟到的原文归旧版。Homer 可核实并复用仍适用的部分，新版验收、发送和续办都须核对目标版本。要覆盖有保留价值的旧稿时，先确认有可恢复的文件版本。已经发生或效果未知的外发仍查原回执。[任务版本与运行归属](../../src/recursive-tasks.ts)

### 暂停、等待和恢复

**修改要求不等于恢复执行。** 事项处于 `paused` 时，`task_update` 可仅提交 `goal`，在原事务内保存新版要求、真实用户来源及修订，仍保持 `paused`；不启动 Worker，也不恢复旧排队输入或审批。只有明确 `action: "resume"` 并通过现有授权、退出与未决操作校验，才恢复为 `open`。恢复按最新有效版本办理，不因单纯解除暂停重复建版；同时改要求或授权时仍保存新版。不新增工具、状态或实体。

| 用户意图 | Homer 与宿主的处理 |
| --- | --- |
| 暂停整件事 | 先冻结该事项的新派工和排队启动，再中断在途轮次。确认前通过现有控制状态和执行记录显示“停止中”及待确认会话，全部确认后记 `paused`。 |
| 中断某个 Worker | 中断选定会话的当前轮次，保留同事项其他会话。Homer 继续判断整件事的下一步。 |
| 恢复办理 | 复用 `task_update(action: "resume")`，可同时提交 `goal`。暂停事项核对仍有效的授权；已结案事项须取得新的用户授权，按下述规则恢复原行。恢复后由 Homer 选择需要续谈的会话。 |
| 取消整件事 | 沿原取消操作确认范围内执行已停止，再记 `settled / cancelled`。已经发生或效果未知的外发保留原回执。 |

**已结案事项继续使用原 `taskId`。** `resume` 覆盖成功、部分完成、失败及取消后的重新办理。宿主从本次可信输入绑定新授权，沿原输入和操作记录核对其晚于上次结案／取消依据及当前版本的有效来源；旧授权、归档事件、Worker 回报或改笔记都不能替代。需要改目标时与 `resume` 一起提交 `goal`，不先恢复旧要求再另改；目标不变时沿用原文，仍创建关联新授权的 TaskVersion。只记补充而未要求继续执行时，更新笔记即可，不恢复办理。已归档的先沿 `restore_work` 恢复可见性，该动作本身不重新授权或启动执行。

已结案事项恢复前核对 `tasks.revision`、旧执行退出、停止结果、未决审批及未知操作；不能确认就保留原状态。在同一原操作事务内写入新版及可信来源，置 `state=open`、清空当前 `outcome / settledAt`，并保存回执；旧结案结果、版本、消息和附件仍沿原记录保留。同一操作重试返回原回执，并发冲突须重读，已为 `open` 时不再创建续办版本。恢复动作不启动 Worker，也不复活旧排队消息、审批或外发；后续沿 `worker_send / worker_open` 按新版办理。不新增重新开单工具、事项副本或状态类型。

等待对象、条件及下一步写在工作笔记中。相关回复、用户消息、审批结果或已登记的定时事件进入同一主队列后，由 Homer 重新判断。日期条件须有可用的定时入口且登记成功，才能向用户确认已安排自动继续。具体定时接入单独验收，尚未登记的触发按待安排记录。结案前，Homer 核对目标完成情况并处置本事项仍在途的执行。

### 同一行在两位 Worker 回报时怎样变化

以用户交办“查清预览为什么空白，先别改文件”为例。下表是同一个 `taskId` 在不同时刻的内容。“页面”和“构建”是两个会话的简称。

| 时刻 | 办理状态 / 结案结果 | Homer 的工作笔记 | Worker 会话（宿主自动更新） |
| --- | --- | --- | --- |
| Homer 记下目标 | 办理中 / 空 | 核对页面请求与实际构建文件名。 | 空 |
| 两位 Worker 均已确认开工 | 办理中 / 空 | 核对页面请求与实际构建文件名。 | 页面、构建均执行中 |
| 页面 Worker 回复“页面请求 app-v1.js，返回 404” | 办理中 / 空 | 核对页面请求与实际构建文件名。 | 页面已答，构建执行中 |
| 构建 Worker 回复“构建里只有 app-v2.js” | 办理中 / 空 | 核对页面请求与实际构建文件名。 | 两个会话均已答，可读两段原文 |
| Homer 核对证据，答复用户并结案 | 已结案 / 成功 | 页面引用了旧文件名，已查明原因。 | 两个原会话均可回看 |

两位 Worker 都答完的那一刻，Homer 仍可以在原会话追问。本例的两段原回复和面向用户的答复就是内容记录，无须生成另一份成果或交付记录。

## Worker 会话工具

| Homer 想做什么 | 需要提供什么，会发生什么 |
| --- | --- |
| `worker_open` 开会话 | 给 `message`，可附选定附件、指定工作目录；普通文件直接给地址。提供 `taskId` 就在该事项下开会话；省略则用本条说明作为初始 `goal`，同时创建任务行。宿主绑定可信来源和现有权限，返回 `taskId / workerId`；受理不等于引擎已启动。 |
| `worker_send` 发消息 | 选会话，写正文，可附选定附件。空闲时沿原会话开下一轮，忙时普通补充按序等候；`immediate=true` 沿 steer 补充当前轮。文字与附件使用同一消息和回执，回执不证明已采用新版要求，也不改变沙箱权限。 |
| `worker_read` 查会话 | 从任务行找到关联会话，按需查看当前状态、原消息和文件地址。消息按游标分页；指定消息及原生内容项可分段读完整原文，不强塞整段历史。 |
| `worker_interrupt` 中断本轮 | 指定会话，由宿主核对当前轮次并确认停止结果。历史保留，可以稍后续谈。收起会话、取消整项工作和归档事项分别按各自意图办理。 |

首次派工在同一现有操作与事务中受理任务、初版要求、首条消息、Run 和回执，提交后才启动引擎；不串行调用两次公开工具，也不新增派工实体。重试返回原编号，参数冲突拒绝，重启查原 Run 与回执，不能再次创建。已有事项的分工显式传 `taskId`，不按相似文字或上下文猜测归属；独立用户目标才新建事项。省略编号不能绕过原事项的暂停、取消或来源限制。需要先整理总目标再分工时，仍可单独记任务，但不是普通派工的前置流程。

开会话及转交变更时，宿主从已有消息和版本记录取出本事项已授权的相关用户原文，随说明送入 Worker，保留来源引用并绑定本轮实际采用的版本。Worker 无需读取整个主聊天。Homer 在委派正文或工作笔记中区分用户要求、已核实事实和自己的执行安排。Agent 自定条件不能当成用户要求；续办、改向或归档时，结合当前目标和用途重新判断是否仍适用。复用原消息、任务版本和笔记，不增加必填报告格式。[事项版本与来源校验](../../src/recursive-tasks.ts) · [原始请求与分工参考](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/004-prompts.md)

并行调查只需开两个会话，返工只需在原会话指出缺口。多个 Worker 写共享文件前，Homer 应明确各自互不覆盖的修改范围或安排先后顺序。需要换人接手同一项写入时，宿主先确认旧执行已结束。Homer 在原事项下交代已知结论、尚缺什么以及获准读取的文件地址；跨 Worker 的资料由 Homer 按授权转交。Worker 内部使用的原生子 Agent 由所属会话管理。

宿主复用 Codex 原生的 `thread/start`、`thread/resume`、`turn/start`、`turn/steer` 和中断能力。空闲执行器可以释放，续谈时核对原会话并重新绑定当前工具和权限。[引擎适配](../../src/engine.ts) · [交互与审批](../../src/worker-interactions.ts)

主提示词继续由 `thread/resume.developerInstructions` 传入，供 Codex 正常压缩时重建上下文。旧会话冷恢复且摘要变化或缺失时，宿主在开始处理消息前通过 `thread/inject_items` 追加新版开发者消息，并明确冲突时以新版为准。原生确认后才在现有 `meta` 中记录会话和提示词的摘要。同版本重启沿用该摘要，恢复阶段不调用模型。[宿主升级回归](../../tests/scenarios/prompt-resources.md#宿主升级回归)

## Worker 怎样自动上报

宿主用已有派工记录定位原事项，附上引擎已确认的会话和轮次。Worker 正常结束回答就触发回传，无需调用“汇报完成”工具。

| Worker 发生了什么 | Homer 怎样知道 |
| --- | --- |
| 已开始、执行中、正常等待 | 自动更新会话状态，在任务行可见。流式正文和工具过程在原会话按需查看，日常进度无需启动 Homer。 |
| 提问或遇到需要决定的阻塞 | 原问题和相关事实进入主输入队列。Homer 先判断，确需用户决定时才发起待答，收到决定后再回复原会话。见[审批与等待](#审批与等待)。 |
| 给出本轮最终回复 | 将面向 Homer 的公开最终正文**原样送入主输入队列**，保留消息顺序、段落和文件地址。纯文字也完整回传。超过单轮容量时按同一原消息分段，标明余文，可读到结尾。 |
| 执行失败、被中断或失联 | 将实际状态和已取得的公开输出送回 Homer，区分部分答复、无正文和结果未知。Homer 可以核查、续谈、换人或告知用户。 |

**需要处理的回报在 Homer 空闲时唤起它，正忙时按现有主队列顺序等候。** 轮到时，宿主展开已保存的原消息，正文直接进入 Homer 的上下文。用户无需再说“继续”，Homer 也无需轮询或手工签收。主输入在归属确认后可恢复，收到原文和已经采取行动分别留证。[主输入队列](../../src/recursive-main-inputs.ts) · [既有投递与恢复机制](../2026-10-23-worker-return-main-queue-implementation.md)

普通回复在现有结束事务中，将公开原文和实际执行状态写入 `agent_messages.payloadJson`，沿原消息字段及载荷绑定事项、版本、Run、线程、轮次和原生消息身份，并创建对应 `agent_receipts`。原文落库后在同一事务内清除临时输出检查点，提交后唤起 Homer。主队列直接读取该消息，重启后仍可完整重读，不依赖引擎会话或 Result。不再自动生成普通候选成果。

本轮协调正常结束时，宿主核对已提交动作的回执并登记处理进度。需要等待时保留等待事实，交后续事件唤醒。处理中断或回执未知时，沿原输入及已提交动作接续。整项工作的完成由 Homer 结合用户目标判断。

## 消息与附件统一交付

**Worker 回复本身就是工作结果。** Homer 读原文、核实内容、追问或回复用户，判断写入任务笔记。文字不再复制为 Result，也没有独立的“已验收”状态。用户明确要求审阅时照常审阅；这个业务要求由任务与消息表达，不变成每次协作的强制协议。

工作中的文件继续直接给获准目录内的地址。只有实际附到消息、需要下载或转交准确版本时，宿主才保存附件快照。正文里出现路径、Markdown 链接或 Worker 说“已完成”，均不自动公开文件。

### 模型只选择内容和接收方

| 动作 | 最少输入与处理 |
| --- | --- |
| 普通答复用户 | 保持自然语言最终回复，宿主自动保存为用户消息；不增加必用工具、JSON 或成果类型。 |
| 带附件答复，或后台明确通知用户 | 用一个 `send_user_message` 动作选择 `text`、可选 `attachments`；即时答复无需创建事项。后台沿当前事件绑定事项，确需选择时才指定 `taskId`。不接收模型填写的授权来源、外部地址、成果 ID 或发送状态。正文与附件至少有一项。 |
| 给 Worker 资料 | `worker_open / worker_send` 保留自然语言 `message`，可选 `attachments` 只列本条消息实际转交的附件，追加与 steer 使用相同输入。普通共享文件继续在正文给地址。 |

附件输入的每项二选一：`{path: 绝对地址}` 表示将获准文件的当前字节附到本条消息；`{assetId, revision}` 表示复用既有准确附件。宿主验证后统一保存为现有 `AttachmentRef`。路径输入只在消息动作中处理，不增加文件登记或采纳工具；不自动扫描正文找文件。这里的 `send_user_message` 替代两个旧工具，底层也按下表删除重复记录，不能实现成调用旧采纳再发布的包装器。

真实用户轮显式发送时使用该请求已有的 `replyId`，正文、附件和本次操作回执一并提交，作为本次答复；后续原生轮次结束沿原记录收尾，不再生成或覆盖这条消息。提交回执丢失、后续轮次失败不能把已提交内容改回未完成；执行事实单独记录。后台通知创建独立消息，关联原事项及实际版本，`requestId` 为空，不冒充对旧用户请求的再次答复。内部协调默认留在内部，只有 Homer 明确发给用户的内容才进入此路径。追加内容使用后续消息，不能用新调用 ID 重发已有内容。

| --- | --- |

| `worker_authorities` 与 `setAuthority` | 删除按 Run 复制的来源和授权描述及专用读写接口。审批沿 Run 的实际 `taskId / version` 读取原 TaskVersion；不再写第二份当前授权。 |
| `agent_messages`、`agent_receipts` | 保留内部原文、顺序及处理回执。Worker 结果无须再次转换、采纳或签收。 |
| `conversation_messages` | 承载面向用户的正文、附件引用、实际生成状态和撤销事实。即时答复和后台消息使用同一结构；内部轨迹保持内部归属。 |

| `accept_result / publish_delivery`、`work_inspect.resultId` | 删除。向用户发送一次消息；`work_inspect.messageId` 直接查获准用户消息及附件，`worker_read` 继续查内部原文。任务详情按需展示关联消息和操作回执，不再要求“先采纳”。 |
| `task_create.resultIds`、`worker_open.resultIds`、`Authority.resultIds` 及 Run 中同类选择 | 删除。所选准确资料只记录在实际转交消息的附件中，Run 继续关联原消息及投递回执，不复制附件清单。 |
| 任务级附件授权及上一稿登记接口 | 删除 `Authority.attachments`，取消拟议的 `task_create.attachments / task_update.attachments`、补充授权汇总及仅为任务清单设置的 pin。不另建会话附件授权表；目标、允许动作和取消约束仍由任务维护。 |
| 以 resultId／runId 下载或定位文件的接口 | 删除旧路由及 `publishedResult/publishedArtifact` 查询链，改由消息所选附件解析。预览与批注的来源同样改为消息＋附件＋摘要，不保留“按 Run 取第一个文件”的入口。 |
| Main／Worker 的旧 HOME 执行分支 | 退役；业务执行统一使用专属 HOME 的现有原生路径。`controlOnly` 管理连接及其受限权限保留，不为旧绑定或测试夹具保留另一条业务执行路径。 |
| `read_material / write_markdown / stage_file_result / create_voice_result` | 按[文件工具的独立用途](#文件工具的独立用途)删去重复读写入口；保留的附件导出只产生文件地址，不创建 Result 或消息，不成为交付前置步骤。 |
| 操作与审批回执 | 保留各自实际动作的身份、范围及未知状态；不增建另一套通用回执或附件授权表。 |

### 文件工具的独立用途

已静态核对当前入口、宿主调用及测试：正式桌面、默认 CLI 和示例配置使用专属 HOME 的原生路径；HOME 不匹配时的受限业务执行用于旧绑定兼容，并被部分合成夹具沿用。**决定退役该业务分支，不再以它为理由保留重复工具。** `!nativeTools` 同时用于无模型轮次的管理连接，不能整段误删。[配置与默认值](../../src/config.ts) · [执行权限配置](../../src/engine.ts) · [宿主接线](../../src/service.ts)

| 现有能力 | 收敛判断 |
| --- | --- |
| Main／Worker 旧 HOME 执行 | 删除因 HOME 不匹配而继续受限运行的业务分支及专用回退。新版本在启动业务执行前明确拒绝不支持的旧绑定，不自动启用其原生工具、迁移账号或改写目录。 |

| `create_voice_result` | 退役 Worker 的系统语音合成及 SILK 编码。既有 SILK 附件继续支持原件下载，已有 WAV 衍生时可播放。渠道沿普通文件交付。固定 Codex 0.163.0 恢复旧 Worker 时仍可能带上历史工具目录，宿主拒绝该旧调用。 |
| `file_checkpoint` | 退役主 Agent 与 Worker 的显式文件快照工具，原有备份文件保留。Codex 对话回退仅影响会话轮次。旧快照需要时先核对清单索引和原摘要，在隔离目录取回准确字节。 |

导出及消息快照继续复用必要的宿主写入与校验，核对执行身份、参数、路径、链接、大小、摘要、覆盖冲突及中断回执。原生文件操作沿 Codex 与操作系统的权限执行，管理连接的保护保持独立。

第 7 项定向复验使用固定 Codex 0.163.0 和隔离数据。旧 Worker 按原 `threadId` 续聊，宿主明确拒绝历史工具调用，会话继续完成。合成旧快照可按清单及 SHA-256 取回原字节，原目标保持不变。验证了附件准确字节导出、SILK 原件下载和 HTTP WAV 预览，返回的 WAV 经 macOS 播放器完成播放。浏览器和打包桌面内播放未实测。

夹具改用当前业务配置与已有合成执行器，退役仅验证旧模式或旧工具存在的断言；来源、审批、准确字节、撤销、停止和恢复断言移到对应保留路径。默认测试仍离线，不因切换夹具配置而启动真实引擎、账号或模型，不新增测试专用执行分支。文件和媒体专项按[测试边界](../testing.md)单独验证；本轮仅更新方案。

### 存储与字段归属

复用现有表并调整必要字段，不新增成果、交付、发布事件或 Worker 实体。任务表仍是一件事一行；已有消息、附件和执行记录各保存自己的事实。

| 数据 | 字段及写入规则 |
| --- | --- |
| 用户消息 | 沿 `conversation_messages.id/threadId/text/status`；`requestId` 仅指实际正在答复的请求，不表示路由或用户轮权限。补齐可空的 `taskId/taskVersion/operationKey/revokedAt`，以及宿主确定的 `audience: user/internal`。显式动作关联原操作；自然答复沿现有请求回执与原生消息身份，不强建额外操作。关联版本取实际上下文，不能伪装成最新版本。 |
| 用户消息的附件关系 | 将现有 `conversation_attachments` 从按请求关联改为按 `messageId` 关联，保存 `refsJson: AttachmentRef[]`。同一请求的输入附件与回复附件可不同，不再根据用户角色猜归属。 |
| Worker 消息的附件关系 | 沿 `agent_messages.payloadJson.attachments` 保存同一引用类型；正文仍原样保存。结合消息接收方、原操作的可信输入及投递回执核验范围，适用于首次派工、追加和 steer。 |
| 附件快照 | 沿 `media_assets` 保存 `assetId/revision`、名称、MIME、字节数、摘要和宿主管理的文件。上传保留真实 `requestId/bindingId`；本地附加允许这两项为空，用 `originOperationKey` 关联原消息操作及其文件选择，不伪造上传请求。原路径从该操作读取，转交和读取按消息来源及现有文件权限核验。 |
| 操作与执行 | `operations` 保存原消息动作、可信输入和回执；`agent_receipts` 与 Run 保存实际投递、执行和恢复事实。附件始终从所关联消息读取，不从操作历史汇总另一份授权。UI、任务列表与下载入口读取原记录。 |

沿用 `{assetId, revision}`，不再新增 attachmentId。已提交的文件字节不可覆盖，源文件改动后需要新的附件；复用既有快照只增加消息引用，不复制文件或改其来源。纯文字只引用原 `messageId`。需要固定尚未对用户公开的版本时，在实际内部转交消息中附上快照；不保留脱离消息的独立“采纳”步骤。

### 下载、留存与撤销

下载、预览、来源定位和“在文件夹中显示”统一从**获准消息＋其准确附件引用**解析，不接受任意文件路径、Run ID 或“本任务最近一个文件”。读者只能取得那条获准消息所选的附件。源文件以后移动、修改或清理不影响已保存的附件；定位原文件时仍校验原地址和摘要，不能把不同内容当成原交付。附件缺失或摘要不符明确报错，不重新取源文件补成别的版本。

现有 `MediaStore` 仅按原请求校验上传附件，且默认到期回收，**不能直接套用到转交和输出附件**。上传入口保留真实请求与绑定检查。转交后的读取核对消息来源、接收方、投递范围、撤销和字节完整性，不要求 Worker 的原请求等于附件的上传请求。原始文件可读与预览、内容提取是否可用分别判断，本地文件不伪装成一次网络下载，也不因缺少可选衍生物失去原文件下载。实际输入模型时仍按原能力及准备条件校验。宿主在处理附件时校验路径、链接、文件类型、大小及磁盘配额，分别沿上传与输出的文件约束处理。

复用 `media_pins` 保护有消息、未完成操作或执行引用的附件。用户输出和明确附到内部消息的准确版本，在对应历史保留期间固定附件，归档、关机和任务结案不解除它；排队及投递结果未知的消息也保留文件。原始上传沿原留存策略，转交或附到输出后按消息引用固定；任务笔记中的引用不另产生 pin。删除或明确解除保留时释放对应 pin，确认没有其他有效引用，才交现有 GC 回收；不新增自动删除会话入口。配额不足时明确失败，不静默删除历史附件。撤销一条消息使依赖该条消息的读取与转交许可失效，不自动撤销其他获准消息对同一文件的引用；全局撤销附件则使所有受管引用不可读。撤销不抹掉已发生或未知的效果。

**撤销不收回已取得的内容。** 已下载、导出到普通目录或进入模型上下文的副本无法通过撤销受管引用收回。导出副本继续受现有文件权限和当前用户要求约束；宿主不自动删除副本或原文件，不新增副本追踪、文件授权清单，也不宣称能阻止原生工具再次读取已有文件。

### 授权与后续复用

**附件跟随会话消息，文件访问沿用现有权限。** 任务版本继续记录目标及变更，`version.authority` 保留用户授权的动作范围；附件不加入任务授权清单，也不汇总成另一份会话授权表。

- **普通文件。** 在消息里给地址，由 Codex 原生工具按用户配置和操作系统权限读取。Homer 受管附件通过已有的消息附件入口提供选定内容。
- **首次转交和后续补充。** `worker_open / worker_send.attachments` 直接选择本条消息的文件或准确附件。宿主核验 Homer 有权读取并在当前委托内转交，沿原操作绑定可信输入、资料来源与接收会话，将消息、附件关系、保留引用和受理回执一并提交。只提供选定资料，不继承生产任务的执行权限、目录写权限或全部历史。暂不转交时保留原用户消息，需要时再发送。
- **追加或 steer。** 普通补充沿原队列等候，`immediate=true` 将同一条带附件消息投递给准确的当前轮。受管附件按该会话的已校验消息和原投递范围读取，排队未投递的消息不提前可读；投递已开始时允许目标轮读取所附内容，不要求模型等待 ACK 后再读取。ACK 及未知结果沿原回执核对，不另登记权限。补充资料不改变目标版本或 Codex 执行配置。
- **续谈、换人和恢复。** 原会话按已投递消息继续读取仍有效的附件，换 Worker 时由 Homer 把所需资料再附到新会话消息，复用原快照。恢复核对原消息、接收方、轮次和回执，不把未知投递改写为已接收，也不自动重发或按任务继承全部资料。收到新材料不表示已采用新的业务要求。

提交、投递和读取时核验消息来源、准确版本、撤销状态及调用者的会话／Run 身份；业务动作继续受任务版本、暂停和取消约束。后台轮沿已有委托办理，不能靠笔记、可读历史或一个附件 ID 获得新操作权限。来源撤销后按现有范围停止后续受管读取和排队动作；已取得内容遵守上述撤销边界，未知效果保留原记录。

实现时移除 `read_material`、`Authority.materials`、`resultGranted/readResultInput` 和任务附件清单的读取分支；`inspect_attachment` 与附件导出共用消息范围和现有文件校验。上传入口仍检查原请求；转交读取不再错误地要求原上传请求等于 Worker 的初始请求。不另建授权工具、授权记录或 Run 附件副本。追加和 steer 均以本条 Worker 消息的附件与投递回执确定范围。

### 本地提交与崩溃收尾

`send_user_message` 的完成边界是本地消息及附件提交。消息 `completed` 表示该条内容已经完成，不证明整个用户目标成功。普通原生最终回复沿原请求及轮次检查点收尾，不为它另建操作。下述暂存与事务规则同样用于 Worker 消息的本地受理；引擎是否接收则沿原投递回执判断，本地已提交不等于追加或 steer 已送达。

1. 显式消息动作沿现有 `operations` 登记意图，绑定当前输入、轮次、文件选择及消息身份。快照写入前登记原操作归属和临时 pin，再复用受管写入与校验；重试先查原回执，参数冲突拒绝。已登记的快照不能被源文件新内容替换，未提交的新增消息及附件关系不能成为读取许可。
2. 快照就绪后重新核验原轮次、任务版本、当前权限和取消状态，在同一主库事务内提交消息正文、附件关系及保留引用、真实来源和操作回执，释放本操作的临时 pin。真实用户请求的回复与原输入沿现有生命周期收尾，不能掩盖仍在途或效果未知的执行。只有已提交内容可通知 UI；通知失败不撤销提交。
3. 恢复先沿现有实例与执行归属机制确认旧写入者不能再提交，再完成数据库恢复、核对原操作。不能只看 `messageId` 是否存在：答复占位行可能早已创建。正文、准确附件关系和本地受理回执的原子提交才是本地提交完成的依据。

| 可核实的事实 | 沿原记录收尾 |
| --- | --- |
| 本地提交已完成，响应丢失或进程退出 | 返回原 `messageId` 和回执，保留消息 pin；不重跑 Worker、不再生成消息或复制附件。后续轮次失败也不覆盖已提交内容。 |
| 已确认旧写入者退出，事务未提交或已回滚 | 将原消息操作记为 `failed`，回执注明 `message_not_committed`；只释放该操作的临时 pin。有答复占位的沿现有中断路径收尾，不写成功正文。失败事实随原输入恢复交给 Homer，由它按当前授权决定是否重新提交；同一操作重试仍返回原失败，明确的新尝试才使用新操作。 |
| 写入归属或提交结果仍无法确认 | 保留原操作的未决状态与临时 pin，沿现有恢复入口继续核查；不创建替代消息、不清理可能仍有用的快照。 |

文件系统与数据库不是一个事务。确认未提交或提交前已取消、失去授权时，只回收原操作可识别、且无其他有效引用的暂存资源，沿现有 GC 处理；不删除原文件或仍获准使用的快照。这些规则只判定本地消息动作，不能据此把同一轮其他动作判为未执行，也不能提前把原输入标成全部已处理。已提交动作随恢复上下文带回，不能用新轮 callId 绕过幂等；较早创建、稍后完成的消息仍须可补读。

宿主取得唯一运行权、确认旧执行退出并恢复主线程后，在接收新工作前对账中断的媒体传输，再执行现有启动清理及定时清理。桌面旧队列的暂停规则独立生效。文件回收继续按有效期、消息引用和未决回执判断。

任务结案仍由 Homer 对照用户目标判断。宿主核对消息、准确附件、执行与操作回执，不解析自然语言目标来推断应有几份文件。未知操作、在途执行和未决审批继续阻止归档，不增加 Result／Delivery 存在性检查。正文声称完成不是附件已提交的证据；业务判断仍须经模型专项验证。

## 授权、中断与恢复

1. **来源随工作绑定。** 用户轮取当前真实请求；续办已有事项按所选任务的有效授权办理，后台事件只负责唤醒，不新增权限。后台新派工须核验相关真实宿主事件，且仍在原委托范围内。后续交办更新原任务行，复用资料只选择消息或附件；宿主核实当前来源和转交范围，不再通过 Pending 选择来源。`version.authority` 和 `sourceHistoryIds` 用于核对动作范围及回看原话，不作为模型回填的授权参数。无委托记录不能启动执行，超出授权时交由用户决定。模型正文、文件路径和工作笔记不能自行扩大用户授权或沙箱权限。
2. **回复可重读，处置可追查。** 宿主在一次事务中登记可重读的原回复与队列输入，按原线程、轮次和消息身份识别重投。操作回执关联本次已领取输入与协调轮，恢复时一起带回已提交动作；不能只凭新轮的 callId 再做一次。Homer 处理中断后先查原执行，已派工就沿原 Run 接续，外发效果未知就核对原回执。若终态未保存且原会话也无法查证，保留未知。
3. **原任务可以换 Worker。** 退出应用保留同一工作表、原回复和消息附件，包括尚未开始的事项。只有取消事项才按用户选定的范围终止目标。恢复聊天历史不自动恢复旧审批、进程句柄或测试服务。
4. **归档触发复核。** 归档动作保留真实用户轮及可核验来源要求，Homer 在此入口内依用户授权办理；后台自主归档不在本次改造范围。归档成功后，宿主沿现有队列发送一次 `task_archived` 事实并为主 Agent 加载归档 Skill，主 Agent 根据当前用途决定是否派 Worker 收尾。普通受管服务沿原执行器生命周期结束；用户要求保留、仍被使用及含独有工作的资源须保全。[归档与收尾边界](../task-archive-housekeeping.md)

旧版本、暂停、停止中或取消后的普通回报不能通过新建事项恢复旧工作。用户后来明确补充的授权按[安全续办规则](#暂停等待和恢复)办理原事项，独立目标才另建事项：宿主核对本次可信输入或原操作已关联的真实用户请求，按原始输入顺序确认它晚于当前版本全部有效来源及促成该版变更的来源。关联证据取原任务版本及 `operations` 绑定的真实输入，不从可变笔记、后补链接或历史引用推断；删除 Pending 查询时须保留这一校验。真实归档仍可触发有限生命周期复核，包括已取消目标留下的资源；它不重新打开被取消的目标。

**归档入口限制单独评估。** 当前“必须在真实用户轮归档”的限制继续保留。它便于绑定当次用户意图，但也阻止 Homer 在已获授权的后台轮自行归档；是否改为核验既有授权，是独立产品决策，不是本次合表的必要条件。无论采用哪种入口，都须保留来源、完成证据、未决审批、执行退出及未知操作检查。

### 审批与等待

**已回答交互的历史展示（2026-11-11）。** Web 历史页按当前页的真实用户答复请求 ID，关联原 `worker_interactions.responseUserMessageId`（该字段保存请求 ID），核对答复原文、对话及原用户来源后，补充只读完成卡片；没有用户答复的内部决定不投影为用户决定。前端授权完成态直接复用固定 ApprovalCard 原生只读回执，保留请求和必要范围；允许使用 `done` 外观、拒绝／取消使用 `denied` 外观，状态文字只表示用户决定，不表示操作执行成功，不传执行回调或详情展开内容。自定义审批完成布局、图标与样式已删除。咨询按原问题 ID 展示问题与回答。 咨询完成态统一复用固定 QuestionFlow 的 `choice` 只读回执，不提供提交回调；原生组件纵向显示全部问答，取消自定义翻页、题号和分页字段。仍是同一用户消息及时间，不新增消息、业务表或权限状态，也不恢复原生回调。旧记录仅在可核验时适配。纯原生提交确认按准确回复身份及固定宿主文案隐藏，含业务结果、错误、附件或取回编号的回复保留。待答与执行授权链路不变。定向离线及合成持久数据库／产品界面专项通过，安装包与真实账号链路未验收；复验见 [测试说明](../testing.md#授权与咨询完成卡片)。

目标设计沿用 Codex 原生审批及操作系统的确认入口。Homer 可以用已有待答和审批卡协调 Codex 已发出的请求，处理等待、决定回流和中断。Homer 业务动作仍按各自的委托来源和状态校验。

以下审批回路继续适用。普通工具权限由 Codex 决定，宿主按原轮次回送决定。[宿主接线](../../src/service.ts) · [原生审批](../../src/main-native-approvals.ts)

**归档轮可以发起审批。** 宿主核对当前领取的真实归档通知、原事项版本和既有用户来源，将具体请求绑定到仍在运行的 Main 轮次，用现有审批卡请用户确认。审批卡的决定直接回到等待中的 Main 请求，普通消息仍按原主队列等候。审批卡可拒绝，现有停止入口可按活动轮次取消等待，决定与停止均可在本轮等待期间送达。轮次结束或失效后关闭卡片，迟到决定不能执行操作。是否派 Worker 由 Homer 根据工作本身决定。

**所有 Worker 审批先交 Homer。** 原生请求和工具能力审批统一走现有 Worker 待答。Homer 查看原请求和真实用户委托，在任务范围内直接批准或拒绝必要的实现、验证及有限临时权限；不因只读沙箱、申请临时权限或命令变化就升级。每个新请求仍须重新审核，用户明确限制单条命令时严格遵守。超出委托、影响不清或必须本人确认时才升级；费用、发布、持久权限及额外私人资料未获明确授权时须请用户决定，并说明必要性、范围和影响。用户决定先记录到原待答，再作为关联输入回到 Homer。Homer 核对当前意图和请求是否仍有效，用现有答复入口回复原 Worker。用户点击允许后，Worker 继续等 Homer 的答复。宿主核对真实决定、原操作和原 Worker 轮次，批准不能扩大范围，拒绝不能转成批准。等待发生在原 Worker，Homer 可以继续处理其他消息。

未升级请求保留 `pending_main`，直接批准不生成用户审批卡或用户回执。已有 `userQuestion` 记录请求曾升级，批准或取消继续要求匹配真实用户决定，包括结束后的重复答复；`details.review` 只承载操作核对内容，不单独决定必须本人确认。沿用原状态和记录，无 schema 迁移。Codex 默认沙箱、Main 自身审批、既有收费和系统本人确认入口保持原边界。

审批读取授权时，沿请求绑定的 Run 查其实际 `taskId / version`，不读取任务最新版本冒充旧轮授权，也不再维护 `worker_authorities`。同时核对当前版本、来源撤销、Run／epoch／thread／turn 和停止状态；无有效委托时明确拒绝。`worker_interactions` 继续保存具体请求、当时依据、升级与用户决定、回复及送达事实，它们是原审批的历史证据，不作为另一份可持续授予权限的记录。来源读取改变不影响 Homer 先判断、用户必要时决定、Homer 再回复原 Worker 的次序。

| 验收场景 | 通过条件 |
| --- | --- |

## 现有机制的去向

必须覆盖以下行为，才可称本次收敛完成：

- 想法、待办与已启动工作在同一表读写，承接和取消均沿用原行；无委托和仅要求记录的事项不能派工。补充授权绑定原用户输入与实际版本，修改笔记、搬动引用、重启或收到 Worker 建议都不能产生授权。多个有效来源及新旧输入顺序校验保留，不因删除 Pending 放行旧要求；对用户意图的语义判断沿模型专项验证，不新增自然语言权限解析器。

- 成功、部分完成、失败及取消后的事项，均可在新的真实授权下经 `task_update.resume` 续办原行；覆盖目标不变、同次改目标及归档后先恢复可见性。新版来源准确，旧结案记录、回复及附件保全；暂停后的正常恢复不受影响。只补笔记、恢复可见性、旧回报或归档事件不能重新办理；旧来源、退出未确认、未决审批及未知操作仍拒绝。
- 并发续办、同一操作重试以及提交前后崩溃，最多提交一次恢复与一个新版；失败不留下半套状态，恢复本身不启动 Worker。后续会话使用新版，不复活旧排队输入、审批或已发生／未知的动作；原操作回执和旧版本归属不被覆盖。
- 首次 `worker_open` 一次返回原 `taskId / workerId`；同一操作并发、重试或受理后崩溃均不重复建行、消息或执行。给已有事项开会话必须使用其编号，不另建任务；授权失败不留下已受理的半套派工，启动结果未知沿原回执核实。
- 删除 Worker 授权副本后，两类审批入口都能读取实际版本的来源；用户改口、撤销、暂停、取消、旧轮迟到及重启仍不能放行失效请求。具体审批证据可回看，用户决定仍先回 Homer，不直接放行 Worker。
- Worker 原文自动回传，纯文字直接答复，普通文件直接给地址；全程不产生成果或交付记录。同一事项版本可以先后发送两条不同消息，重复同一操作仍只有原消息。
- 一次发送选定多个文件，只附所选文件；缺失、变更中的源文件、越权、保护目录及摘要错误均明确失败。附加失败不生成“文件已交付”的完成消息，不对部分附件静默成功。
- 修改或清理工作目录后，历史消息仍可下载原字节；重启、归档、到期 GC 不删除仍有历史、操作或执行引用的附件。撤销一条消息不破坏其他合法引用；在撤销范围内，后续受管读取、转交和导出均拒绝。已导出的普通文件不被改写或删除，其读取继续遵守原文件权限；不得以“副本仍可读”误报受管撤销失败，或以“受管读取已拒绝”宣称副本已收回。
- 后续 Worker 能读取所选旧附件；知道未转交附件的 ID、同属一个任务或能读部分历史，都不能取得其他受管附件或原任务的操作权。保留上传来源和撤销检查，转交不伪造新上传，也不以 Worker 初始请求不同为由拒绝合法附件。

- 分别在登记意图后、快照写入中或完成后、消息事务回滚、提交后响应前退出；确认未提交则原操作失败且无引用暂存可回收，已提交则复用原消息，无法确认则保留未决与 pin。提交前取消或失去授权同样不能留下成功消息或永久阻塞；共享快照和原文件保全，其他未知动作不被误结案。
- 恢复不重复派工或消息，显式消息已提交后的原生轮次结束不另建答复；内部消息不进入用户输出。占位消息和较早创建、较晚完成的消息均可按原身份恢复读取。

### 重启后，原任务怎样继续

桌面 `v0.1.4` 的主会话可以沿原生线程恢复到增加了可选 `worker_open.title` 的版本。宿主只放行这两个已核实的工具指纹组合。恢复保留原线程的工具声明和资料中的旧指纹，因此回退时旧版仍可识别原会话。新线程使用当前工具定义，其他不匹配仍需兼容性审查。[启动兼容检查](../../src/service.ts) · [定向回归](../../tests/main-tools-resume-compatibility.test.mjs)

2026-11-09，本地 `main` 的 `41a24f71fa2ec3cab05f277f3e826b4203ab5f18` 在隔离 macOS App 中通过 10 项真实 ChatGPT 检查。首次正常重启后，已接收但从未领取的用户消息沿原线程和原回执只执行一次，回复引用了重启前的上下文。测试在宿主接收边界扣留另一轮的完成事件，两次正常重启均保留其未知回执，未重放。切换模型来源和资料接管使用隔离合成验证，确认旧待处理消息仍暂停，新消息可执行。本轮验收针对本地候选。

首次启动只提供欢迎页、账号引导和三个内置 Skill，零自动模型轮。原执行归属确认后，宿主仅取消仍待处理且没有领取证据的旧 `first_launch` 输入，保留原文、来源与回执身份。已领取、结果未知或已结束的记录沿用原恢复规则，旧首启来源不能作为用户授权。普通用户输入与归档 Skill 使用各自的现有入口。

「排查重启后任务无法重跑」发现两项实际任务停在 `recovery`。旧 Run 记有 `interrupted / uncertain` 和 `restart_unconfirmed`，对应进程租约已不存在。旧版跳过已中断的 Run，隔离复现中续跑、接管和替换均返回 `run_stop_unconfirmed`。当时的记录无法还原这两个进程怎样结束，另开同目标任务可能重复改文件或外发。[排查及复现记录](../work-coordination-architecture.md)

正常关闭 Homer 时，宿主关闭自己持有的执行器，保留原任务及待审成果。执行器确认关闭，或重启核实原租约的执行者已经退出后，宿主在同一事务中把退出事实写进原 Run 的检查点并释放匹配的租约。Unix 还检查受管进程组。历史记录缺少退出证据时，原任务保持待核实。[启动与关机](../../src/service.ts) · [进程归属](../../src/processes.ts)

重开后，Homer 用 `work_inspect` 查看原事项，用 `worker_read` 直接读已保存的答复；前一轮文件通过 `resultId` 查看，本次目标改为消息的准确附件。需要继续工作时，`worker_send` 在原版本、当前授权和确认退出的范围内续谈并关联前次执行。外发仍凭原发送回执判定。桌面必须先取得实例独占，归属不明的进程仍阻止接管。[续办判定](../../src/recursive-tasks.ts) · [桌面实例归属](../../scripts/desktop-profile.mjs)

| 宿主能证实什么 | 主 Agent 能怎样继续 |
| --- | --- |
| 已有原回复、正式成果或交付回执 | 直接读原文、核对已有成果或原交付。即使仍须核实某次写入，也可先查看已保存的结果。关机不作废结果。 |
| 旧执行确已结束，目标未完成，下一步没有未决冲突 | 主 Agent 可在原授权内续谈。原 Worker 会话不能恢复时，沿原 Task 和已核实进度派新 Worker，用户无需重新交办。宿主在同一事务中复核退出证据、未决操作和当前修订，再创建关联前次尝试的 Run。两次并发继续最多启动一次，旧执行的迟到回调不能提交结果。 |
| 旧执行者可能仍能写，或它已退出但某次外发效果未知 | 指出哪项写入或发送受阻，核对原进程归属、文件版本或原渠道回执。可安全隔离的只读核查先做。无法查证的外发保留未知。空租约、超时或单个 PID 都不足以安全重做。 |

同次排查还复现了三种独立故障。目标架构须让它们分别有可观察的结果。

| 隔离复现 | 实施后应看到什么 |
| --- | --- |
| Worker 已提交候选，退出应用后任务变成 `cancelled`，候选变成 `invalid` | 重开原事项可继续读原回复、核对正式成果，Worker 启动次数不增加。普通回复不再生成候选；明确取消才处置用户选中的工作。 |
| 模型先 ACK 后崩溃会漏办候选，验收及发布准备已提交却漏 ACK 又会留下阻塞 | 宿主按原消息及已提交的业务处置收尾，中断后能找回未处理原文。确认尚未发送的交付沿原记录续送，发送结果未知时核对原回执。普通答复免去模型签收。 |
| 一个无关新问题被迫多跑一轮核对旧回执，随后被报 `main_recovery_unconfirmed` | 旧问题留在对应事项。宿主可用时，新请求按原队列顺序独立完成，附加历史模型轮为零。接待成功也不批量解禁桌面暂停的历史工作。实例归属不明时仍保护整库独占。 |

### 其他试用问题能避免到什么程度

| 此前遇到的情况 | 新架构的作用与界限 |
| --- | --- |
| 派工时把说明填进材料字段而收到 `material_path_denied`，审阅时填错嵌套字段或漏验收证据 | **普通会话消除这类填表要求。** 首条消息就是说明，文字答复直接可读，不经过材料解析、成果类型和必填验收表。用户指定交付的文件仍须实际核对；不保留旧合同。[派工复现](../2026-10-30-task-dispatch-and-isolated-transport-fix.md) · [审阅复现](../2026-11-02-review-publication-repair.md) |
| 已看到完整正文，用户要的文件却没有正式交付记录 | **目标是直接检查消息是否有准确附件。** 一次发送附上实际文件，不再补办采纳与发布；缺文件或发送未知仍须如实说明。旧问题记录不证明新链路已通过。[交付缺失记录](../2026-11-02-review-publication-repair.md) |
| 后续 Worker 知道成果引用，却读不到原任务的已验收成果 | **转交能力保留，去掉成果前置条件。** 普通文件给获准地址，准确版本按本次用户委托转交附件；未选内容、越权历史与操作权限仍拒绝。现有授权回归须改测消息和附件的实际接线，不能仅删掉拒绝断言。[新转交边界](#授权与后续复用) · [现有授权回归](../../tests/result-input-authority.test.ts) |
| 只发归档事实，主 Agent 曾只确认通知，也曾把自己补充的预览条件延续到验收后而重启服务 | **更容易复核，用途判断仍可能错。** 从原会话区分用户要求、Agent 的执行选择和当前用途。报告提到某文件只提供查证线索。隔离实测中，明确要求保留时没有派工，到期后有实际回收 worktree、构建和日志的样本，共享依赖和独有草稿得到保全，部分场景只完成了部分回收。到期只结束原保留条件。[归档实测](../task-archive-housekeeping.md) |
| 测试曾留下运行中的预览服务，后续 Worker 无法停服 | **沿用原执行器生命周期。** 正常受管样本在原 Worker 退出时已停服。另一夹具延后关闭、却报告执行器已退出，服务当时确实仍在运行。夹具修正后原事项尚待结算，实际没有触发归档。自行脱管的服务仍须核实归属，这些样本无需新增跨 Worker 停服接口。[受管服务与夹具对照](../task-archive-housekeeping.md) |
| 断线重试后出现两段相同文字 | **同一消息重投可去重，不同消息仍可能同文。** 固定引擎的假上游试验产生了两个身份不同的完成项（独立候选提交 `22b44c7`）。保留原生身份，可区分宿主重复投递与引擎产生第二条消息。仅凭文字不能推断工具是否执行了两次。[队列重投验证](../2026-10-23-worker-return-main-queue-implementation.md) |
