# 会话历史虚拟化实施方案

更新日期：2026-11-18。状态：**第一阶段已实现；隔离功能验收通过，性能部分达到探索目标**。下方自动补齐、上方自动读取、定位与活动交互已接线；复审与提交状态以Git记录为准，未部署，未实施数据淘汰。

## 1. 目标与第一阶段边界

用户确认的方向是：优先使用 TanStack Virtual；下方新消息自动完全补齐，不以手动加载为前提；上方历史在接近边界时自动加载，离开视野的内容可卸载展示；保留阅读位置和引用定位。先验证消息渲染虚拟化，再根据实测决定是否淘汰上方数据缓存。

第一阶段只改变前端展示及其与既有分页、滚动的接线：

- 下方仍由现有历史读取 owner 自动逐批补齐；不因正在看旧消息或 DOM 未挂载而停止。
- 上滑接近已加载边界时自动调用既有 `before` 读取，不再依赖“加载更早消息”按钮。
- 只有视口附近及确需保护的消息挂载 React/DOM，其余位置由库提供的测量、估算与占位维持。
- `HistoryWindow` 保留已加载消息、连续性判断及现有数据身份；本阶段不裁剪消息体，不新增持久缓存或数据库结构。
- 自动补齐不等于自动滚底。初始化及用户明确点击“最新消息”只定位一次；新消息、流式增长、重连、触底及新 Run 不得擅自恢复跟随。

不在本阶段实现全文搜索、Markdown 分块引擎、自动淘汰消息数据、定时回收服务或新的滚动管理框架。单条巨大消息的成本和前端数据持续增长是明确边界，不用“虚拟化已接入”替代性能验收。

## 2. 依据、已有能力和已知代价

方案调研及原展示实测基线为 `e3434e27`。实施验证采用当前工作区的隔离冻结副本和固定依赖，源码哈希及测量边界记录在本地验收材料；不是把并行变化中的共享目录直接当作运行实例。历史连续加载已在 `8d469d5c`；性能专项及实测说明在 `e3434e27`。共享工作树另有图片、Preview 等并行修改，实施时必须重新核对，不能整份覆盖 `homer-app.tsx` 或其他混合文件。

## 3. 最简渲染接线

在 `HomerApp` 内接入一个 `useVirtualizer`，直接替换现有消息列表输出，首版不另建 `VirtualThread` 文件、controller、store、消息注册表或事件总线。只有实际接线确实无法保持清楚边界时，才考虑提取一个薄组件，不预先创建抽象。

实施顺序与约束：

1. 从运行时**已提交**的消息 ID 顺序生成可见项，沿用 `isVisibleConversationMessage` 并排除无持久消息 owner 的 runtime 占位。每项只携带稳定消息 ID 和对应 runtime index，不复制消息体。不把筛选后索引直接作为 `MessageByIndex` 的 runtime index。
   `HomerApp` 自己位于其返回的 `AssistantRuntimeProvider` 外，不能在这里直接调用需要该 Provider 的 `useAuiState`。最少接线是复用已有 `runtime.thread.subscribe/getState`：消息 ID 序列变化时通知父层重新渲染，正文变化仍由现有消息 scope 订阅；有 pending 时继续通知身份校验。当前订阅只在 pending 时通知父层，若原样保留，会漏掉新 ID 已提交后的虚拟范围更新。无需为此新建 store、订阅总线或第二份消息数据。
2. 虚拟行 key 使用消息 ID；prepend 后索引变动不改变身份。通过 `ThreadPrimitive.MessageByIndex` 调用原 `UserMessage/AssistantMessage`，复用其原请求、附件、批注、过程、成果、菜单和授权展示，不重写气泡。
3. 包装行覆盖日期分隔与整个消息，用库的 `measureElement` 测实际高度。局部包装采用正常文档流并包住消息外边距，例如只在该包装设置 `display: flow-root`；不为测高重置全局 Markdown 或消息 CSS。
4. 上下占位及必要的内部空隙只使用虚拟项的 `start/end` 和库的总高度；占位不参与消息测高或业务消息计数。不能把保护中的离屏行直接塞进只有上下 padding 的连续布局，否则中间缺口会被错误压缩。
5. 初始估高和 overscan 是测量参数，不是固定行高。可先以约一至两屏缓冲为验证起点，实际值由快滚空白、DOM 数和延迟确定；不新增产品设置项。
6. 不在每次 token、快照或重渲染时清空测量缓存。容器宽度或字体尺寸真正改变时，保留锚点并按库接口重新测量；日期切换、图片完成和过程展开由动态测量覆盖。

整消息虚拟化是最少改动起点。若超长单条消息仍是热点，再单独评估已有 `createThreadRowsSelector/ThreadPrimitive.Row` 的 parts 级方案。该方案会触及气泡、日期、过程和操作栏边界，不能作为本阶段的顺手重构；parts 级也不会自动把一个巨大的 Markdown text part 拆小。

## 4. 一个滚动控制者，保留现有阅读语义

### 4.1 模式选择

首个隔离候选采用 TanStack 常规 `anchorTo: 'start'`、`followOnAppend: false`，不启用 end 模式的吸底。这样把库用于范围计算、动态测高与屏幕上方尺寸补偿；Homer 继续决定**是否**进行初始化、最新跳转、引用定位或 prepend 位置恢复。

不能简单使用 `anchorTo: 'end'` 再关闭 append 跟随：研究时核对的 core 3.19.11 在末项高度变化且位于末端时，仍可能执行吸底补偿。若首个候选不能满足下述契约，应停在隔离验证，不通过增加多个 scroll writer 或更改既有跟随规则来凑通过。

### 4.2 视口与写入分工

保留 `.thread-viewport`、布局、滚动条、键盘/手势事件和 `overflow-anchor: none`。以普通滚动元素接管现有 `ThreadPrimitive.Viewport` 的位置，按现有组件实际需要保留 `ViewportProvider` 上下文接线；不要同时运行 built-in viewport 的 resize/re-pin 和虚拟列表的尺寸补偿。

Homer 的明确位置操作统一调用虚拟器的 `scrollToIndex/scrollToOffset` 等公开接口；不再与库各自修改 `scrollTop`。库负责测量造成的上方偏移补偿。旧 `restoreAnchor` 不能继续在所有内容 ResizeObserver 回调中无条件写位置，否则会双重补偿。

复用 `claimPosition`、`navigation/userScroll`、epoch 和范围 token。已有 `reader.pending` 按需增加“保留阅读锚点”这一种事务即可，不另建导航协调器。实际实现以现有 pending 的 positioned 标记及受所有权保护的 RAF 等待范围测量和原生滚动回读，目标偏移按真实可滚范围校准后才消费；`preserve` 在视口不足时等待合法尺寸更新，用户操作仍能打断。不能在命令回读前取消命令，再让尺寸补偿从旧 offset 写回。

具体职责：

- **初始化/最新**：等运行时对应数据已提交、目标范围已计算且末项实际挂载/测量后，由库定位一次；成功后消费 pending。持续新消息只更新数据与“有新内容”提示，不延长跟随。
- **prepend**：请求前记录首个实际可见消息 ID 与其相对视口 top；页加入后用稳定 ID 找新索引，先经库定位使目标挂载，再依据真实消息节点校准原像素偏移。复用既有锚点字段，日期分隔高度纳入测量；不自行估算新增页总高度。
- **动态高度**：常态交给库测量补偿；只在有效位置事务内对目标做必要校准。不能对每次图片/stream 变化都重新发起“最新”命令。
- **用户打断**：wheel、touch、键盘导航、Composer 输入、换线程或新引用定位取消旧事务。迟到读取或测量不得把用户拖回原目标。

原“全部消息 DOM 已提交”条件必须拆为：数据/运行时版本身份正确，以及**本次目标**需要的行已挂载。虚拟列表永远不会同时挂载全部消息；不能简单删掉 metadata/版本校验，也不能只看总条数就消费 pending。

## 5. 自动上下加载

### 5.1 下方继续自动补齐

保留 `HistoryWindow.fillTail` 和 `tailRead` 的职责。定位旧消息或重连发现缺口时，仍依次读 after，每批最多 80 单元，直到与足够新的近期快照衔接；不因末项尚未挂载而误报“未加载”，也不以用户滚到底作为读取前提。

DOM 行离屏不得取消后台历史补齐或活跃模型 Run。取消仍按原 thread/epoch/range、断线及组件销毁处理。临时错误等待有效新快照、重连或已有主动恢复操作，永久错误保留当前数据和草稿并停止自动读取；不增加无休止轮询。网络不通或源持续失败时明确显示未补齐，不能承诺瞬时或无条件完成。

“最新消息”仍是已有的位置导航/错误恢复入口，不是下方分页按钮。正常新消息无需点击它才能获得数据。

### 5.2 上方自动读取

把既有 `loadPage('before')` 接到实际可见范围接近已加载起点的条件。只读当前 `before` 游标，复用 `pageBusy/pageRead` 与 epoch/range 校验，不新增 loader 类或查询缓存库。

- 初始化/明确定位尚未完成时，不让“初始 range 在顶部”误触发整段历史下载。
- 判断真正接近上边界，不以被焦点/选区保护的最小离屏索引作为到顶信号。
- 同一方向单飞；一次成功后可见锚点在新数组中的索引增加，自然停止预取。历史不足一屏时可继续填满视口，遇 before 为空即停止。
- 失败不能因 `pageBusy` 复位和 effect 重跑而马上重复读取同一游标。复用页 owner 记录失败触发条件，在新连接/有效更新或用户再次上滑时才允许重试；保留错误提示和草稿。
- before 与既有 after 各自使用已有请求 owner，仍核对 revision、epoch、范围和用户位置；不新增全局请求调度器，也不把慢响应无条件合入。

去掉普通“加载更早消息”按钮依赖，保留必要的顶部读取/错误状态；这一变化不新增历史 API、不修改业务提交权限。

## 6. 引用、选区、焦点及其他边界

| 场景 | 第一阶段契约 |
| --- | --- |
| 已缓存但未挂载的引用目标 | 根据消息 ID 找虚拟索引并请求挂载；不能仅因 `getElementById` 为空就再发 around |
| 未缓存目标 | 调用既有 around；目标数据提交后才虚拟定位，再等待真实节点选文/聚焦。消息不存在、修订失配或摘录不匹配保留原明确提示，不猜原文 |
| 焦点/编辑/打开的媒体 | 暂时保护仍在操作的行，不能滚出视口就让输入、放大图或播放中媒体消失。依实际必要性复用 `readingPins`，不为每行建持久状态对象 |
| 原生选区 | 保护完整选中消息跨度，不只保护两个端点；跨屏拖选、Shift 选文和复制必须真实交互验收。特别大的活动选区可以临时扩大挂载量，明确其内存代价，不能清空选区换性能 |
| 稀疏保护行 | 可用库的 range 扩展保留必要行；由库的位置数值表示中间占位，不能自行写一套高度索引。程序性消息根焦点与仍在操作的控件要区分，不能把曾经定位过的每条消息永久 pin |
| 已形成的引用/草稿 | 继续由原结构化草稿 owner 保存，不依赖被引用行一直存在。明确的新导航按既有位置所有权处理；不静默丢弃摘录、批注或编辑内容 |
| 日期/时间/附件与展开态 | 日期依据逻辑消息顺序。已存业务状态从原 owner 恢复；确需跨卸载保留的操作态按 ID 存于现有 owner，或操作期间保护行。不把全部消息组件本地状态一概搬进新 store |
| 媒体加载 | 复用 LazyMedia 的 abort、URL revoke 和版本隔离；卸载不导致旧错误污染新修订。已由用户发起的下载不能因重挂载自动再发一次 |
| 搜索 | 当前历史 API 无全文搜索。Ctrl+F 只搜索挂载 DOM，不能承诺覆盖完整历史；不通过默认全量重挂载伪装解决。若后续要求全文搜索，应按数据查 ID，再走统一定位链 |
| 键盘/无障碍 | 保留角色、时间标签、Tab/Shift+Tab、PageUp/Down 和焦点归还；加载状态可感知，新消息提示不重读整段旧内容。未挂载内容不在普通无障碍树中，库的 ARIA 支持不等于 Homer 已通过读屏验收 |
| 停止/审批/交互 | 原停止和审批 owner 不变。视觉卸载不停止 Run，不重放授权回调；重挂载读取最新业务状态，不能复活失效按钮 |

正常流布局的消息 margin、动态图片、代码块、公式、过程展开、窗口与 Composer 尺寸变化都属于测高输入。只修改虚拟行包装需要的局部样式，不借机重做字体、气泡或 Preview。

## 8. 验收方法与阶段门槛

### 8.1 先修正测试观察口径

复用 [tests/reader-scroll.test.mjs](../../tests/reader-scroll.test.mjs)、[tests/web-history-window.test.ts](../../tests/web-history-window.test.ts)、[tests/web-history-tail.browser.mjs](../../tests/web-history-tail.browser.mjs) 和 [tests/web-history-performance.browser.mjs](../../tests/web-history-performance.browser.mjs)。不新建一套 benchmark 平台。

现有专项把全部消息是否有 DOM 当完整性，以及用 `.scroll-latest.disabled` 表示成功；虚拟化后须分别记录：

- **数据完整性**：缓存的消息 ID、单元边界、去重、revision 与衔接状态；不能仅根据服务端返回成功宣称客户端已保留。
- **视图正确性**：当前挂载项身份/顺序、目标实际可见、阅读锚点偏差和焦点；DOM 数少是预期，不是漏消息。

## 9. 何时讨论上方数据淘汰

第一阶段不实现数据淘汰，也不增加回收定时器。仅当同条件实测显示 DOM 已受控但消息体、runtime 或投影缓存仍主导内存/更新成本时，再据证据决定是否裁剪上方数据。

后续候选应复用现有页/单元和 before/around 能力，按页数/字节预算管理，仅淘汰可重读、非可见/锚点/选区/编辑/媒体操作所需的旧单元及关联投影；数据库和正式消息不删除。须保留有效边界，避免把“已同步后淘汰”错当未获取缺口或让滚动位置跳变。当前 `pages` 已合并为连续范围，不能直接切消息数组几个元素就宣称分页契约正确。

如果用户停在很旧位置、下方持续完全补齐，即使上方裁剪，下方数据仍可能增长。DOM 虚拟化与上方缓存淘汰都不自动保证总内存有界；任何进一步的数据驻留策略需明确需求和验收，不在本方案第一阶段偷偷实施。

## 11. build 303 桌面渲染卡死修复（2026-11-18）

历史定位挂起时，内容观察器曾在每次 DOM 变动后立即请求重渲染。Markdown 链接在渲染时替换节点，再次触发 MutationObserver，连锁更新使滚动回读的动画帧和任务侧栏请求无法及时运行。修复后，内容观察器把同一帧内的变动合并为一次延后唤醒。已有滚动回读在等待时由它继续处理，观察器的回调也只能唤醒原定位事务。

用 build 303 前端在隔离 Electron 45 复现并捕获 JavaScript 栈，暂停落在 React 同步提交和 TanStack Virtual 的布局更新中。探针观测到 540 次观察器唤醒。单独撤掉观察器的同步更新后，同一夹具恢复。一条带链接的纯合成历史答复也能复现。

修复候选在 Node 22.22.0 通过 99 项定向离线检查及两端类型检查，隔离 Electron 完成任务侧栏读取、滚动、输入和打开设置。[历史浏览器回归](../../tests/web-history-tail.browser.mjs) 的原有三种宽度六个场景及新增的含链接启动、引用、草稿及设置场景全部通过。日常正式包的 LLDB 附加受 macOS 签名保护限制，运行实例仍是 build 303。
