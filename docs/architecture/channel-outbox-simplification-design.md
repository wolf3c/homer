# 减少渠道补读重复扫描

2026-11-18 · 后续评估，待实施。原生最终答复的第一阶段复用现有补读、发件箱和重启门禁。 [统一交付实施范围](final-answer-delivery-design.md) · [多渠道现行恢复契约](multi-channel-architecture.md#补读与外送)

渠道插件启动、收到消息提交 Hook 或发现状态变化时，会检查登记的请求及有效订阅。每次核对从头分页读取符合条件的已提交消息，按 `messageId` 去重入队。已有消息越多，日常同步需要检查的历史越多。实际时间和 I/O 开销待测。 [同步触发、补读和入队](../../src/channel-plugin.ts)

后续可评估在保存具备外送资格的用户答复时，用同一事务记录这个消息的待发事实。普通运行和重启都按待发项继续发送，沿现有 `messageId`、分片步骤及回执推进。提交 Hook 仍可用于唤醒发送。适配器继续执行发送前权限核验。已发送的步骤沿原回执去重，结果未知的步骤保留待核实状态。

主聊天和渠道发件箱目前分库存储。落地前先用合成历史对比实际扫描成本、迁移成本及订阅行为。事务方案需证明提交失败不会留下孤立待发项，重启可以续发准确版本，原请求、订阅生效先后及换绑撤权都可复用原规则。旧发件箱和历史回执用于迁移去重。确认替代路径覆盖这些场景后，再删除已被替代的历史扫描。 [订阅生效与恢复](multi-channel-architecture.md#4-事务恢复与验收)
