# Homer 如何用一张任务清单管理交办

历史提案。当前实现已采用[当前／归档](main-worker-chat-architecture.md#当前与归档)，其中退役独立归档的建议已撤回。

2026-11-20 · 优化提案，待确认。本文说明现有协作架构怎样落到工具、任务清单和工作列表。产品实现以现行架构正文为准。[主 Agent 与 Worker 会话架构](main-worker-chat-architecture.md)

## 协作关系

**用户把事情交给 Homer。Homer 对结果负责，有权在用户委托的范围内决定怎么办。** 用户只和 Homer 沟通。Homer 可以自己做，也可以创建、分派、追问、中断和续用 Worker。每个 Worker 把问题、发现、成果和失败交回 Homer。Homer 读原文、评估是否可信，决定采用、返工、换人、等一等、直接交付，或者带着具体选择找用户决定。审核可以只是读完回报后作出判断，无需再点一次“验收”。

固定的是消息归属和管理权。办理顺序由 Homer 随情况安排。一件事可以没有 Worker，可以先给用户一个有用的阶段结果，也可以在用户没有发新消息时继续推进。宿主确保真实消息能抵达 Homer；Homer 忙时沿原主队列接收，空闲时由真实输入唤起。[Worker 回报和 Main 信箱](main-worker-chat-architecture.md#worker-会话工具)

例如，Worker 回报“修复已提交，测试通过”。用户原话是“修好并提交”，Homer 看过提交和测试，可以交差并划掉这项。用户原话多了“明早再看一次错误率”，Homer 此刻可以把修复结果告诉用户，留下观察安排；要承诺自动回来，就登记实际可用的定时触发。若用户只说“帮我判断要不要修”，Homer 可能只需汇总证据并给出建议。同一个 Worker 结果，对应三种合理处置。宿主收到的都是同一类回报。

## 任务清单归 Homer 维护

清单是 Homer 跨轮记住承诺的地方。每一行回答三个问题：**用户交办了什么？现在办到哪了？接下来我还欠什么，或者最后怎样结束的？** 即时可答的事可以留在聊天。Homer 决定哪些长期事项值得登记；先建项写入目标。派工时用已有事项编号；整件交办可省略消息，有分工才写给 Worker 的具体说明。首次授权随派工绑定到当前版本。

| Homer 日常读写的内容 | 用法 |
|---|---|
| 事项与当前要求 | 标题、当前目标、用户原交办及后续变更的引用。沿用同一个事项 ID；改要求时保留前一版，迟到的回报仍能追溯。 |
| 工作笔记 | 一段可更新的文字，按需写决定、缺口、下一步、观察条件或结论。允许留空，不要求每轮交表，不解析这段文字来调度。 |
| 办理状态 | **在办、暂停、结束。** Homer 主动改表。等回复、等明早、已交付阶段结果，都可以是“在办”。“暂停”表示确实要收住执行；单个 Worker 停止只影响该 Worker。 |
| 结束结果 | Homer 划掉事项时顺手记下成功、部分完成、失败或取消，以及用户需要知道的结论。四个值用于回看历史。已存在的正式回复、原文和附件可引用，避免再写一份成果。 |

Worker 的原会话、审批、发送及送达回执留在各自的记录中，Homer 需要时可查。一张任务清单指的是 Homer 的管理界面；技术上，可靠投递、授权和执行恢复仍由各自的记录负责。

**办完后的默认动作很小。** Homer 决定交差，就面向用户答复，并用已有的事项更新能力写下结果。正常情况下二者在同一轮办理。宿主可以在保存该轮答复时，一并落下 Homer 明确指定的清单更新，避免应用退出后只保存一半。这是一次明确决定的写入保证。单独发送阶段答复、内部协调后安静结束本轮、引用此前已提交的回复来结束事项，也都是合法行为。[主会话交付](final-answer-delivery-design.md)

若 Homer 忘记更新，清单确实可能滞后。让 Homer 在接办、续办和答复这件事时容易读到原要求、自己的笔记及最新回报，并能当场修正。删除上一稿提出的“检测漏判、排队补问、判断是否有合格下一步”机制。一次漏记首先是 Homer 的管理质量问题；要用真实任务检查它是否善用清单，无需为此添加巡检模型轮或要求用户补说“结案”。

## 代码从哪里减

现行实现已有正确的骨架：宿主把 Worker 原文送到 Main，Main 可以沿原会话追问，也能直接向用户交付。优先削减的是围绕清单的一圈重复动作。

| 实现入口及现况 | 建议改动 |
|---|---|
| [事项工具](../../src/recursive-tools.ts)允许 Main 更新清单、管理 Worker，另有独立归档和恢复可见工具 | 保留建项、更新、查询和原有 Worker 会话管理。结束是一次清单更新。退役日常的归档／恢复可见工具及旧工具表兼容要求。查询历史直接读原事项。 |
| [事项实现](../../src/recursive-tasks.ts)中，结案、归档分别写入；归档另查 Worker、处理轮、回报、附件等多种证据 | 移除归档状态及专属完成证据查询。Homer 判断证据是否足以交差。宿主继续校验操作是否属于当前事项和版本，保护正在执行的动作；仍在运行、尚未确认停止及未知外发的事实必须能回到 Homer 处理。 |
| [工作总览](../../src/task-overview.ts)与[状态展示](../../src/task-status.ts)组合 Run、审批、回报及清单状态，默认可能显示“未结案” | 列表先读 Homer 的清单，再叠加对用户有用的独立事实。普通行以事项名为主；需你批准、需你回答、明确暂停、停止或送达待核实用文字说明。有在途执行可显示活动图标。删除“未结案”兜底和图标旁重复的普通过程文字。 |
| [交付及定时结果](../../src/service.ts)与[渠道投递](../../src/channel-plugin.ts)已有各自的消息、文件和权限依据；部分入口仍读取事项可见性 | 展示从“在办／暂停”读取，结束默认收起，用户明确要求留在清单则保留。历史详情直接打开；Homer 按用户新委托恢复原事项。文件读取、定时执行和外送各自检查原授权及准确身份；工作列表的显隐不承担权限职责。 |
| 实际归档会产生事件，唤起资源复核轮 | 随独立归档一起退役这条默认链路。执行器的退出仍由宿主确认；任务自建资源由 Worker 和 Homer 在办理中按授权处理。确有清理需求时，Homer 可以继续办或另作安排。保留的成果、共享资源和归属未知的文件不因清单收起而删除。[现有归档复核职责](../task-archive-housekeeping.md) |

**执行可靠性有独立价值。** “这项业务是否办妥”由 Homer 判断；“原 Worker 是否已退出”“这条消息有没有保存”“外部发送结果能否确认”由宿主如实报告。例如用户要求停止时，宿主必须冻结相关新执行、核实原执行退出，才能报告已停；发送后断线时保留未知，不擅自重发。Homer 拿到这些事实后决定如何解释、补救或继续。确认停止的实现值得保留，其状态不需要再复制成一套管理流程。

## 实施与验收

先沿现有 Main 入口打通“读清单、看原文、管理 Worker、记结论、答复用户”，再移除归档字段、工具、事件及其消费者，最后统一工作列表和历史查询。允许直接采用新工具表和新资料格式，用独立新资料验证，旧实例可留给原版本查阅。若现有表足以表达上述内容，就沿用；数据格式变更只服务确实删掉的职责。

验收重点是 Homer 面对不同委托能作出不同的合理决策。用隔离的真实 Main 对照“修复并提交”“提交后继续观察”“只评估是否值得修”，给它相同的 Worker 回报；再给它一份证据不足的回报，观察它是否读原文、追问或如实说明。看它是否履行用户承诺、清单是否准确、用户是否只需在真正有决定要作时介入。允许不同的工具顺序和 Worker 数量。

宿主用离线测试验证另一类问题：回报交回正确的 Homer 和事项；并行 Worker 的一轮结束不会误改整项；旧版回报不会覆盖新要求；停止、审批、文件和外送失败保留原事实；已确认的动作重启后不会重复；清单更新与同轮交付中断时可按原记录恢复。界面验证在办、待答、暂停、未知和历史都能找到，普通成功事项收起，已结束但明确保留的仍然可见。

本提案只调整设计。真实模型的管理表现和宿主行为都需要在实施后验收。
