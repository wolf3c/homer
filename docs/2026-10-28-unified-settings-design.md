## 目标与范围

在现有设置页中管理本机权限、微信和 Telegram。复用 `ui/desktop-permissions.tsx` 的 `DesktopSettings`、既有原生菜单入口和 Base UI 组件，不增加第二套设置壳，不改变会话布局。

本轮获准在隔离工作树实施设置 UI：复用现有设置壳和同源接口，保留此前恢复候选与其他 dirty 工作。保留全部历史；不重放旧消息、不真实发送、不恢复真实收发、不读取凭据，不调用真实渠道、钥匙串或系统权限接口。

本稿替代 2026-10-27 接线计划中有关入口、页面组合、状态显示、关闭与长等待的决定。旧计划中的同源请求、服务端凭据保存、精确本人批准、错误白名单和超时边界继续作为后续接线约束；旧计划中的自动提交/合入授权不在本轮生效。旧成果保留原样，不覆盖其证据。

## 设计阶段事实与实施前提（实施前记录）

- 当前主工作区已有 `DesktopSettings`：齿轮入口、一个 Base UI Dialog、“本机权限”面板，以及 `homerDesktopSettings.onOpen` 原生菜单接线。渠道接入应扩充这个 owner，不新增 `SettingsDialog`。
- `ui/homer-app.tsx` 仍同时挂载 `WechatConnection` 和 `DesktopSettings`。后续迁入后，移除微信专用入口和独立弹窗，工作状态、预览、会话及草稿 owner 保持。
- `scripts/desktop-runtime.mjs` 的采用路径设置 `pauseOldDesktopWork:true`；当前 `src/dev-host.ts` 会跳过渠道对象创建/恢复，管理调用可能返回 `web_method_denied`。因此旧计划“后端已足够、仅改 UI”的结论已失效。
- 现有授权、连接和收发启动可能耦合。不能靠改按钮文案把同一个 API 当作“只授权”；必须先核实真实调用语义。管理状态读取与收发启动需要明确边界，具体后端修订另行评估，不在本轮开发。
- 无法确认远端积压、游标和服务端新旧消息边界时，继续暂停。设置迁移不能关闭 `pauseOldDesktopWork`，不能通过重扫、重绑或普通“恢复”绕过这一限制。

## 状态与动作

配置事实与当前收发状态分开，来源仅为当前有效的管理回执。请求失败不能覆盖成未配置；历史缓存若展示，必须标“上次状态”，且不能据此启用变更动作。

| 状态/事实 | 主要文案与呈现 | 允许的下一步 |
|---|---|---|
| 首次读取中 | 正在读取连接状态 | 可离开，不展示未连接空态 |
| 管理不可用、读取失败、未知值 | 状态暂不可用；无法确认当前连接，请重新检查 | 重新检查；禁用授权、恢复、解绑等变更，不能建议重绑 |
| 已确认无配置/无绑定 | 尚未授权 / 尚未配置 Bot | 展示对应授权或配置流程；是否能执行仍取决于服务端实际能力 |
| 已保存配置、尚未绑定 | 配置已保存，待绑定本人 | 只展示当前配对步骤；不称“收发可用” |
| 已绑定、明确暂停 | 收发已暂停；绑定已保留 | 安全条件确认后才提供恢复；暂停本身不代表积压已处理 |
| 已绑定、安全边界未确认 | 收发已暂停；新旧消息边界尚未确认 | 继续暂停；恢复按钮禁用并就地解释原因，不提供强制开启 |
| 当前回执明确在线且准许收发 | 收发已开启 | 暂停收发；绑定详情与异常消息按需展示 |
| 保存/变更回执超时 | 结果未确认；操作可能已生效，请先检查当前状态 | 重新检查，不自动重发；不能显示保存成功 |
| 凭据失效或冲突 | 明确白名单原因和可执行下一步 | 不自动删除 webhook、抢占消费者、覆盖账号或清理绑定 |

`configured`、`bound`、`enabled` 和实际在线分别解释。单个绿色勾或 HTTP 成功不证明所有条件成立。`uncertain/failed` 消息只在存在时显示简短提示；不新增“重发旧消息”动作，不展示原始内容、内部日志或服务商正文。

状态应根据现有明确返回值映射；如果缺少安全边界或管理能力信息，就保持未知/暂停，不由前端推断可恢复。本稿不虚构现有接口已提供新字段。

## 微信面板

标题“微信”，说明“使用微信继续同一个主对话”。一个状态区，一个当前动作区；移除重复的“连接账号 / 尚未连接 / 未连接”大空态卡。

1. 读取不到状态：只显示状态不可用与“重新检查”，不生成二维码。
2. 已确认未绑定且操作能力允许：主按钮“扫码授权”。二维码仅在用户点击后生成，使用服务端短期同源图片；等待扫码、手机确认、验证码、过期依次呈现，不把“已扫码”当成功。
3. 授权确认后重新读取完整状态，再分别显示绑定与收发事实；不以登录 confirmed 直接宣布收发已开启。当前服务端若不能在安全暂停条件下完成授权，就暂不允许该动作，不能重命名后照常调用。
4. 已绑定且暂停：显示“绑定已保留”，常规动作叫“恢复收发”；新旧边界未确认时禁用，并显示“新旧消息边界尚未确认，继续暂停”。不展示虚构的微信账号名称或本人 ID。
5. 已明确开启：提供“暂停收发”，无需危险确认。暂停成功仅以真实回执为准，不取消后台工作。
6. “解除绑定”作为次要危险操作，单独确认，说明将清理绑定凭据、需要重新授权，以及不取消已派发工作。后续必须验证全部历史与必要解密资料仍保留；核实前解除/删除动作不可执行，也不能建议先解绑再重连。不能只证明聊天记录未删除就声称全部可恢复。

保留真实状态拼写、账号不一致拒绝、验证码限制、二维码失效和图片失败处理。关闭扫码面板只停止前端轮询，不宣称已撤销服务端登录；重新打开读取仍有效的状态。

## Telegram 面板

标题“Telegram”，说明“配置专用 Bot，绑定你的 Telegram 账号”。仅展开当前步骤，已完成步骤显示简短摘要和明确的重新配置入口，不把三份表单同时铺开。

1. **配置 Bot。** 指引在 Telegram 中找到官方 BotFather 创建专用 Bot；不新增不可信外链。Token 密码输入、可手动显隐，提示“请勿发送到聊天中”。按钮“验证并保存”；开始提交即清空秘密，失败后明确“Token 输入已清空，请重新输入”。保存成功不代表绑定或在线；允许同一 Bot 更新 Token，换 Bot 继续沿明确解绑约束。
2. **绑定本人。** 解释下一步在 Bot 私聊发送一次性 `/start …`，然后返回。沿实际现有 configure/connect/pair/candidate/approve 契约接线，不合并安全批准，也不伪造独立的“只配对连接”。如果 connect 会恢复旧收发且无法隔离，则配对入口同样保持暂停，先解决前置条件。状态演示可展示未来允许配对时的等待和候选状态，不表示当前真实服务已具备该能力。
3. **核对并批准。** 展示后端返回的 userId、chatId 与真实剩余有效期；说明“仅批准你刚刚在此 Bot 私聊发起的配对。如不确定，请勿批准，重新发起本人配对。”数字 ID 不能单独证明本人；没有可独立核对的身份信息时明确限制，不伪造昵称或安全勾。保留“不是我，重新配对”与“确认是我并绑定”，不自动批准候选。重新配对先清前端候选；服务端旧码撤销能力仍按实际契约，不能仅凭前端隐藏声称已失效。
4. **绑定后。** 显示当前收发状态，“暂停收发 / 恢复收发”与微信同名。安全边界未确认时继续暂停；“解除绑定并删除凭据”另置次要危险区并明确确认。

不自动复制 Token、验证码或配对码，不增加剪贴板权限或深链接接口。配对指令展示在可选择的代码文本中，步骤说明优先于额外功能。关闭页面不撤销服务器已生成的配对码，按服务端 TTL 失效。

## 长等待、关闭与确认

- 短暂提交只禁用同一渠道的重复变更；允许关闭、返回和切到本机权限/另一渠道，不把整个设置锁住 95 秒。离开只停止当前页面轮询与清理秘密，不作为服务端取消。重新进入读取状态；不能因为卸载组件解除服务端重复提交保护。
- 沿现有配置 95 秒、一般 POST 40 秒、GET 8 秒及微信 poll 长等待边界；前端超时不证明服务端失败。变更在途或结果未确认时，重新进入仍禁止盲目重试；现有回执机制若不足以识别该操作，先设计最小核对策略，不能新增一个布尔 busy 副本当作可靠事实。
- 同一 Bot 的 Token 更新即使读到 `configured:true`，也不能证明本次更新成功。缺乏准确回执时持续“结果未确认”，不建议重复保存。
- 所有读取、poll、变更与 finally 具有本次打开/请求身份检查；晚响应不能改新面板、错误提示或 busy。关闭清理计时器，不撤销已落库事实。
- 未提交 Token/验证码在关闭和切换时一次确认：“丢弃当前输入？”；按钮“取消 / 丢弃并继续”，取消默认获焦。未提交输入与已发起服务端操作分开说明。
- 暂停收发为可逆普通操作，无危险确认。解除绑定/删除凭据明确确认，按钮“取消 / 解除绑定”（Telegram 为“解除并删除”），取消默认获焦。未提交输入遇到危险动作先用同一个确认说明输入会清空，不连续弹两个确认框。
- Escape、遮罩、关闭和返回走同一入口。关闭回到齿轮；取消确认回到发起按钮。原生菜单仍打开同一个 Dialog；会话树、草稿与阅读位置不重挂。

## 本地实施与验证（2026-10-28）

- 顶栏仅保留原设置齿轮；扩充原 `DesktopSettings` 的 Dialog、Tabs 和原生菜单入口，默认本机权限。微信成为内嵌面板，Telegram 采用配置/配对/绑定的当前步骤。复用 Base UI 和已有样式变量，无新增依赖、路由或设置框架。旧 Telegram 独立页面保留兼容，本次未修改其业务逻辑。
- `ui/channel-settings.ts` 集中同源请求、白名单错误、读取身份与变更去重。GET 在途去重，变更淘汰晚读取。配置 95 秒、POST 40 秒、GET 8 秒，超时包含响应体；无自动变更重试。
- 为防会话切换重挂或页面刷新解除未知操作保护，只在 sessionStorage 保存每个渠道的非秘密 `pending` 标记，不含 Token、账号、请求体或结果。发送前先记录，准确回执/明确失败后清除；存储不可用时不发变更。残留 pending 按结果未确认处理；普通 GET 和 `configured:true` 不能清除锁。该标记只覆盖本浏览器会话；跨客户端准确核对仍需服务端操作回执，当前不提供盲目重试入口。
- Token/验证码仍只在组件内存中，提交即清空；未提交输入离开时统一确认，取消默认获焦。渠道变更在途可切页/关闭，不解锁重复提交。恢复、扫码及会启动收发的配对均要求当前 recovery 明确允许；缺少时间边界证据继续暂停，解绑/删除因历史保留未核验保持禁用。本轮不改变宿主暂停开关或后端恢复候选。
