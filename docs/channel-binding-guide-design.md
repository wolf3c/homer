# 渠道绑定后的身份与设置引导

2026-11-20 整理。微信实验完成于 2026-11-18。三渠道绑定引导均为待评审设计，尚未接入产品。[现行多渠道架构](architecture/multi-channel-architecture.md)

## 1. 结论与建议

建议只向**新绑定的授权私聊**发送一组引导。先让用户知道“这是荷马 Homer”，再说明如何在该渠道辨认或设置它。头像可用时随说明发送。绑定成功后何时发，由各渠道实际具备的发送条件决定。

| 渠道 | 建议首次发送的时机 | 用户收到什么 | 验证状态 |
| --- | --- | --- | --- |
| 微信 | 维持连接，等绑定本人发来第一条通过身份核验的文字并取得该私聊的 `context_token`。扫码完成时，桌面先提示用户发一句话。 | 身份说明、设置备注名和头像的指引，以及可用的头像图片。首条用户文字照常交给 Main。 | 在同一隔离绑定上，无 token 时用户未看到测试文字；取得 token 后，用户确认看到了文字和头像。 |
| Telegram | Homer 确认私聊配对、运行时应用成功且 Bot 连接就绪后即可发送。 | 身份说明和可用的头像图片。管理该 Bot 的用户可按 BotFather 指引修改资料。 | 引导及其显示效果待实测。 |
| 钉钉 | Homer 确认配对、运行时应用成功且同一 Stream 连接就绪后，只发给已核验的员工。 | 身份说明和可用的头像文件；需要修改机器人资料时联系管理员。 | 引导、文件显示及设置流程待实测。 |

一次引导按绑定记录文字和头像各自的发送结果。已有绑定升级、重启或同身份重新授权时不补发；解绑后重新配对才产生新绑定。头像在发送前确认不可用时，可按渠道降级为文件或省略。任一步骤已尝试且明确失败或结果未知时，停止后续发送。用户仍可继续正常对话。引导使用固定文案，远端资料由用户或管理员自行设置。

## 2. 微信对照的事实与边界

2026-11-18，使用用户扫码授权的隔离绑定；不修改日常渠道配置。可见性依据用户逐项确认，接口响应与实际显示分开记录。

| 条件 | 接口事实 | 用户观察 |
| --- | --- | --- |
| 刚授权、无 token、未启动持续连接：初次文字与图片 | HTTP 200；早期脚本仅保存消息 ID 字段存在性 | 均未见，顶部显示暂无法连接 OpenClaw |
| 同一绑定启动持续连接，无 token：新文字 A | HTTP 200，返回消息 ID | 顶部提示消失后，A 仍未显示 |
| 用户发送指定测试文字，取得其 token：新文字 B | HTTP 200，返回消息 ID | B 实际收到 |
| 同一连接，携带该 token：新头像 C | CDN 上传及发送均 HTTP 200，返回消息 ID | 深蓝底荷马头像实际可见 |

初次前台连接曾退出。第二至四行均在恢复持续连接后进行。对照结束后专用进程已停止，`notifyStop` 返回 `ret:0`。隔离凭据、二维码和实验脚本已在实验结束时清理。

**微信的产品取舍是等待第一条合法入站文字。** 同一绑定在线时，无 token 的文字 A、有 token 的文字 B 和头像 C 都取得了 HTTP 200 和消息 ID，用户只看到了 B 和 C。因此，判断用户看见了什么，应以客户端观察为准。B、C 之前用户主动发过消息，这也可能改变服务端状态。此次对照能支持上述发送时机，无法单独确定 token 的因果作用、有效期或其他环境的行为。

腾讯固定版源码允许无 token 构造发送请求；协议同时明确这不保证服务端接受。正常启动包括 `notifyStart` 和持续 `getUpdates`，公开材料没有说明微信顶部提示的精确判定规则。[协议](https://github.com/Tencent/openclaw-weixin/blob/874637a0dbc24050f72d1385add4fc6170a2d726/docs/protocol_zh_CN.md) · [发送构造](https://github.com/Tencent/openclaw-weixin/blob/874637a0dbc24050f72d1385add4fc6170a2d726/src/messaging/send.ts) · [生命周期](https://github.com/Tencent/openclaw-weixin/blob/874637a0dbc24050f72d1385add4fc6170a2d726/src/channel.ts)

## 3. 方案取舍

以下为本次建议，不表示用户已经选定具体实现。

| 做法 | 代价与取舍 |
| --- | --- |
| 每个适配器自行欢迎、保存状态 | 首个渠道代码少，但各自处理重启、半组成功、未知回执及解绑竞态，难以保持一致 |
| 创建核心消息并走业务发件箱 | 可复用业务消息读取，但现有路由必须有真实请求或订阅；为连接指引增加虚构请求、事项或特殊核心消息，不合当前边界 |
| **建议：绑定上保存最少状态，插件统一调度，适配器可选提供就绪内容** | 增加一个绑定内状态和小的可选接点，复用现有连接生命周期及发送结果，核心业务模型保持不变 |

现有 `channel_outbox` 有请求／订阅二选一约束，并通过 `readCommittedMessage` 核验正文。因此不直接塞入伪造 `messageId`，也不扩大发件箱业务路由。本能力是渠道插件内部的连接服务内容，不是核心已提交业务消息；这条例外必须在渠道架构中显式说明。[现有插件](../src/channel-plugin.ts)

## 4. 最少接入契约

适配器只增加一个可选的准备接点，概念上为 `prepareBindingGuide(address)`。它不发送、不落库、不改远端资料：

- 未实现接点：该适配器不参加，原行为保持。
- 返回未就绪：保留待发送状态，等待原连接／授权事件；不发探测消息，不为引导启动第二连接或定时器。
- 返回可发送内容：给出该渠道的简短设置说明及头像可用形式（图片、普通文件或省略）。插件加上统一身份文案和已有品牌资产，冻结这组内容，再按原发送通道处理。

准备接点、现有 `connectionState` 共用相同的账号事实；前者提供内容，后者继续解释「待首条消息／暂时离线／需重新授权」，不另建一套健康状态。适配器重连就绪、可信首条入站、管理应用完成时唤醒原插件同步；无法取得就绪条件时不猜测可发。

插件负责授权绑定与私聊地址、一次性状态、串行发送和回执。适配器负责就绪判断、渠道设置知识、图片／文件编码与平台响应分类。新增渠道实现这个可选接点及已有发送契约即可；不要求其他渠道一起升级。

发送层抽取或复用以 `address / part / attemptId` 为输入的单步传输。核心 `messageId`、请求／订阅校验仍在业务发件路径；连接引导使用绑定内步骤定位，不伪装成核心消息。为引导增加图片呈现方式时，只对显式要求的可信头像启用，不把所有业务图片附件自动改为图片消息。

统一名称建议为「荷马 Homer」，头像复用[社交方形资源](../assets/branding/homer-social/homer-x-avatar.png)，用途见[品牌资源入口](../assets/branding/README.md)。不从微信 `wx-…` 或 Telegram 用户名推导品牌名称，不新增可编辑身份、头像副本或配置表。

## 5. 绑定内状态与可靠性

建议在已有 `channel_bindings` 上增加一个可空的引导状态字段，包含待发状态、冻结内容、当前步骤及该步骤的发送尝试／回执。不是新表或独立消息实体。只存短文案、头像资源引用和摘要，不复制品牌文件，不在此保存凭据、私聊内容或 token。

| 状态 | 行为 |
| --- | --- |
| 空值 | 已有绑定、未接入能力或不应自动引导；不在启动时回填 |
| pending | 已获准的新绑定，尚未取得可发送内容；暂停、离线或等待首条消息都停在此处 |
| queued | 内容已冻结，尚未尝试当前步骤；可在重启后恢复 |
| sending | 网络动作前持久认领，保存唯一尝试标识；同一绑定串行发送 |
| sent | 所有实际选定步骤取得渠道成功回执；不等于用户已读或完成设置 |
| failed / unknown | 明确失败／结果未知，停止后续步骤，不自动重试 |

新绑定记录与 pending 意图在同一插件事务内提交。实际发送须等配置与运行时均应用成功，不能只凭二维码 confirmed、文件保存完成或界面显示成功。已有 `reconfigure` 的暂停、连接停稳、发送等待及退出取消也覆盖引导；事务里不做网络调用。

每个步骤在网络前写入 sending，成功回执落库后才推进。文字已成功而头像发送中断，只保留头像的未知状态，不重发文字。进程恢复时遗留 sending 转 unknown；客户端 ID 不被当作平台幂等保证。回执落库失败也按未知处理。明确失败首期同样不自动重投，用户仍可在绑定详情查看名称、头像和设置指引，不增加「重发」操作。

发送每步前重新核对原绑定仍有效、同一授权目标和发送前提；解绑后未发内容取消，已经发出的网络效果不能撤回。不得沿账号名把旧步骤投到新绑定。模板或头像更新不触发补发；冻结后的资源若缺失或摘要改变，不静默换一张图继续发送，可省略尚未开始的可选头像并保留可查原因。已经尝试过的图片效果未知时不做降级补发。

缺图、不支持图片或超过限制，在冻结前优先选择可发送的普通文件；文件也不可用则只发送文字，不称「头像已发出」。这不算发送失败。冻结后未产生网络效果的资源缺失可省略，但实际平台拒绝或网络异常沿 failed／unknown，不自动换形式再投。

引导文字优先排在首次普通回复之前；最多等待当前一步的既有发送时限，不长期阻塞用户业务。图片是可选步骤，不以它的结果决定是否接受用户输入。绑定详情复用现有发送情况位置，单列「连接引导发送失败／结果待确认」，不能沿用「消息仍在荷马会话」的文案，因为引导没有核心会话消息。

## 6. 新旧绑定与渠道差异

升级时所有已有插件绑定置空；对已经存在于账号配置、但尚未生成插件绑定的账号，也按已有入口处理。首次迁移必须在受理绑定管理前，以同一运行锁和插件事务完成新增列及全部已有配置的绑定核对，旧配置对应的引导保持空值；中断则整笔回滚。以该字段的迁移完成事实区分升级基线，不新增迁移业务表或额外配置标记。

基线完成后，可信配置核对实际创建的新绑定，在同一绑定事务登记 pending。这样即使新账号配置已保存、进程在运行时应用前退出，下次启动仍可恢复新增绑定与引导意图，不依赖易丢失的管理回调。配置未变不创建新绑定，重复管理、保存后应用重试及睡眠唤醒不重新登记。

换密钥或同身份重新授权保留绑定及其引导状态；解绑后重新绑定产生新 ID，可以发送新的一组。将来某渠道新增此能力也不追溯旧绑定。CLI 绑定写配置前同样先完成升级基线，随后复用配置核对与绑定事务；显式编辑可信配置增加账号沿相同规则处理。不往账号 JSON 存第二份待发状态，也不在启动时根据账号数量或文件时间猜测新旧。迁移的事务包装应复用绑定核对内部同步步骤，避免嵌套 `BEGIN`。

| 渠道 | 可发送条件及最小接法 | 设置边界 |
| --- | --- | --- |
| 微信 | 正常连接且持有已核验本人文字入站取得的 token 后准备内容；扫码后未就绪，沿现有 setup 提示先发一句话；当前产品仍只接受文字入站，不扩大到媒体收件 | 用户手动在「更多」页修改头像、备注名；截图确认两入口存在，具体文件选择及各版本行为未验，不自动修改 |
| Telegram | Bot 身份、私聊配对和用户确认完成，运行时应用成功后准备内容；只发原绑定私聊，不广播到群或话题 | BotFather 的 `/setname`、`/setuserpic` 需 Bot 管理者；配对用户不一定是管理者；用户名与显示名称不同 |
| 钉钉 | 配对确认、运行时应用成功且同一 Stream 连接就绪后准备；主动发送只选已绑定的一名员工；头像复用普通文件上传 | 首期只作身份说明，需改机器人资料时联系管理员；不假设配对者具有管理权限 |

微信图片发送需补产品的 `media_type=1 / image_item`；当前普通附件仍走文件通道。Telegram 同理需补显式图片发送或选择文件降级，当前附件为 `sendDocument`。本次隔离微信图片实测不代表这些产品路径已实施。

Telegram 官方也提供 `setMyName`、`setMyProfilePhoto`，所以不宣称不能自动设置；本方案选择手动指引，避免顺带覆盖远端 Bot 资料。[BotFather 设置](https://core.telegram.org/bots/features#editing-settings) · [名称 API](https://core.telegram.org/bots/api#setmyname) · [头像 API](https://core.telegram.org/bots/api#setmyprofilephoto)

## 7. 用户文案

绑定完成但微信尚无 token，沿现有状态显示：

> 微信已绑定。请在微信 ClawBot 私聊发一句话，荷马会在这里发送身份和设置指引。

微信首次可发送时：

> 你好，我是荷马 Homer，以后可以在这里找我。
>
> 为了更容易认出我，请打开这个会话的「更多」页面，将「备注名」改为「荷马 Homer」，并在「头像」中使用我发来的图片。

图片省略时，去掉「我发来的图片」，改为「你可以在头像设置中选择自己容易识别的图片」。具体保存、相册与文件选择步骤待客户端核验，不提前写死；置顶不是完成引导的必需步骤。

Telegram：

> 你好，我是荷马 Homer，以后可以在这里找我。
>
> 如果这个 Bot 由你管理，可以打开 @BotFather，用 `/setname` 将名称改为「荷马 Homer」，再用 `/setuserpic` 上传我发来的头像，方便以后找到我。

未附图时删去头像上传句。后续渠道不提供设置说明时，保留首句和可用头像即可；身份说明不要求用户修改个人账号的姓名或头像。

## 8. 最小验证与落点

实施前仍需评审，以下是必要验收范围，不是已通过的测试。

| 层级 | 最小检查 |
| --- | --- |
| 插件离线 | 未接入适配器行为不变；新绑定只登记一次；旧配置首次核对、升级、重启、睡眠及重新授权均不补发；解绑重绑不串目标 |
| 状态与故障 | 保存／应用失败不发；待就绪不请求发送；每步发送前认领；文字成功图片失败不重发文字；遗留 sending、回执落库失败及超时均停在未知；解绑晚到回执不能恢复旧绑定 |
| 渠道协议替身 | 微信无 token 等待、收到合法本人文字后准备；Telegram 配对确认前不发且不发群；头像图片／文件／省略降级；稳定资源引用和字节；平台拒绝与未知不自动换形式发送 |
| 真实组件 | setup 提示、连接引导失败／未知及无图文案；查看本地指引不触发网络；原首条业务输入与普通回复仍可用 |
| 实网专项 | 实施完成后另获专项授权，逐渠道验证绑定、实际文字与头像显示、手动设置路径、重启不重复；接口成功不能替代手机确认 |

实现接点：`DesktopChannels` 的新增绑定保存与运行时应用、`ChannelPlugin` 的绑定事务／同步泵／停止恢复、各 `ChannelAdapter` 的可选准备和现有单步发送、已有绑定详情组件。三个现有适配器的接入步骤见第 9 节；后续适配器仍可不实现，不增加核心模型工具。

设计所属边界见[多渠道架构的绑定引导一节](architecture/multi-channel-architecture.md#绑定后的身份与设置引导建议未实施)。早期实现记录见[个人微信接入](11-wechat-integration.md)。

## 9. 三个现有渠道的最小实施步骤

源码确认的三个聊天应用适配器为 `WechatChannel`、`TelegramChannel`、`DingtalkChannel`，由 [dev-host.ts](../src/dev-host.ts) 和 [cli.ts](../src/cli.ts)装载。[多渠道架构的接入纲要](architecture/multi-channel-architecture.md#适配器接入纲要)是统一入口；`08-telegram-integration-plan.md`、`11-wechat-integration.md` 是历史方案，`2026-11-13-live-channels.md` 只覆盖即时重配，不是第二套接入规范。

### 9.1 三渠道共用部分先完成一次

1. 在现有 `channel_bindings` 增加一个引导字段，按第 6 节完成旧配置基线；`bind / configureBindings` 在同一事务创建新绑定及 pending。保持原 `bindingId` 作为唯一归属，不另建引导 ID、批次、实体表或配置文件。
2. 在 `ChannelAdapter` 增加第 4 节的一个可选准备方法。统一身份与头像从现有品牌资源取得；返回值只需短设置说明、头像呈现方式或未就绪。不增加每渠道的 welcome 服务、发送重试器、能力列表或资源生成器。
3. 在现有同步泵检查 pending，准备并冻结文字／可选头像，沿同一暂停及停止机制逐步认领与发送。由插件给现有连接传入一个可选的泵唤醒回调，微信合法入站、Telegram 身份核验及钉钉 Stream ready 后调用；不建事件总线、新增长轮询或另一个计时器。不能只在绑定时唤醒一次，否则异步就绪后可能一直待发。
4. 三个发送方法目前均只使用 `address / part / attemptId` 及 Telegram 群参数，核心 `messageId` 留在插件。将公共传输参数收窄到这些实际字段，业务路径继续自行核验消息；引导不填伪造核心 ID。
5. 头像沿现有附件字节结构，只增加一个显式的图片呈现提示即可。微信／Telegram 实现该提示，钉钉先走原文件分支；未标记的普通业务附件保持原语义。打包只纳入既有一份社交头像，核对字节、摘要和平台限制，不复制新母源。

以上只增加一个持久绑定字段、一个可选适配器方法和必要的图片呈现提示；方法名及字段形状须在实施前类型检查时定稿，不建立通用富媒体框架。状态转移、文案组装、品牌读取和失败展示共用，适配器仅处理实际协议差异。

### 9.2 微信：首次合法文字后发送文字和图片

**当前源码。** [DesktopChannels.authorizeWechat](../src/desktop-channels.ts)在二维码 confirmed 并校验身份后直接提交，不经过 Telegram／钉钉的二次确认页；凭据保存与运行时应用仍由 `commit / reconfigure` 协调。[WechatChannel](../src/wechat-channel.ts)的 `inbound` 只接受本次绑定之后、本人发给同一 Bot 的非空纯文字及合法 token；`connect` 先保存最新 token 再接收业务文字；`connectionState` 无 token 返回 setup，`send` 无 token 直接 failed。

**最小改动顺序。**

1. 新绑定先记录 pending；不在二维码回调中直接发送。应用后原 `connect` 正常轮询，无 token 时保持 setup 和第 7 节提示。
2. 复用入站身份核验及 `persist`，成功取得 token 后唤醒引导；不消费该业务输入，不从任意其他事件、旧扫码数据或其他账号借 token，不新增「获取 token」请求。
3. 准备微信设置文字与图片提示。文字仍走现有 `send`；在 [WechatIlink.file](../src/wechat-ilink.ts)附近仅提取已有加密／上传共用步骤，图片选择 `media_type=1` 并构造 `image_item`，保留普通文件 `media_type=3 / file_item` 分支。每步使用原绑定当前 token，不把 token 冻结进引导字段。
4. 接口回执沿现有 `WechatIlink.send` 校验：明确非零错误为 failed，缺少有效成功证据或网络效果未知为 unknown。收件、文件回复与长文字原行为不变。

**降级与风险。** 本头像的大小符合测试条件；产品仍需校验内置资源可读及大小限制。准备时不能发图片则选原文件形式，文件也不可用只发文字并调整文案；图片尝试之后失败不补发文件。token 失效或重新授权时按原账号状态等待／失败，不能因引导自动扫码。实验使用过 `notifyStart / notifyStop`，并未证明它们是显示的必要条件；本需求复用产品原 `connect`，不顺带建立第二生命周期。

**去重与兼容。** 只使用共用绑定字段；同身份重授权不欢迎，解绑重绑才新建意图。微信整表配置写回与即时重配继续遵守原停稳窗口，不另改 `wechat.json` 存引导。不得扩大媒体入站范围来完成本功能。

**最小验收。** 在现有 [wechat-channel.test.ts](../tests/wechat-channel.test.ts)增加：扫码后零发送；假／陌生／过期文字不能触发；合法本人文字触发一次且仍提交业务；发送携带同账号 token；图片上传类型、加密字节、`image_item` 和回执；文字成功图片未知时重启不重发。共用迁移／解绑测试不复制一套。**已验证仅为第 2 节隔离实测；产品引导、设置具体操作、打包后图片与各平台仍待实施和专项。**

### 9.3 Telegram：私聊配对确认后发送文字和图片

**当前源码。** [verifyTelegramBot / pairTelegramBot](../src/telegram-channel.ts)核对 Bot 身份、Webhook 冲突、一次性 `/start`、非 Bot 私聊发起者和普通私聊地址；[DesktopChannels.authorizeTelegram / confirm / commit](../src/desktop-channels.ts)再经用户确认保存并应用。原 `send` 已支持文字和 `sendDocument`，没有图片消息分支。

1. 新 Bot 配对并在 Homer 确认后，由共用绑定事务登记 pending；身份核验通过、同一账号连接 ready 且运行时应用成功才准备，不等用户再发第二条消息。准备接点同时核对原私聊地址，不能把群接入完成当作新绑定。
2. 使用第 7 节固定文字；Bot 的 `username` 只作渠道身份标签，不覆盖统一名称。只有管理者能按 BotFather 指引修改该 Bot 的名称、头像；不因绑定拥有 token 就替用户改远端资料。
3. 在现有 `send` 中为显式图片附件增加 `sendPhoto` 的小分支，复用 FormData、可信 Bot 选择及请求函数，校验图片限制。其余附件继续 `sendDocument`，普通文字分支保持。首版仍是短文字与图片两步，不另做 caption 合并、相册或富卡。
4. 引导只取 `address.conversationKey` 私聊目标，不带 `telegramGroup`、`reply_parameters` 或群话题字段。每步沿原回执核对服务端消息 ID、返回会话和 Bot 身份；明确 Telegram 拒绝为 failed，其余效果不明为 unknown。

**降级与风险。** 准备时无法满足图片要求则走原 `sendDocument`，或者只发文字并删去上传头像句；实际图片发送失败之后不自动发文件。用户封禁 Bot、删除 Bot、权限或网络变化按发送结果处理，不测试性发送／自动解除 Webhook／另启配对。BotFather 资料修改是面向该 Bot 的公开变化，不是 Homer 私有备注；没有管理员权限的用户仍能正常使用，不把修改资料设为绑定成功条件。

**去重与兼容。** 换 token、重启、同身份重新授权沿原绑定状态，不欢迎；解绑再配对按新 ID 处理。群成员变化、隐私模式和群背景补读不触发引导，不影响现有群请求路由。

**最小验收。** 在 [telegram-channel.test.ts](../tests/telegram-channel.test.ts)补：配对未确认／应用失败零发送；确认就绪后仅原私聊一组；`sendPhoto` 字节及回执身份校验；无图分支与业务 `sendDocument` 保持；多 Bot 不串发；群／话题更新不触发。复用共用未知／重启用例。**已有架构记录可作为普通私聊和文件基线；本引导及 Telegram 图片、BotFather 手动设置效果均未实测，不能借微信图片证据验收。** [官方图片接口](https://core.telegram.org/bots/api#sendphoto)

### 9.4 钉钉：配对确认后发送文字和头像文件

**当前源码。** [DesktopChannels.authorizeDingtalk](../src/desktop-channels.ts)先核验 AppKey／AppSecret，再经一次性私聊指令核验组织、员工和会话，用户确认后应用。[DingtalkChannel](../src/dingtalk-channel.ts)从 Stream 更新 ready；发送用主动单聊 `oToMessages/batchSend`，文字使用 `sampleText`，附件使用已有 `/media/upload?type=file` 和 `sampleFile`。本轮不依赖未核验的图片模板能力。

1. 新绑定确认并应用后，等待同一 Stream ready，再由可选准备方法提供身份说明和文件形式头像。只认已核验的账号、组织、员工和会话；Stream ready 表明连接状态，不证明出站权限齐全，权限错误留给原发送路径明确报告，不加权限探测消息。
2. 固定说明建议为：「你好，我是荷马 Homer，已连接到这个钉钉私聊。附上荷马头像，方便识别；如需修改机器人名称或头像，请联系该机器人管理员。」文件省略时去掉「附上」句。配对员工身份不等于应用管理员，不指导用户修改个人账号资料，也不猜客户端设置路径。
3. 文字复用 `sampleText`，头像按既有附件结构传 `homer-avatar.png` 和原始 PNG 字节，复用 `sampleFile` 全流程。不新增图片模板、上传服务、存储或权限。访问令牌及 legacy 上传令牌继续使用原缓存和取消逻辑。
4. `userIds` 只含原绑定的一名员工，不向群、组织全员或其他账号发送。成功回执仍是 `processQueryKey`；命中无效／限流员工列表沿现有失败判断，不能仅以 HTTP 成功当作送达。进入主动发送后效果不明就停止引导后续步骤。

**降级与风险。** 当前文件上限为 20,000,000 字节，文字阈值 2,048 UTF-8 字节；内置头像及短文案先按这些现有检查校验。无可用头像文件则仅身份说明。文件的客户端预览、保存及用作头像效果待验证，不承诺内联显示。若部署者明确只允许文字，不为头像自动申请新权限；准备时选无图即可。实际上传／发送失败按共用终态展示，不自动换身份、模板或收件人。

**去重与兼容。** AppSecret 更新保留原绑定和引导状态；解绑后新配对才可新发。保持原配置私有权限、Stream 单连接和停稳语义，不把 `dt-…` 当品牌名，不向配置另写引导账本。

**最小验收。** 在 [dingtalk-channel.test.ts](../tests/dingtalk-channel.test.ts)补：确认前／Stream 未 ready 零发送；就绪后短文字及头像文件两步；组织／员工／会话不匹配禁止发送；原 PNG 字节、文件名、单员工目标及 `processQueryKey`；缺图只文字，上传失败和发送未知不换形式重投。共用绑定恢复用例不逐渠道复制。**既有普通文字／文件实网记录是基线；本引导、头像文件显示及管理员设置流程仍待产品专项验收。**

### 9.5 实施顺序与停止条件

按「共用绑定状态与恢复 → 三个小准备方法 → 微信／Telegram 图片分支 → 现有详情文案」实施；钉钉发送方法可直接复用，不为三渠道对称而增加代码。先在已有测试文件覆盖行为，再接真实渠道专项。无新增依赖、通用媒体框架或渠道独立管理器。

共用层在 [channel-plugin.test.ts](../tests/channel-plugin.test.ts)、[desktop-channels.test.ts](../tests/desktop-channels.test.ts)核验一次即可：

- 升级列与旧账号基线事务回滚／重启，不把旧配置当新用户欢迎。
- 配置保存后、绑定提交前退出，再启动可恢复新绑定 pending；已提交的绑定不二次登记。两者必须同时满足，不能用「全部启动时跳过」规避丢失意图。
- 三个适配器未就绪后异步变为 ready，可唤醒 pending；适配器不实现可选接点时保持原行为。
- 不同账号及不同渠道的状态独立；重配等待在途分片、注销撤权、遗留 sending 及回执落库失败沿原安全恢复。
- 文字成功、头像未知时不重复文字；无图仍能完成文字指引；首次业务输入不丢失、不因引导失败重新调用模型。

实施时优先扩展现有测试文件与协议替身，不为短固定文案建立一套测试框架。若增加真实渠道专项，按项目规则登记至 `scripts/test.mjs` 并更新 `docs/testing.md`，不纳入默认离线测试。

完成产品实现的条件是：最小相关离线检查通过，实际设置组件验证通过，获授权的逐渠道实网确认显示与重启不重复。某渠道专项未跑就保留其未验证状态；微信隔离实测、旧版 Telegram／钉钉文件回执不能替代本功能验收。**当前三渠道实施步骤均为待执行方案，本轮只更新文档。**
