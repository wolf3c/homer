# 事项归档与工作环境收尾方案

更新日期：2026-11-04。

本文保留当时的生命周期设计和隔离试验。通用原则继续沿用；当前会话工具接线与最新验收以[会话架构及实施记录](architecture/main-worker-chat-architecture.md)为准，旧派工接口不再是正式入口。

状态：正式归档事件、原生 Skill 选择和内置分发已接入；Main／Worker 共用的有限生命周期授权约束已接入源码，并以正式 `on-request` 配置完成 ChatGPT 隔离验证。方案复用现有服务生命周期，不新增跨 Worker 停服机制；Skill、审批逻辑、沙箱及旧实例未改。多场景稳定性、并发恢复及脱管例外仍有验证边界。

## 目标与职责

让 Agent 对自己及所委派 Worker 留下的工作环境负责：回收已无用途的临时资源，保全有价值的成果和其他工作，让后续任务可以继续使用整洁、可靠的环境。

| 层次 | 职责 |
| --- | --- |
| 主 Agent system prompt | 保留简短的童子军原则，不追加文件类型举例或清理流程。 |
| 宿主 | 在实际归档后可靠发送事实事件，并为该事件轮显式加载归档 Skill。 |
| 归档 Skill | 提供通用判断方法与现有工具的必要用法，不枚举删除对象。 |
| 主 Agent | 理解当前状况，决定是否及如何派 Worker，检查结果并承接未完成部分。 |
| Worker | 在明确范围和既有授权内检查、处置资源，提供实际结果和保留原因。 |

主提示词保留现有表述：

> **童子军原则（Boy Scout Rule）**：让工作环境在你离开时比来时更整洁；保全有价值的成果与工作，遵守既有授权边界。

归档是复核时机，不表示所有资源都已失去价值，也不增加权限。

## 归档触发与执行链路

```text
事项实际归档 → 持久事实事件 → 主 Agent 事件轮显式加载 Skill
→ 主 Agent 检查上下文并决定是否派工 → Worker 检查与处理 → 主 Agent 核验结果
```

- 用户和 Agent 发起的归档统一从实际状态变更触发，不依赖调用方另发消息。归档失败、受阻、重复调用及恢复归档不产生新的归档事件；恢复后再次归档是新事件。
- 事件仅携带事项标识、版本和归档修订等事实，不写“请清理”，不伪装成用户消息。资源线索优先从现有任务记录、交付物和执行记录取得；信息不足时在任务范围内检查，不扫描整机。
- 宿主显式选择 `homer-archive-review`，通过引擎已有的原生 Skill 输入加载；不依赖模型仅凭 Skill 描述自行触发。缺失、禁用或加载失败须记录复核未完成，不静默宣称已收尾，不覆盖用户的禁用选择。
- 复用现有消息、回执、操作幂等及待办机制。相同事件重投先核已有处理，不重复派工；处理中断或结果未知时先恢复事实，不盲目重做删除或停服。
- 收尾 Worker 自己归档时同样复核；没有新增遗留或已有有效处理结果时结束，不强制再创建 Worker，避免无限递归。

通知已处理只证明主 Agent 收到并处理了事件，不能证明资源已检查或清理完成。事项归档须先满足原任务结算与退出检查，不等待归档后新派的收尾任务完成；未完成的收尾沿既有任务或待办继续承接。

## 复用受管服务生命周期

普通受管服务沿现有链路结束：Worker 返回 → 宿主关闭原执行器 → 确认退出并清除 lease → 验收、结算 → 允许归档。原执行器负责其受管会话，归档收尾不再接管这些会话，也不为归档延长执行器寿命。

依据：[Worker 结束与关闭](../src/service.ts)、[固定执行器生命周期](../src/engine.ts)、[归档检查](../src/recursive-tasks.ts)。等待中、关闭未确认或恢复未完成的任务不能正常归档；启动恢复沿现有 lease 核实并停止遗留执行器，失败须保留不确定状态。

归档收尾聚焦实际留下的资源，例如临时工作树、构建文件、日志和失效会话记录，仍按归属、当前用途、独有价值、依赖及既有授权判断。进程退出不等于文件应删除；收尾完成也不以删除所有资源为标准。

| 运行中服务的例外 | 处理边界 |
| --- | --- |
| 启动脚本自行脱管，服务逃离原受管会话 | 已有隔离执行器实测证明可能在原执行器退出后继续运行。先核对实际启动方式、归属及已有管理入口；原句柄可能已失效，不能靠转发句柄字符串接管。 |
| 服务属于其他任务、主 Agent 或独立服务管理器 | 原事项归档不表示它失去用途或转移所有权。根据真实用途及依赖判断，保全共享和仍在使用的资源；未做这些业务场景的完整验收。 |
| 原执行器停止未确认或异常恢复 | 属于原有生命周期和恢复流程的问题，不作为归档后正常遗留来绕过检查。不能将未知状态标成已停止。 |

当前不新增跨 Worker 停服接口、长期控制连接、资源登记实体或进程管理器。只有真实业务暴露现有机制无法处理的具体缺口，再据证据评估最小修改；测试夹具制造的状态不构成新增能力的需求。

## Skill 的通用判断方法

Skill 应围绕以下问题组织，保持短小，不把测试场景、路径、文件名、端口、容量阈值或删除命令写成规则：

1. **归属与目的**：资源由谁创建、服务什么目标，与本事项及其他工作有什么关系？
2. **当前价值**：是否仍被使用、被交付承诺依赖，或包含独有工作、恢复材料和必要证据？
3. **处置边界**：拟采取的动作是否在原有授权内，影响哪些使用者，误判后能否恢复、代价多大？
4. **实际结果**：处置是否成功，有价值内容和依赖是否保全，剩余部分为什么保留？

主 Agent 有必要时安排 Worker 调查和执行，无需收尾也是正常结论，但必须有事实依据。Worker 接收当前任务需要的范围与约束，不机械复制整篇 Skill。

“已归档”“可重建”“名称像临时文件”“时间很久”“无人打开”均不能单独证明可删除；同样，不能用抽象的“无法排除任何用途”无限保留。应指出具体风险和缺失证据，做与影响及恢复代价相称的核验。核验仍不足时保留相关部分，其他可独立处理的部分继续完成。

针对不同资源的专业检查由执行时选择合适工具完成；Skill 不维护一套按文件类型分支的清理脚本。存在当前依赖就先解决依赖，再判断处置，不能为了清理破坏原件、交付或并行工作。

## 授权：必须正面解决的边界

这里有两个不同问题：

| 问题 | 处理方式 |
| --- | --- |
| 事件轮如何派 Worker？ | 沿原事项查真实用户来源，通过现有待办选择机制派工，不制造新用户请求。此路径已在隔离测试跑通。 |
| Worker 能否处置某项资源？ | 根据真实用户授权、项目约束和资源生命周期判断。能够派工不等于获得删除或停服许可。 |

### 共用的有限生命周期授权合同

> 任务授权包含 Agent 为完成本任务自行创建、仅服务本任务的临时资源的必要生命周期管理：核实已无用途、无独有价值且无其他依赖后，可在原任务范围内回收，无须逐项再次申请。用户原有、共享、持久、归属不明及仍有用途的资源不在该许可内；用户明确限制和宿主审批继续生效。

该约束在现有 [loadPrompts](../src/prompts.ts) 中统一附加给 Main 和 Worker，不增加配置、授权记录或清理接口。它界定用户任务授权内的必要生命周期管理，Skill 只解释如何判断，不自行授予权限。原始业务消息及归档通知不添加清理提示，真实来源和待办派工机制保持原样。

仅有 Agent 创建这一事实还不够：资源后来承载独有工作、成为交付依赖或被其他事项使用后，就不满足回收条件。判断基于可核验的当前事实，不要求证明世界上不存在任何未知用途，也不能把缺失记录当作无人使用。

源码接入不等于旧实例已采用。当前未打包、安装或重启日常实例，也不追溯修改旧任务授权；正式发布及日常实例验收另行安排。宿主审批继续独立生效，不能只在 Skill 中加强删除措辞或为特定目录增加豁免。

用户原有文件、共享或持久资源、仍有用途及归属不明的资源继续遵守各自授权。需要额外授权时，只询问影响判断的具体部分，不要求用户具备清理工具的专业知识。

## 验证记录与边界

以下均为隔离试验，不是日常实例或全平台验收。真实模型采用 ChatGPT 登录的实际配置：Main `gpt-6.1-terra / high / priority`，Worker `gpt-6.1-terra / xhigh`，固定 Codex `0.163.0`。最新验证从产品加载共用约束；此前夹具注入授权且覆盖为 `never` 的样本不代表正式审批配置已验证。

| 试验 | 有效结论与限制 |
| --- | --- |
| 早期候选 Skill、有限授权验证 | 曾由测试程序加载 Skill、补充资源事实；观察到自主派工、保全和部分回收，也有因授权解释而全部保留的样本。早期停服失败使用脱管服务，不能泛化为普通受管服务无法回收。 |
| 共用授权与正式审批配置 | 最新样本不注入授权文本、不覆盖产品审批配置，断言 Main／Worker 实际请求均为 `on-request`。仅发归档事实，产品自动加载 Skill；Main 自主派工，Worker 经检查及一次 `ask_main` 确认后移除临时 worktree、Git 登记、构建及中间文件和失效会话记录，两项任务均成功，无待用户审批。原报告、正式成果、7 个保护文件及另一 worktree 独有修改保全；134 字节构建日志被判断为验收证据而保留，不能宣称所有日志均已回收。49 项定向离线检查及类型检查通过。 |
| 四种用途与保全场景 | 同一配置下每种各测一次：用户明确保留时未派收尾 Worker；保留条件结束后自主派工并回收工作树、构建、日志及失效会话记录；共享依赖的实际消费者前后均可用，资源保留；独有草稿摘要不变，失效会话记录被回收。均保全正式成果和保护文件。共享及独有工作场景的收尾状态为 `partial`；保留本身不是失败，未证明可独立回收的部分也不能算已回收。条件到期场景的原业务曾因预览持续性解释结算为 `partial`，归档收尾成功；原文的解释空间不能直接认定为产品缺陷。 |
| 正式自动接线 | 只发归档事实、产品自动加载 Skill，Main 自主查记录并派工。曾自行追加“保留可用预览”并在归档后重启服务，说明触发成功不等于判断正确或完整回收。 |
| 来源与阶段复核、后续复验 | 普通受管样本中，服务在原 Worker 执行器关闭时、归档前已退出；归档后自主 Worker 实际移除临时 worktree 及 Git 登记、构建及中间文件、日志和失效会话记录。原报告、正式成果、7 个保护文件及另一 worktree 独有修改保全。证明这些样本完整回收，不证明所有场景稳定成功。 |
| 固定执行器协议验证 | 非真实模型行为测试。原连接的会话控制及关闭有效，其他执行器不能直接复用句柄；自行脱管的服务可在原执行器关闭后继续运行。发现可用原语，不等于已接入跨 Worker 产品控制。 |
| 延后关闭、却返回成功的夹具 | 服务被留活，但 Homer 因虚假成功删除了原运行槽和 lease。该生命周期状态无效，不能作为正常产品停服失败或新增机制的依据。 |
| 修正为真实 pending close 的夹具 | 原运行槽、lease、连接和服务均保留；Main 判断任务尚未结算，只记录归档请求，未调用停止入口。没有实际归档、事实通知、Skill 轮或收尾 Worker。观察后宿主真实关闭执行器并停服，仅算测试撤除。 |

## 实施顺序与完成条件

1. 复用现有受管服务关闭、停止及恢复链路；不新增跨 Worker 停服机制，不修改 Skill、审批逻辑或沙箱。
